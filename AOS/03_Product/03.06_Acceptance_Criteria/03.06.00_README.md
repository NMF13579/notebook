Acceptance Criteria

Назначение документа

Этот документ определяет критерии, по которым оценивается соответствие продукта ожидаемому поведению.

Acceptance Criteria не описывают способ реализации.

Они определяют:

* какой observable behavior ожидается;
* какие условия считаются выполненными;
* какие результаты являются недостаточными;
* что может быть подтверждено;
* что не может считаться доказанным;
* какие проверки необходимы;
* какие решения остаются за человеком.

Acceptance Criteria являются критерием оценки продукта, а не инструкцией по его реализации.

⸻

Acceptance в AOS

Acceptance означает:

пользовательское поведение соответствует заранее определённому Product Contract.

Acceptance не означает автоматически:

* техническое совершенство;
* отсутствие известных ограничений;
* отсутствие future work;
* production readiness;
* завершённость всей системы;
* разрешение на commit;
* разрешение на release.

Каждая acceptance boundary относится только к своему объекту проверки.

⸻

Что считается Acceptance

Acceptance подтверждает только то, что было проверено.

Например:

Primary User Journey
accepted

означает:

* journey соответствует ожидаемому поведению;
* observable behavior подтверждён;
* acceptance criteria выполнены.

Это не означает:

Product complete

или

All Product Contracts implemented

⸻

Acceptance Boundary

Каждый acceptance должен иметь явную boundary.

Например:

* один Product Contract;
* один User Journey;
* один Vertical Slice;
* один Feature;
* один Stage;
* один документ;
* один validation scenario.

Запрещается использовать неопределённые формулировки:

Система готова.

Всё работает.

Проект завершён.

Без определения конкретной boundary.

⸻

Acceptance Sources

Acceptance может использовать:

* Product Contracts;
* User Journeys;
* Acceptance Criteria;
* Validation Reports;
* Human Review.

Acceptance не должен основываться только на:

* сообщении агента;
* успешной генерации документа;
* наличии кода;
* наличии тестов;
* количестве файлов;
* CI PASS.

⸻

Observable Acceptance

Acceptance должно быть связано с тем, что может наблюдать пользователь.

Пример.

Плохой критерий:

Внутренняя архитектура стала лучше.

Хороший критерий:

Пользователь может открыть проект и менее чем за минуту определить:

* текущий stage;
* active task;
* pending decision;
* next action.

⸻

Acceptance Levels

Level 1 — Documentation Acceptance

Проверяется:

* полнота документа;
* непротиворечивость;
* соответствие соседним контрактам;
* отсутствие ложных утверждений;
* отсутствие implementation claims.

Не проверяется:

* runtime behavior.

⸻

Level 2 — Workflow Acceptance

Проверяется:

* возможность пройти manual workflow;
* соблюдение contracts;
* корректность boundaries;
* понятность reports.

⸻

Level 3 — Product Acceptance

Проверяется:

* достигает ли пользователь ожидаемого outcome;
* уменьшилась ли когнитивная нагрузка;
* понятен ли workflow;
* понятно ли следующее действие.

⸻

Level 4 — Technical Acceptance

Проверяется:

* конкретная реализация;
* проверки;
* runtime behavior;
* соответствие implementation контрактам.

⸻

Acceptance для First Vertical Slice

First Vertical Slice считается содержательно успешным, если пользователь способен выполнить полный цикл:

intent
→ Task Brief
→ execution authorization
→ execution
→ Execution Report
→ validation
→ Validation Report
→ human review
→ next action
→ stop

без необходимости самостоятельно восстанавливать workflow.

⸻

Acceptance для Current State

Критерий считается выполненным, если пользователь способен без просмотра chat history определить:

* где находится workflow;
* какая задача активна;
* какой stage последний;
* что требует решения;
* что делать дальше.

⸻

Acceptance для Task Brief

Task Brief считается достаточным, если независимый исполнитель способен понять:

* цель;
* scope;
* ограничения;
* проверки;
* stop conditions;

без дополнительных предположений.

⸻

Acceptance для Scope

Scope считается корректным, если:

* разрешённые изменения перечислены;
* запрещённые изменения перечислены;
* попытка выйти за scope приводит к остановке.

⸻

Acceptance для Human Authority

Acceptance достигается, если система нигде не:

* симулирует approval;
* симулирует Risk Profile;
* симулирует acceptance;
* автоматически выполняет обязательные решения.

⸻

Acceptance для Validation

Validation считается корректной, если:

* выполняется отдельно;
* не изменяет artifacts;
* фиксирует UNKNOWN;
* фиксирует NOT_RUN;
* формирует Validation Report;
* завершается остановкой.

⸻

Acceptance для Reports

Execution Report и Validation Report считаются достаточными, если независимый reviewer способен понять:

* что произошло;
* что проверено;
* что неизвестно;
* какие findings существуют;
* какое следующее действие требуется.

⸻

Acceptance для Session Resume

Resume считается успешным, если пользователь после новой session способен продолжить работу без чтения всей предыдущей истории.

⸻

Acceptance для One Next Action

Критерий выполнен, если после каждого stage существует одно основное следующее действие.

Пользователь не должен выбирать между несколькими равнозначными направлениями.

⸻

Acceptance для Unknown Handling

Unknown считается обработанным корректно, если:

* неизвестный факт явно показан;
* объяснено его влияние;
* определено следующее действие;
* неизвестность не скрывается.

⸻

Acceptance для Git Boundaries

Критерий считается выполненным, если пользователь понимает различие между:

Edit
Commit
Push
Merge
Release

и каждое действие требует собственного решения.

⸻

Negative Acceptance

Следующие ситуации автоматически означают, что acceptance не достигнут:

* scope расширился автоматически;
* validation исправила artifact;
* approval был симулирован;
* UNKNOWN скрыт;
* next action отсутствует;
* workflow продолжается автоматически после stage;
* человек потерял понимание текущего состояния.

⸻

Acceptance Evidence

Evidence может подтверждать:

* прохождение сценария;
* выполнение проверки;
* результаты validation;
* поведение продукта.

Evidence не подтверждает автоматически:

* acceptance;
* approval;
* release readiness.

⸻

Human Acceptance

Окончательное решение о принятии результата всегда принадлежит человеку.

Даже если:

* проверки успешны;
* Product Contracts соблюдены;
* Validation PASS;
* CI PASS.

Человек может:

* принять;
* отклонить;
* потребовать correction;
* изменить scope;
* отложить решение.

⸻

Минимальный набор Acceptance Criteria для первой версии

Первая версия AOS считается концептуально успешной, если пользователь способен:

1. Понять текущее состояние проекта.
2. Сформулировать intent.
3. Получить bounded Task Brief.
4. Отдельно разрешить execution.
5. Получить понятный Execution Report.
6. Запустить независимую validation.
7. Получить понятный Validation Report.
8. Принять решение самостоятельно.
9. Получить одно следующее действие.
10. Возобновить работу после новой session.

⸻

Что не является Acceptance

Не считаются критериями принятия:

* количество документов;
* количество строк кода;
* количество агентов;
* использование LLM определённого класса;
* наличие registry;
* наличие Control Plane;
* наличие сложной архитектуры;
* использование определённого framework.

Acceptance определяется исключительно достижением пользовательского результата.

⸻

Инварианты

Во всех Acceptance Criteria сохраняются фундаментальные правила:

PASS ≠ approval.
Evidence ≠ approval.
CI PASS ≠ approval.
UNKNOWN ≠ OK.
NOT_RUN ≠ PASS.
Human approval cannot be simulated.
Skeleton ≠ implementation.
Documentation ≠ technical completion.
Plan output ≠ Task Brief.
Plan output ≠ execution authorization.
Routing decision ≠ execution authorization.

⸻

Acceptance Statement

Acceptance в AOS означает подтверждение конкретного Product Contract через наблюдаемое поведение в пределах заранее определённой boundary.

Acceptance не является техническим, организационным или юридическим разрешением на последующие действия.

⸻

Краткое резюме

Acceptance оценивает не внутреннюю реализацию, а пользовательский результат.

Каждый критерий должен быть:

* наблюдаемым;
* проверяемым;
* ограниченным;
* связанным с Product Contract;
* независимым от конкретной реализации;
* понятным пользователю.

Acceptance подтверждает только ту boundary, которая была явно определена и проверена.
