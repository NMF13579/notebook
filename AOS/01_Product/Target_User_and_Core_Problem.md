Target User and Core Problem

Назначение документа

Этот документ определяет:

* основного пользователя первой версии AOS;
* рабочий контекст этого пользователя;
* проблему, которую пользователь пытается решить;
* последствия существующего способа работы;
* желаемый пользовательский результат;
* ограничения текущих инструментов;
* границы initial product scope.

Документ описывает пользовательскую проблему, а не architecture, implementation или полный набор product features.

Он не утверждает, что сформулированные гипотезы уже подтверждены пользовательским исследованием или работающим Product Runtime. Их необходимо будет проверить через последующие product discovery, contracts, manual workflows и первый vertical slice.

⸻

Primary Target User

Основной пользователь первой версии AOS — человек, который создаёт или изменяет software product с помощью AI coding agents, но не располагает устойчивой инженерной системой управления такой разработкой.

Типичный primary user:

* product owner;
* founder;
* domain expert;
* non-programmer;
* начинающий разработчик;
* vibe coder;
* team lead, управляющий агентной разработкой без полноценной engineering organization.

Пользователь может понимать желаемый product outcome, business domain и пользовательские потребности, но не обязан глубоко разбираться в:

* software architecture;
* Git workflows;
* dependency management;
* CI;
* test strategy;
* release engineering;
* agent orchestration;
* Governance;
* recovery procedures.

Primary user способен принимать продуктовые решения, но нуждается в системе, которая помогает преобразовывать эти решения в ограниченные, проверяемые и понятные изменения.

⸻

Основная характеристика пользователя

Главная характеристика primary user определяется не уровнем программирования, а способом работы.

Этот пользователь:

* формулирует намерение естественным языком;
* передаёт задачи одному или нескольким AI agents;
* оценивает результат преимущественно по объяснениям агента и видимому поведению продукта;
* часто не может самостоятельно проверить все технические последствия изменения;
* работает итеративно;
* регулярно меняет или уточняет требования;
* зависит от сохранения контекста между сессиями;
* хочет быстро двигаться к product value;
* не хочет вручную управлять сложной внутренней инфраструктурой разработки.

Даже технически опытный человек может относиться к primary target group, если он использует AI agents как основных исполнителей и сталкивается с теми же проблемами контроля, контекста и доверия.

⸻

Рабочий контекст

Пользователь обычно начинает не с полного технического задания, а с намерения:

* создать новый продукт;
* добавить возможность;
* исправить проблему;
* переработать существующий компонент;
* продолжить незавершённую работу;
* проверить состояние проекта;
* понять, что делать дальше.

Исходное намерение часто является:

* неполным;
* неоднозначным;
* слишком широким;
* не связанным с текущим состоянием repository;
* не разделённым на planning, execution и validation;
* не обеспеченным явными acceptance criteria;
* не ограниченным конкретным scope.

AI coding assistant может начать немедленно генерировать изменения, хотя пользователь ещё не определил:

* точную проблему;
* допустимые границы;
* ожидаемый результат;
* baseline;
* запрещённые изменения;
* способ проверки;
* условия остановки;
* действия, требующие отдельного human decision.

В результате скорость генерации кода оказывается выше скорости понимания и контроля проекта.

⸻

Текущий способ работы

Без AOS типичный цикл выглядит следующим образом:

идея
→ prompt
→ изменения агента
→ объяснение результата
→ новый prompt
→ дополнительные изменения
→ рост контекста
→ потеря понимания состояния
→ попытка восстановления

Пользователь ведёт работу через длинную последовательность chat sessions, терминальных команд, Git changes и документов.

Часть состояния существует в repository, часть — в сообщениях, часть — только в объяснениях агента, а часть остаётся неявной.

Пользователь вынужден самостоятельно связывать:

* исходное намерение;
* принятые решения;
* текущий scope;
* выполненные изменения;
* результаты проверок;
* незавершённые действия;
* текущий Git state;
* риски;
* следующий шаг.

По мере роста проекта эта работа становится отдельной задачей, требующей всё больше внимания.

⸻

Core User Problem

Основная проблема состоит не в том, что AI agent не способен написать код.

Проблема состоит в том, что пользователь не может устойчиво управлять переходом:

намерение
→ ограниченная задача
→ контролируемое изменение
→ независимая проверка
→ понятный результат
→ human decision

Обычный AI coding workflow плохо сохраняет границы между этими состояниями.

Пользователь не всегда может достоверно определить:

* что именно сейчас делает агент;
* на основании какого контекста он действует;
* входит ли изменение в согласованный scope;
* какие файлы и факты являются Source of Truth;
* было ли изменение фактически выполнено;
* какие проверки действительно запускались;
* означает ли PASS техническую проверку или human acceptance;
* какие выводы доказаны, а какие только заявлены;
* завершён ли текущий этап;
* безопасно ли переходить к следующему;
* какое одно действие требуется от пользователя.

В результате проект может продолжать изменяться, хотя его фактическое состояние уже перестало быть понятным человеку.

⸻

Problem Statement

Primary user нуждается в способе управлять AI-assisted development так, чтобы в каждый момент было возможно установить:

1. какое пользовательское намерение рассматривается;
2. какая bounded task из него сформирована;
3. какой scope разрешён;
4. какое действие выполняется сейчас;
5. что фактически изменено;
6. какие проверки выполнены;
7. какие результаты остаются UNKNOWN или NOT_RUN;
8. где требуется human decision;
9. какое одно действие следует дальше.

Без этого AI-assisted development быстро превращается в последовательность локально правдоподобных действий без устойчивой общей управляемости.

⸻

Почему проблема возникает

Высокая скорость изменений

AI agents способны создавать и изменять большое количество artifacts быстрее, чем пользователь успевает:

* понять их;
* проверить;
* сопоставить с product intent;
* обнаружить scope drift;
* оценить долгосрочные последствия.

Неполный исходный контекст

Пользователь часто формулирует задачу на уровне результата, а не технического контракта.

Агент вынужден делать предположения. Если предположения не обозначены явно, они могут незаметно стать частью продукта.

Смешивание этапов

Одна agent session может одновременно:

* анализировать;
* планировать;
* изменять files;
* запускать validation;
* исправлять найденные ошибки;
* создавать commit;
* предлагать merge.

При таком смешивании пользователь теряет возможность независимо оценить каждый этап.

Потеря контекста между сессиями

Решения, ограничения и незавершённые действия часто остаются внутри chat history.

Новая session может не знать:

* почему решение было принято;
* какие варианты были отклонены;
* какие риски уже обнаружены;
* где остановилась предыдущая работа;
* что разрешено делать дальше.

Неоднозначные claims

Такие заявления, как:

* «готово»;
* «всё работает»;
* «проверено»;
* «безопасно»;
* «можно merge»,

могут означать разные вещи.

Без явных contracts пользователь не может отличить:

* implementation claim;
* validation result;
* Evidence;
* approval;
* readiness;
* Git authorization.

Распределённое состояние

Фактическое состояние проекта может быть распределено между:

* repository;
* working tree;
* Git history;
* chat sessions;
* issue tracker;
* local files;
* generated reports;
* CI;
* внешними сервисами;
* памятью пользователя.

При отсутствии определённых источников истины эти представления начинают противоречить друг другу.

⸻

Последствия проблемы

Scope drift

Агент начинает решать соседние задачи или улучшать систему сверх исходного намерения.

Локально такие изменения могут выглядеть полезными, но они:

* увеличивают объём проверки;
* изменяют architecture;
* создают новые dependencies;
* усложняют rollback;
* отдаляют первый полезный product outcome.

Ложное ощущение завершённости

Наличие code, documentation или PASS-результата может восприниматься как завершение работы.

Однако:

Skeleton ≠ implementation.
Documentation ≠ technical completion.
PASS ≠ approval.
Evidence ≠ approval.
CI PASS ≠ approval.

Потеря доверия

Если пользователь не может проверить утверждения агента, он вынужден либо:

* доверять им без достаточных оснований;
* вручную перепроверять всю работу;
* прекращать использовать automation.

Во всех трёх случаях ценность AI-assisted development снижается.

Repair loops

После накопления неясностей работа смещается с развития продукта на восстановление состояния:

неясное состояние
→ аудит
→ исправление
→ новый аудит
→ новые противоречия
→ очередное восстановление

Recovery начинает потреблять больше ресурсов, чем product development.

Преждевременная сложность

Попытка сразу решить все проблемы контроля может привести к созданию:

* Control Plane;
* registry;
* сложного Governance;
* autonomous workflows;
* Runtime Enforcement;
* многочисленных schemas;
* собственной orchestration infrastructure.

Такая инфраструктура создаётся до подтверждения основной product value и сама становится источником новых проблем.

Зависимость от конкретного агента

Если процесс существует только в поведении одной модели или одном длинном chat, проект становится трудно:

* продолжать другим агентом;
* проверять другим человеком;
* воспроизводить;
* переносить;
* восстанавливать.

Непонятное следующее действие

После завершения agent response пользователь часто получает:

* длинный список рекомендаций;
* несколько равнозначных вариантов;
* предложения дополнительных улучшений;
* новые задачи, не входившие в исходный scope.

Пользователь остаётся без ясного ответа на вопрос:

Что конкретно требуется сделать сейчас?

⸻

Desired User Progress

Пользователь не пытается получить максимальное количество автоматически сгенерированных изменений.

Он пытается безопасно и последовательно продвигать продукт вперёд.

Желаемый progress:

от неструктурированного намерения
к понятной bounded task
от bounded task
к контролируемому изменению
от изменения
к проверяемому результату
от результата
к осознанному human decision
от human decision
к одному следующему действию

Ценность AOS должна измеряться не количеством automation, документов или control mechanisms, а способностью пользователя сохранять понимание и контроль во время развития продукта.

⸻

Основной пользовательский outcome

В любой момент пользователь должен иметь возможность понять:

* что сейчас происходит;
* почему выполняется именно это действие;
* какой scope разрешён;
* что уже сделано;
* что проверено;
* что не проверено;
* какие проблемы обнаружены;
* требуется ли human decision;
* какое одно действие следует дальше.

Этот outcome должен сохраняться:

* между agent sessions;
* между разными agents;
* между planning, execution, validation и review;
* при успешном выполнении;
* при failure;
* при UNKNOWN;
* при остановке задачи;
* при возобновлении работы.

⸻

Job to Be Done

Когда пользователь хочет создать или изменить software product с помощью AI agents, он хочет преобразовать своё намерение в ограниченный и проверяемый цикл работы, чтобы продвигать продукт вперёд, не теряя понимание scope, состояния, результатов и необходимых решений.

Формула Job to Be Done:

Когда я поручаю AI agent изменить мой продукт, я хочу видеть, что именно разрешено, что фактически сделано, как это проверено и какое решение требуется от меня дальше, чтобы я мог использовать возможности агента без потери контроля над проектом.

⸻

Существующие способы решения

Обычный chat с coding assistant

Пользователь формулирует запрос и получает:

* explanation;
* code;
* commands;
* иногда validation result.

Этот способ эффективен для коротких изолированных задач, но плохо управляет длительным состоянием проекта.

Ручное ведение документации

Пользователь самостоятельно поддерживает:

* specifications;
* plans;
* notes;
* TODO;
* decision logs;
* status reports.

Это повышает прозрачность, но требует постоянной дисциплины и часто расходится с фактическим состоянием repository.

Git и pull request workflow

Git хорошо хранит изменения и историю commits, но сам по себе не объясняет:

* product intent;
* разрешённый scope;
* почему изменение было выполнено;
* какие assumptions использовал агент;
* является ли validation достаточной;
* какое human decision требуется.

Issue trackers

Issue tracker помогает хранить задачи, но не гарантирует:

* bounded execution;
* соответствие реальных изменений задаче;
* независимую validation;
* корректное разделение technical result и approval;
* восстановление session context.

Agent frameworks

Agent frameworks могут автоматизировать routing, tool use и multi-agent workflows.

Однако automation не решает проблему управления, если заранее не определены:

* contracts;
* boundaries;
* authoritative state;
* stop conditions;
* human checkpoints;
* правила обработки unknowns.

Собственная Control infrastructure

Проект может создать специализированные control mechanisms.

Но если они появляются раньше подтверждённого Product Runtime, пользователь начинает строить инфраструктуру управления вместо самого продукта.

⸻

Почему обычного Coding Assistant недостаточно

Coding assistant обычно оптимизирован для выполнения локального запроса.

Он может:

* объяснять;
* писать code;
* изменять files;
* искать ошибки;
* запускать commands;
* предлагать улучшения.

Но сам по себе он не обеспечивает устойчивую операционную модель проекта.

Он не гарантирует, что:

* исходное намерение стало bounded task;
* scope был принят человеком;
* assumptions явно зафиксированы;
* current repository state известен;
* validation независима от execution;
* failure остановит workflow;
* найденная ошибка не будет автоматически исправлена во время validation;
* technical PASS не будет представлен как approval;
* следующая стадия не начнётся автоматически;
* destructive action потребует отдельного разрешения;
* контекст сохранится для следующей session;
* другой агент сможет продолжить работу без восстановления всей истории.

Проблема требует не более сильного генератора кода, а более понятного и контролируемого взаимодействия между человеком, агентом и состоянием проекта.

⸻

Проблема, которая действительно требует AOS

AOS нужен не для замены IDE, Git, CI, coding assistant или project management system.

AOS нужен для организации границ и переходов между ними.

Ключевые границы:

intent

task
plan

execution authorization
execution

validation

human acceptance

approval

AOS должен помогать пользователю проходить эти границы явно и последовательно.

Основная product problem AOS:

AI agents способны выполнять значительную часть software development, но пользователю не хватает простого способа сохранять human authority, bounded scope, factual state, проверяемость и понятное следующее действие на протяжении всего рабочего цикла.

⸻

Initial Product Scope

Первая версия ориентирована на одного человека, управляющего одним software project через AI-assisted workflow.

Предполагаемый initial context:

* один primary human owner;
* один repository;
* одна активная bounded task;
* один writer в рамках этапа;
* ограниченное количество agents;
* локальная development environment;
* manual human checkpoints;
* repository-first factual state;
* chat-first interaction;
* последовательное выполнение stages;
* ручное принятие Git decisions.

Initial scope должен быть достаточным, чтобы проверить основной product promise без создания полной Development Factory или Control Plane.

⸻

Пользовательские группы вне Primary Scope

Первая версия не ориентирована непосредственно на:

Полностью автономные software organizations

AOS первой версии не должен автоматически планировать, реализовывать, проверять, merge и release изменения без human checkpoints.

Крупные enterprise organizations

Не предполагается начальная поддержка:

* сложных organizational hierarchies;
* enterprise IAM;
* cross-department approval workflows;
* regulatory compliance automation;
* multi-tenant control planes;
* large-scale portfolio management.

Команды с уже зрелой engineering platform

Организации с устойчивыми:

* platform engineering;
* release management;
* Governance;
* developer portals;
* policy engines;
* internal agent platforms,

могут иметь похожие потребности, но не являются primary target первой версии.

Пользователи, ожидающие только генерацию кода

Если пользователю требуется исключительно:

* code completion;
* одноразовый script;
* isolated code snippet;
* короткое объяснение;
* локальное исправление без project continuity,

обычного coding assistant может быть достаточно.

Пользователи без human decision role

AOS предполагает наличие человека, который имеет право:

* определять цель;
* ограничивать scope;
* принимать решения;
* разрешать рискованные действия;
* оценивать результат.

Система не должна симулировать отсутствие такого человека.

Non-software workflows

Первая версия сосредоточена на software product development.

Другие domains могут быть рассмотрены позднее, но не входят в initial product scope.

⸻

Сценарии вне Initial Scope

На первом этапе не требуется решать:

* autonomous multi-agent orchestration;
* automatic architecture governance;
* automatic Risk Profile assignment;
* automatic approval;
* automatic commit, push, merge или release;
* multi-project portfolio control;
* organization-wide policy enforcement;
* persistent global registry;
* full project knowledge graph;
* complex recovery platform;
* production Runtime Enforcement;
* third-party ecosystem integrations;
* graphical control dashboard;
* replacement of Git hosting platforms;
* replacement of IDE;
* replacement of existing CI systems.

Эти возможности могут появиться только после подтверждения основной пользовательской ценности и возникновения доказанной необходимости.

⸻

Product Boundary

AOS не должен забирать у пользователя authority.

Он должен уменьшать когнитивную нагрузку, необходимую для реализации этой authority.

AOS не принимает решения вместо человека.

Он должен:

* показывать, где требуется решение;
* предоставлять достаточный контекст;
* разделять факты, assumptions и claims;
* не продолжать работу при обязательном нерешённом human decision;
* завершать этап одним понятным next action.

⸻

Граница между Product Problem и Engineering Problem

Пользовательская проблема:

Я не могу устойчиво понимать и контролировать, как моё намерение превращается в изменения продукта через AI agents.

Engineering problems, которые могут возникнуть позднее:

* хранение project state;
* contract representation;
* agent routing;
* validation isolation;
* repository inspection;
* report generation;
* session handoff;
* tool integration;
* policy enforcement.

Engineering решения не должны определяться до того, как сформулированы:

* user outcome;
* vertical slice;
* user journey;
* observable behavior;
* acceptance criteria.

⸻

Основные Product Assumptions

На текущем этапе принимаются как гипотезы следующие положения:

1. Пользователю важнее понимать состояние и следующее действие, чем видеть внутреннюю сложность системы.
2. Один понятный bounded workflow полезнее, чем ранняя полная automation.
3. Chat-first interaction может быть достаточной для первой версии.
4. Repository может служить основным источником factual project state.
5. Явное разделение planning, execution, validation и review уменьшает число ошибок.
6. Отображение UNKNOWN и NOT_RUN повышает доверие сильнее, чем попытка всегда показывать успешный результат.
7. Одно следующее действие снижает cognitive overload.
8. Manual workflow должен быть проверен до его автоматизации.
9. Пользователь готов принимать явные решения, если система показывает их своевременно и понятно.
10. Minimal Safety Floor может обеспечить достаточный начальный контроль без полного Governance.

Эти assumptions должны быть проверены через последующие product artifacts и реальные пользовательские циклы.

⸻

Признаки того, что проблема сформулирована правильно

Формулировка core problem считается полезной для дальнейшей разработки, если она позволяет:

* определить один конкретный Product Runtime vertical slice;
* описать primary user journey;
* сформировать observable product contracts;
* определить acceptance criteria;
* отделить product value от internal infrastructure;
* исключить преждевременный Control Plane;
* провести manual workflow с реальной пользовательской задачей;
* проверить, стал ли следующий шаг понятнее пользователю.

Формулировка недостаточна, если она приводит только к созданию:

* новых документов;
* schemas;
* registries;
* agent roles;
* policies;
* automation;
* control mechanisms,

без наблюдаемого улучшения пользовательского workflow.

⸻

Критерий сохранения Product-First направления

Каждое последующее решение должно отвечать на вопрос:

Как это помогает primary user преобразовать намерение в ограниченный, проверяемый и понятный результат?

Если предлагаемая возможность не улучшает:

* понимание текущего состояния;
* bounded scope;
* качество результата;
* проверяемость;
* human decision;
* session continuity;
* ясность следующего действия,

она не должна становиться prerequisite первого полезного продукта.

Краткое определение

Primary User

Человек, который управляет созданием software product с помощью AI agents и нуждается в понятном способе сохранять контроль над scope, состоянием, результатами и решениями.

Core Problem

AI-assisted development создаёт изменения быстрее, чем пользователь способен устойчиво понимать, ограничивать и проверять их в рамках долгоживущего проекта.

Desired Outcome

В любой момент пользователь понимает:

что происходит
→ что сделано
→ что проверено
→ что требует решения
→ какое одно действие следует дальше

Product Direction

AOS должен сначала доказать этот outcome через минимальный Product Runtime vertical slice и manual workflow.

Development Factory, расширенный Governance, automation и Runtime Enforcement должны добавляться только после подтверждения необходимости.
