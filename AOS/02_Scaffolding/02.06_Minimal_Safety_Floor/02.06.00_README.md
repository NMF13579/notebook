02.06 — Minimal Safety Floor

Назначение

Этот документ определяет минимальные safety boundaries, которые действуют в проекте AOS с первого дня.

Minimal Safety Floor нужен для того, чтобы:

* агент не выдавал технический результат за решение человека;
* неизвестность не превращалась в положительный статус;
* scope задачи не расширялся неявно;
* protected и destructive actions не выполнялись без разрешения;
* разные Git actions не объединялись в одно разрешение;
* validation честно отражала выполненные и невыполненные проверки;
* временные материалы не становились Source of Truth;
* проект мог развиваться без немедленного создания полного Governance / Control Module.

Minimal Safety Floor действует:

* при работе с документацией;
* при изменении кода;
* при planning;
* при execution;
* при validation;
* при review;
* при использовании AI-агентов;
* при ручной работе человека;
* при будущей автоматизации.

Он не является отдельным поздним этапом.

Он действует до появления automation, validators и Runtime Enforcement.

⸻

Главная формула

Documentation определяет намерение и границы.
Implementation создаёт изменение внутри этих границ.
Validation проверяет результат.
Human принимает необходимые решения.
Minimal Safety Floor не позволяет смешивать эти действия.

⸻

Минимальный уровень, а не полный Governance

Minimal Safety Floor — это небольшой набор всегда действующих ограничений.

Он не должен автоматически включать:

* полный Governance lifecycle;
* сложную систему gates;
* universal Risk Matrix;
* task registry;
* approval database;
* cryptographic authorization;
* automatic policy engine;
* runtime state machine;
* merge authorization packages;
* release automation;
* persistent Control Plane.

Эти механизмы могут появиться позднее, если их необходимость доказана реальными workflows и failure modes.

Главная задача Minimal Safety Floor — предотвращать опасную или ложную интерпретацию результата без превращения обычной работы в тяжёлый control process.

⸻

Всегда действующие инварианты

Следующие утверждения являются обязательными:

PASS не означает approval.
Evidence не означает approval.
CI PASS не означает approval.
Metrics не означают approval.
UNKNOWN не означает OK.
NOT_RUN не означает PASS.
BLOCKED не означает PASS.
Skeleton не означает implementation.
Documentation не означает technical completion.
Plan не означает Task Brief.
Plan не означает execution authorization.
Routing decision не означает execution authorization.
Task completion не означает human acceptance.
Human approval нельзя симулировать.
Scope нельзя расширять без explicit human permission.

Git boundaries:

Edit не означает commit.
Commit не означает push.
Push не означает merge.
Merge не означает release.

Эти границы не могут быть отменены удобством, automation или уверенностью агента.

⸻

Human Authority

Человек сохраняет authority над решениями, которые изменяют:

* product scope;
* существенную architecture;
* Source of Truth;
* protected или canonical content;
* approval semantics;
* lifecycle;
* security boundaries;
* destructive behavior;
* commit policy;
* push policy;
* merge policy;
* release policy.

Агент может:

* анализировать;
* предлагать;
* формировать draft;
* выполнять разрешённое изменение;
* собирать Evidence;
* проводить validation;
* фиксировать findings.

Агент не может:

* approve;
* принять результат за человека;
* симулировать human checkpoint;
* назначить себе authority;
* выдать собственное предложение за принятое решение;
* считать отсутствие ответа согласием.

Если обязательное решение человека отсутствует, затронутое действие не выполняется.

⸻

Human approval нельзя симулировать

Недопустимы созданные агентом claims:

approved: true
human_accepted: true
authorized: true
merge_approved: true
release_approved: true

если соответствующее решение человека фактически не было предоставлено.

Недопустимо считать approval:

* сообщение агента;
* успешную validation;
* Evidence;
* CI PASS;
* commit;
* подпись автора commit;
* отсутствие возражений;
* истечение времени;
* автоматически установленный status;
* generated report.

Human approval должен быть явным, scoped и относящимся к конкретному решению.

⸻

Scope Boundary

Каждая write-задача должна иметь ограниченный scope.

Необходимо понимать:

* цель;
* target paths;
* allowed changes;
* forbidden changes;
* ожидаемый результат;
* validation;
* stop conditions.

Агент не должен самостоятельно добавлять:

* соседние исправления;
* дополнительные features;
* architecture refactoring;
* dependency changes;
* новую automation;
* изменение CI;
* изменение Governance;
* новый registry;
* cleanup вне задачи;
* изменение lifecycle.

Если для продолжения необходимо расширить scope, агент должен:

1. остановить execution;
2. объяснить причину;
3. предложить отдельное изменение scope;
4. дождаться решения человека.

⸻

Technical Result и Human Decision

Следующие состояния должны храниться отдельно:

работа выполнена
изменение существует
проверки выполнены
проверки прошли
Evidence собрано
review проведён
результат принят человеком

Они не являются синонимами.

Пример:

Implementation: COMPLETED
Validation: PASS
Human acceptance: NOT_PROVIDED

Это допустимое состояние.

Нельзя автоматически преобразовывать его в:

Task approved

⸻

Evidence Boundary

Evidence может включать:

* Git diff;
* список изменённых файлов;
* test output;
* validation output;
* command logs;
* screenshots;
* observed behavior;
* список NOT_RUN;
* unknowns;
* blockers;
* environment information.

Evidence подтверждает факты.

Evidence не принимает решения.

Evidence не должно содержать human approval claim, если соответствующее решение не было предоставлено отдельно.

Большое количество Evidence не компенсирует отсутствие обязательного approval.

⸻

Validation Boundary

Validation должна честно различать:

PASS
FAIL
UNKNOWN
NOT_RUN
BLOCKED

PASS

Проверка была выполнена, и проверяемое условие подтверждено.

FAIL

Проверка была выполнена, и проверяемое условие не подтверждено.

UNKNOWN

Данных недостаточно для вывода.

NOT_RUN

Проверка не выполнялась.

BLOCKED

Проверка не могла быть выполнена из-за конкретного blocker.

Нельзя:

* преобразовывать UNKNOWN в PASS;
* считать NOT_RUN несущественным без объяснения;
* скрывать failed checks внутри общего положительного статуса;
* использовать один успешный test как доказательство полной готовности;
* считать validation human review.

⸻

CI Boundary

CI выполняет технические проверки.

CI может:

* запускать tests;
* проверять formatting;
* проверять schemas;
* искать запрещённые claims;
* проверять repository consistency;
* собирать технический report.

CI не может:

* approve;
* назначать Risk Profile без принятого deterministic classifier;
* принимать architecture;
* разрешать merge самостоятельно без отдельной принятой политики;
* считать отсутствие test успешной проверкой;
* изменять human decision;
* скрывать unknowns.

Изменение required checks, branch protection, validator semantics или approval semantics является отдельным controlled change.

⸻

Unknown Handling

Существенная неизвестность должна оставаться явно неизвестной.

Агент не должен:

* угадывать current state;
* придумывать baseline;
* предполагать approval;
* считать dependency доступной без проверки;
* считать integration работающей без test;
* считать старую документацию актуальной автоматически;
* выдавать historical claim за repository fact.

Unknown должен блокировать только затронутый claim или action.

Примеры:

неизвестный baseline
→ блокирует write execution
неизвестный approval
→ блокирует действие, требующее approval
неизвестная production compatibility
→ блокирует claim о production compatibility
неизвестный будущий UI
→ не блокирует documentation работы над Project Identity

Unknown не должен автоматически превращаться в глобальную остановку всего проекта.

⸻

Fail-Closed Boundary

Fail-closed применяется там, где ошибочное продолжение может привести к:

* неразрешённому изменению;
* подмене human authority;
* destructive operation;
* protected или canonical mutation;
* неправильному commit, push, merge или release;
* ложному claim о готовности;
* раскрытию secret;
* внешнему необратимому действию.

Fail-closed означает:

1. явно сообщить о blocker;
2. не выполнять затронутое действие;
3. не придумывать отсутствующее разрешение;
4. не скрывать unknown;
5. указать одно необходимое действие;
6. остановиться.

Fail-closed не должен использоваться для блокировки безопасного read-only анализа, который не затрагивает соответствующую boundary.

⸻

Protected и canonical изменения

Protected или canonical content может определять:

* Project Identity;
* Product Vision;
* architecture;
* Source of Truth;
* Governance;
* approval model;
* lifecycle;
* safety semantics;
* release policy;
* destructive behavior.

Изменение таких материалов требует human checkpoint.

Агент может подготовить draft, но не может самостоятельно:

* объявить его принятым;
* заменить существующий canonical source;
* изменить precedence;
* удалить предыдущий source;
* применить новый contract к execution;
* начать migration.

Если protected или canonical status объекта неизвестен, safe state:

HUMAN_REVIEW_REQUIRED

⸻

Destructive Operations

Destructive operation — действие, способное удалить, перезаписать или необратимо изменить данные или состояние.

К destructive operations относятся:

* удаление содержательных файлов;
* массовый overwrite;
* git reset --hard;
* git clean;
* force push;
* удаление branch;
* history rewrite;
* удаление database;
* очистка unknown workspace;
* изменение production state;
* удаление external resources;
* перезапись чужих uncommitted changes;
* необратимый migration.

Destructive operations запрещены по умолчанию.

Для выполнения требуется explicit, scoped human authorization.

Разрешение должно указывать, какое именно действие допустимо.

Общая просьба «исправь проект» не является разрешением на destructive operation.

⸻

Git Action Boundaries

Каждое Git action требует собственного основания.

Edit

Изменяет working tree.

Stage

Изменяет Git index.

Commit

Создаёт новый объект истории.

Push

Публикует commits в remote.

Merge

Объединяет histories.

Release

Предоставляет версию пользователю или объявляет её устойчивой.

Authorization одного действия не распространяется автоматически на последующие.

Особенно запрещено без отдельного разрешения:

* auto-commit;
* auto-push;
* auto-merge;
* auto-release;
* force push;
* branch deletion;
* destructive history rewrite.

⸻

Risk Profile

Risk Profile назначается человеком.

Агент может:

* оценить возможный уровень риска;
* предложить Risk Profile;
* объяснить причины;
* перечислить необходимые safeguards.

Агент не может самостоятельно назначить себе низкий Risk Profile, чтобы упростить execution.

Если для задачи Risk Profile обязателен, но не назначен:

execution: BLOCKED

или:

HUMAN_REVIEW_REQUIRED

Unknown risk не может автоматически считаться low risk.

Полная Risk Matrix не входит в Minimal Safety Floor и должна появиться только при доказанной необходимости.

⸻

Planning Boundary

Planning:

* формирует draft;
* исследует варианты;
* предлагает scope;
* выявляет unknowns;
* предлагает Risk Profile;
* определяет validation;
* определяет stop conditions.

Planning не:

* разрешает execution;
* изменяет implementation;
* выполняет commit;
* принимает architecture;
* изменяет canonical state;
* начинает следующий этап автоматически.

Plan остаётся предложением, пока человек не принял необходимые решения и не сформирован достаточный executable Task Brief.

⸻

Execution Boundary

Execution выполняется только внутри разрешённого scope.

Execution не должен:

* расширять задачу;
* исправлять все найденные проблемы;
* начинать новый этап;
* изменять protected content без checkpoint;
* выполнять Git actions сверх authorization;
* скрывать отклонения от Task Brief.

После выполнения задачи или обнаружения blocking finding execution должен сформировать report и остановиться.

⸻

Validation Boundary

Validation является отдельным read-only этапом.

Validation:

* проверяет;
* фиксирует результаты;
* выявляет findings;
* сообщает unknowns.

Validation не:

* исправляет artifact;
* повторяет execution;
* запускает correction;
* принимает результат;
* начинает review автоматически;
* запускается повторно после failure без отдельного решения.

⸻

Review Boundary

Review является read-only оценкой результата.

Review может:

* выявлять противоречия;
* классифицировать findings;
* проверять consistency;
* рекомендовать correction.

Review не может:

* изменять проверяемый artifact;
* создавать approval от имени человека;
* автоматически начинать execution;
* расширять scope.

⸻

Один запуск — один этап

Один run выполняет один тип работы:

Planning
или
Execution
или
Validation
или
Review

Смешение этапов запрещено по умолчанию.

Недопустимый скрытый цикл:

выполнить
→ проверить
→ исправить
→ снова проверить
→ принять
→ начать следующую задачу

Разделение этапов обеспечивает traceability и независимую проверку результата.

⸻

Один writer

В одном workspace одновременно допускается один write-процесс.

Parallel write agents запрещены по умолчанию.

Это предотвращает:

* конфликты;
* потерю изменений;
* неясное авторство;
* смешение scopes;
* невозможность точно проверить diff.

Read-only agents могут работать параллельно, если они не изменяют files, index или Git state.

⸻

Secrets

Secrets запрещено помещать в repository.

К secrets относятся:

* API keys;
* access tokens;
* passwords;
* private certificates;
* authentication cookies;
* production credentials;
* private environment values.

Допустимо хранить:

* names переменных;
* .env.example;
* безопасные placeholders;
* инструкции настройки.

Если secret найден в repository, работа должна быть остановлена и случай должен рассматриваться как отдельный security finding.

⸻

Network Access

Network access по умолчанию выключен.

Он включается только если:

* задача действительно требует внешнего ресурса;
* локальных данных недостаточно;
* цель доступа понятна;
* разрешён соответствующий источник;
* отсутствует более безопасная локальная альтернатива.

Network access не должен автоматически включаться для:

* локального documentation editing;
* Git diff review;
* local tests;
* repository inspection;
* работы с уже предоставленными sources.

⸻

Temporary Workspace

Временные outputs хранятся только в:

/.aos-tmp/

Temporary workspace:

* local-only;
* disposable;
* исключён из Git;
* не является Source of Truth;
* не является Evidence storage;
* не является approval storage;
* не является checkpoint storage;
* не является canonical documentation storage.

В /.aos-tmp/ нельзя хранить единственную копию:

* принятого решения;
* Evidence;
* final report;
* Task Brief;
* checkpoint;
* protected или canonical artifact;
* lifecycle decision;
* Risk Profile assignment.

Если важный artifact создан временно, он переносится в durable path отдельным контролируемым действием.

⸻

Source of Truth Boundary

Не каждый полезный artifact является Source of Truth.

Следует различать:

* canonical content;
* factual repository state;
* Evidence;
* generated index;
* cache;
* temporary output;
* reference material;
* human decision.

Generated, cached и navigational artifacts не должны незаметно становиться authority.

Если derived artifact конфликтует с canonical source, он должен быть пересоздан или признан устаревшим.

Если Source of Truth неизвестен для решения, которое зависит от него, действие блокируется до clarification.

⸻

Legacy Boundary

AOS-FARM и AgentOS/AOS-1 используются только как historical и read-only reference.

Legacy materials не дают новому AOS:

* active roadmap;
* active architecture;
* Source of Truth;
* approval;
* execution authorization;
* lifecycle state;
* permission на protected change;
* merge или release authority.

Старый component не импортируется автоматически.

Default подход:

понять contract
→ извлечь observable behavior
→ изучить lessons
→ reimplement from contract

⸻

Кратчайший безопасный путь

AOS использует кратчайший безопасный путь по умолчанию.

Он означает:

* минимальный достаточный scope;
* минимальное количество этапов;
* минимальные permissions;
* минимальное количество изменяемых файлов;
* обязательную validation;
* явную human boundary;
* отсутствие необязательной automation.

Кратчайший безопасный путь не даёт:

* approval;
* execution authorization;
* Risk Profile assignment;
* permission на protected change;
* permission на destructive operation;
* commit authorization;
* push authorization;
* merge authorization;
* release authorization;
* permission на scope expansion.

Упрощать можно процесс, но не authority boundary.

⸻

Когда короткий путь допустим

Сжатый workflow допустим, если:

* задача узкая;
* ownership понятен;
* target files известны;
* forbidden scope известен;
* baseline понятен;
* protected content не затрагивается;
* destructive operation не требуется;
* approval semantics не меняются;
* validation способна доказать результат;
* unknowns не скрываются;
* следующие Git actions выполняются отдельно.

⸻

Когда короткий путь запрещён

Нельзя сжимать workflow, если:

* ownership неясен;
* Source of Truth неоднозначен;
* меняется architecture;
* меняется approval или lifecycle;
* затрагивается protected или canonical content;
* требуется destructive action;
* Risk Profile обязателен, но не назначен;
* UNKNOWN может быть ошибочно принят за OK;
* NOT_RUN может быть ошибочно принят за PASS;
* Evidence может быть ошибочно принято за approval;
* scope расширяется;
* вовлечены merge или release authority.

В этих случаях требуется human review или отдельный control path.

⸻

Что запрещено с первого дня

Запрещены:

* fake human approval;
* agent auto-approval;
* auto-completion;
* auto-commit;
* auto-push;
* auto-merge;
* auto-release;
* hidden execution;
* hidden lifecycle mutation;
* hidden scope expansion;
* protected change без checkpoint;
* destructive operation по умолчанию;
* secret в repository;
* parallel write agents;
* validation, которая скрыто исправляет результат;
* review, которое изменяет проверяемый artifact;
* трактовка UNKNOWN как OK;
* трактовка NOT_RUN как PASS;
* трактовка Evidence или CI PASS как approval;
* agent self-assignment низкого Risk Profile;
* автоматическое начало следующего этапа.

⸻

Минимальный safety preflight

Перед write execution необходимо подтвердить:

repository известен;
project root известен;
branch известна;
baseline известен;
scope ограничен;
allowed paths известны;
forbidden paths известны;
expected result проверяем;
validation определена;
stop conditions определены;
permissions достаточны и не избыточны;
protected boundary не пересекается без checkpoint;
destructive action не требуется без authorization;

Для routine low-risk задачи preflight должен оставаться коротким.

⸻

Минимальный safety report

После этапа необходимо сообщить:

что было поручено;
что сделано;
какие files изменены;
что проверено;
что не проверено;
какие findings обнаружены;
какие unknowns остались;
какие Git actions выполнены;
какое одно действие требуется дальше.

Report не должен объявлять human acceptance.

⸻

Minimal Safety Floor для документации

При работе с документацией агент должен:

* сохранять смысл и Markdown;
* не добавлять approval claims;
* не менять соседние документы без scope;
* не объявлять draft canonical;
* не выдавать документ за implementation;
* не удалять historical content без разрешения;
* не создавать metadata и lifecycle, если они не требуются;
* явно отделять active knowledge от reference material.

⸻

Minimal Safety Floor для кода

При работе с кодом агент должен:

* выполнять bounded task;
* не менять public behavior без требования;
* не добавлять dependency без необходимости;
* не ослаблять tests ради PASS;
* не скрывать failing checks;
* не выполнять unrelated refactoring;
* раскрывать непроверенные paths;
* не выполнять deployment или production mutation без отдельного разрешения.

⸻

Minimal Safety Floor для manual workflow

Manual workflow должен сохранять те же границы, что и будущая automation:

bounded task
→ controlled change
→ validation
→ report
→ human decision

Отсутствие автоматического enforcement не отменяет safety rules.

На раннем этапе соблюдение обеспечивается:

* ясным Task Brief;
* ограниченным scope;
* Git diff;
* отдельной validation;
* human review;
* явными Git boundaries.

⸻

Переход к полному Governance

Полный Governance / Control Module оправдан, если реальные manual workflows показывают повторяющуюся необходимость:

* классифицировать разные типы риска;
* защищать несколько classes canonical content;
* управлять командными approvals;
* проверять многочисленные lifecycle transitions;
* контролировать внешние необратимые actions;
* поддерживать сложный multi-project workflow;
* формально проверять regulated requirements.

До этого момента Minimal Safety Floor должен оставаться небольшим.

Нельзя строить полный Governance только потому, что он может понадобиться в будущем.

⸻

Переход к Runtime Enforcement

Safety rule может быть перенесено в Runtime Enforcement, если оно:

* стабильно;
* однозначно;
* многократно применялось вручную;
* имеет высокую цену нарушения;
* может быть проверено детерминированно;
* не требует симуляции human judgment.

Runtime Enforcement не должен создаваться для ещё неустойчивых или неоднозначных правил.

⸻

Ошибки, которых необходимо избежать

Full Governance в bootstrap

Создание сложного Control Plane до работающего продукта повторит основную ошибку AOS-FARM.

Формальная безопасность без product value

Количество gates не является показателем полезности продукта.

Global blocking из-за локального unknown

Unknown должен блокировать затронутое действие, а не автоматически весь проект.

Agent-defined authority

Агент не может назначать себе Risk Profile, approval или право на следующий этап.

Validation как correction loop

Validation должна остановиться после finding.

Safety как бюрократия

Routine задача не должна требовать enterprise-sized package.

Temporary artifact как authority

Файл в /.aos-tmp/ не становится canonical из-за того, что он содержит полезный результат.

CI как reviewer

CI проверяет технические условия, но не принимает человеческие решения.

⸻

Критерий готовности

Minimal Safety Floor считается достаточно определённым, если любой человек или агент понимает:

1. что PASS не означает approval;
2. что неизвестность должна быть раскрыта;
3. что scope нельзя расширять без разрешения;
4. что human authority нельзя симулировать;
5. что protected changes требуют checkpoint;
6. что destructive operations запрещены по умолчанию;
7. что Risk Profile назначает человек, когда он требуется;
8. что planning, execution, validation и review разделены;
9. что Git actions имеют отдельные boundaries;
10. что secrets не попадают в repository;
11. что network и permissions минимальны;
12. что temporary workspace не является Source of Truth;
13. что после finding или завершения агент формирует report и останавливается;
14. что полный Governance откладывается до подтверждённой необходимости.

⸻

Что не входит в Minimal Safety Floor

Этот документ не определяет:

* полную Risk Matrix;
* полный Governance lifecycle;
* все категории protected paths;
* автоматическую task state machine;
* deterministic risk classifier;
* Evidence schema;
* approval database;
* merge authorization package;
* release policy;
* organization compliance;
* Runtime Enforcement implementation;
* полный набор validators.

Эти элементы должны проектироваться отдельно и только после появления подтверждённой необходимости.
