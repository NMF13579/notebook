02.09 — First Manual Workflow

Назначение

Этот документ определяет первый полный ручной workflow разработки проекта AOS.

Он объединяет ранее определённые элементы Scaffolding:

* Project Skeleton;
* Workspace Foundation;
* Agent Contract;
* Git Foundation;
* Task and Report Templates;
* Minimal Safety Floor;
* Local Development Environment;
* Minimal Checks and CI.

Цель workflow — доказать, что ограниченная задача может быть безопасно и понятно выполнена без:

* полного Development Factory;
* task registry;
* Control Plane;
* automatic routing;
* automatic correction;
* persistent workflow database;
* autonomous agent loop;
* Runtime Enforcement;
* автоматического commit, push, merge или release.

Первый manual workflow должен стать рабочей основой, из которой позднее можно извлекать требования к automation.

⸻

Главная цель

Manual workflow должен позволить провести одну реальную задачу через полный bounded cycle:

намерение человека
→ ограниченная задача
→ подтверждённый scope
→ контролируемое изменение
→ техническая проверка
→ короткий отчёт
→ human review
→ одно следующее действие
→ stop

Workflow считается полезным только тогда, когда его можно применить к реальной задаче и получить проверяемый результат.

Наличие документа с описанием workflow не означает, что workflow уже проверен на практике.

⸻

Основная формула

Понять задачу.
Ограничить scope.
Зафиксировать baseline.
Разрешить один этап.
Выполнить только разрешённое.
Проверить отдельно.
Показать факты.
Получить решение человека.
Остановиться.

⸻

Что доказывает первый manual workflow

Успешный manual cycle должен подтвердить, что проект уже способен:

* сформировать bounded Task Brief;
* связать работу с repository, branch и baseline;
* отделить allowed scope от forbidden scope;
* дать агенту понятную инструкцию;
* выполнить ограниченное изменение;
* не затронуть unrelated files;
* провести заявленные checks;
* честно показать PASS, FAIL, UNKNOWN, NOT_RUN и BLOCKED;
* отделить technical result от human decision;
* передать состояние следующей session;
* показать одно следующее действие;
* завершиться без recovery loop.

⸻

Что manual workflow не доказывает

Один успешный manual cycle не доказывает:

* готовность Product Runtime;
* готовность первого product vertical slice;
* готовность Development Factory;
* необходимость registry;
* необходимость автоматизации;
* готовность Governance;
* готовность Runtime Enforcement;
* готовность CI;
* готовность к merge;
* готовность к release;
* масштабируемость процесса;
* production readiness.

Manual workflow проверяет только возможность безопасно провести ограниченную development task через понятную последовательность.

⸻

Manual workflow и product value

Development workflow не является заменой продукта.

Первый manual workflow относится к Scaffolding и отвечает на вопрос:

Можем ли мы безопасно и воспроизводимо выполнить одну задачу?

Первый product vertical slice должен отвечать на другой вопрос:

Получает ли пользователь AOS наблюдаемую продуктовую ценность?

Нельзя объявлять product proof только потому, что Task Brief, report и review успешно прошли внутренний development cycle.

⸻

Границы первого workflow

Первый workflow должен быть намеренно простым.

Он не должен включать:

* несколько параллельных задач;
* несколько write agents;
* multi-repository coordination;
* production deployment;
* внешний destructive action;
* migration;
* full architecture change;
* изменение approval semantics;
* automatic retry;
* automatic correction;
* automatic handoff;
* task state machine;
* сложный Risk Profile workflow;
* merge или release.

Для первого цикла следует выбрать low-complexity, reversible и легко проверяемую задачу.

⸻

Предпочтительный тип первой задачи

Хорошая первая задача:

* затрагивает один или несколько тесно связанных файлов;
* имеет ясный expected result;
* легко проверяется;
* не требует network;
* не требует новых dependencies;
* не затрагивает production;
* не меняет architecture;
* не затрагивает protected или canonical rules;
* может быть отменена обычным Git diff или revert;
* завершается за один execution stage.

Подходящие примеры:

* заполнение одного нового Markdown-документа;
* исправление одной документированной команды;
* добавление малого deterministic test;
* локальное исправление одного validation behavior;
* устранение одного точно воспроизводимого defect.

⸻

Неподходящая первая задача

Не следует начинать manual workflow с задач:

перестроить архитектуру;
создать полный Control Plane;
автоматизировать весь development process;
импортировать AOS-FARM;
добавить database;
создать agent orchestrator;
исправить всё, что найдётся;
подготовить production release;
мигрировать несколько repositories;

Такие задачи слишком широки и не позволяют проверить сам workflow отдельно от сложности предметной работы.

⸻

Участники

В минимальном manual workflow участвуют следующие роли.

Human

Человек:

* определяет намерение;
* принимает или корректирует scope;
* назначает Risk Profile, если он требуется;
* разрешает write execution;
* рассматривает результат;
* принимает, отклоняет или отправляет его на revision;
* отдельно разрешает commit, push, merge или release.

Planning agent

Planning agent:

* анализирует задачу;
* выявляет unknowns;
* предлагает bounded scope;
* формирует draft Task Brief;
* определяет validation;
* определяет stop conditions.

Planning agent не изменяет implementation.

Execution agent

Execution agent:

* выполняет только разрешённое изменение;
* соблюдает allowed и forbidden scope;
* запускает declared execution checks;
* формирует короткий Execution Report;
* останавливается.

Validation agent

Validation agent:

* проверяет результат;
* сравнивает его с Task Brief;
* запускает validation commands;
* фиксирует findings;
* не исправляет artifact;
* не начинает следующий этап.

Для малой reversible задачи human может выполнить validation вручную, но граница между execution и validation всё равно должна сохраняться смыслово.

⸻

Один запуск — один этап

Первый manual workflow должен сохранять правило:

один run
=
один stage

Допустимые stages:

Planning
Execution
Validation
Review

Недопустимый единый run:

agent сформировал план
→ сам разрешил execution
→ изменил файлы
→ сам исправил найденные ошибки
→ объявил validation PASS
→ создал commit
→ начал следующую задачу

Разделение stages необходимо даже при использовании одной и той же модели в разных sessions.

⸻

Полный manual cycle

Stage 0 — Выбор задачи

Человек выбирает одну bounded задачу.

На этом шаге должно быть понятно:

* какую проблему нужно решить;
* почему задача нужна сейчас;
* что будет наблюдаемым результатом;
* почему задача достаточно мала для одного цикла;
* не является ли она частью другой более крупной задачи.

Результат Stage 0:

одна задача;
один ожидаемый результат;
одна граница завершения.

Если задача содержит несколько независимых результатов, её следует разделить.

⸻

Stage 1 — Preflight

До подготовки executable Task Brief необходимо подтвердить рабочее состояние.

Минимальный preflight:

pwd
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short

Для AOS subtree дополнительно:

git status --short -- AOS

Preflight должен установить:

* правильный repository;
* правильный project root;
* active branch;
* baseline commit;
* наличие uncommitted changes;
* отсутствие незавершённого merge, rebase или другой конфликтной Git operation;
* возможность изолировать target paths.

Preflight не должен превращаться в полный repository audit.

⸻

Preflight result

Preflight должен завершиться одним из состояний:

READY

Baseline и scope можно определить.

BLOCKED

Существует конкретный blocker, который не позволяет безопасно начать write task.

HUMAN_REVIEW_REQUIRED

Обнаружено состояние, требующее решения человека, например:

* неизвестные изменения target file;
* protected scope;
* потенциальная destructive operation;
* неизвестный Source of Truth;
* architecture conflict.

При BLOCKED или HUMAN_REVIEW_REQUIRED execution не начинается.

⸻

Stage 2 — Task Brief

Для задачи формируется Task Brief.

Он должен включать:

* цель;
* expected result;
* context;
* repository;
* branch;
* baseline;
* allowed paths;
* forbidden paths;
* requirements;
* validation;
* stop conditions;
* разрешённые permissions;
* запрещённые Git actions.

Task Brief должен описывать одну executable unit.

⸻

Минимальный Task Brief для manual cycle

# Task Brief — <название>
## Цель
<Один конкретный результат.>
## Baseline
- Repository: `<repository>`
- Branch: `<branch>`
- Commit: `<commit>`
## Allowed scope
- `<path>`
## Forbidden scope
- все остальные files;
- dependencies;
- CI;
- architecture;
- protected и canonical rules.
## Expected result
<Наблюдаемый итог.>
## Validation
- `<check>`
- `<check>`
## Stop conditions
- задача выполнена;
- требуется расширение scope;
- baseline изменился;
- найден blocking finding;
- требуется human decision.
## Permissions
- Workspace write: разрешён только в allowed scope.
- Network: запрещён.
- Commit: запрещён.
- Push: запрещён.
- Merge: запрещён.
- Release: запрещён.

⸻

Полнота Task Brief

Task Brief достаточно полный, если execution agent не должен самостоятельно определять:

* product goal;
* architecture;
* разрешённые paths;
* критерий завершения;
* обязательные проверки;
* authority;
* следующий этап.

Если агенту приходится принимать такие решения, Task Brief возвращается на revision.

⸻

Stage 3 — Human execution decision

Write execution начинается только после явного решения человека.

Разрешение должно относиться к:

* конкретной задаче;
* конкретному Task Brief;
* конкретному scope;
* текущему baseline;
* конкретному типу действия.

Execution authorization не означает:

* commit authorization;
* push authorization;
* merge authorization;
* release authorization;
* разрешение расширить scope;
* разрешение изменить protected или canonical content за пределами Task Brief.

Если baseline materially изменился после authorization, разрешение должно быть пересмотрено.

⸻

Routine documentation workflow

Для текущего процесса заполнения документов допускается сокращённая human boundary:

человек просит создать конкретный документ
→ target path и ограничения уже понятны
→ assistant формирует готовый Markdown
→ человек вручную вставляет текст

Это допустимо, потому что:

* фактическую запись в repository выполняет человек;
* assistant не получает write access;
* commit не выполняется;
* scope ограничен одним документом.

После вставки всё равно требуется проверить diff.

⸻

Stage 4 — Execution

Execution agent получает:

* Task Brief;
* точный baseline;
* allowed paths;
* forbidden paths;
* validation commands;
* stop conditions;
* permissions.

Execution agent должен:

1. подтвердить target;
2. изменить только необходимое;
3. не трогать unrelated files;
4. не расширять scope;
5. не добавлять незаявленные dependencies;
6. выполнить только разрешённые commands;
7. остановиться после expected result или blocking finding.

⸻

Поведение execution agent

Execution agent может принимать локальные implementation decisions, если они:

* находятся внутри Task Brief;
* не меняют observable contract;
* не расширяют paths;
* не создают новую architecture;
* не требуют дополнительных permissions;
* не затрагивают human authority.

Если возникает новая самостоятельная проблема, агент фиксирует её как finding.

Он не исправляет её автоматически.

⸻

Execution stop conditions

Execution немедленно останавливается, если:

* baseline не совпадает;
* target path изменён неизвестным участником;
* требуется forbidden path;
* требуется новая dependency;
* требуется network;
* требуется protected change;
* требуется destructive action;
* обнаружена architecture ambiguity;
* expected result достигнут;
* произошёл failure;
* найден blocking finding.

После остановки агент формирует report.

⸻

Stage 5 — Execution Report

Execution Report должен быть коротким и фактическим.

Минимальное содержание:

# Execution Report — <название>
## Результат
<Что фактически сделано.>
## Изменённые файлы
- `<path>`
## Выполненные проверки
- `<check>` — `<result>`
## Findings
- <finding или отсутствие blocking findings>
## Unknowns
- <unknown или отсутствие существенных unknowns>
## Scope
- Forbidden paths изменены: нет.
## Git actions
- Commit: NOT_RUN
- Push: NOT_RUN
- Merge: NOT_RUN
- Release: NOT_RUN
## Следующее действие
Провести independent validation.

Report не должен утверждать human acceptance.

⸻

Stage 6 — Independent Validation

Validation выполняется после execution как отдельный этап.

Validator должен получить:

* Task Brief;
* baseline;
* execution result;
* diff;
* declared checks.

Validator проверяет:

1. baseline binding;
2. allowed scope;
3. forbidden scope;
4. expected result;
5. заявленные requirements;
6. tests или другие checks;
7. unknowns и NOT_RUN;
8. отсутствие скрытых Git actions.

⸻

Validation является read-only

Validator не должен:

* исправлять artifact;
* менять tests;
* форматировать files;
* обновлять dependency;
* создавать commit;
* повторно запускать execution;
* начинать review;
* принимать результат за человека.

Если найден finding:

finding
→ validation report
→ одно следующее действие
→ stop

⸻

Минимальный Validation Report

# Validation Report — <название>
## Проверяемый объект
- Task Brief: `<идентификатор>`
- Baseline: `<commit>`
- Changed paths: `<paths>`
## Scope validation
- Allowed scope: PASS
- Forbidden paths unchanged: PASS
## Checks
- `<check>` — PASS
- `<check>` — NOT_RUN
## Findings
- <finding или отсутствие blocking findings>
## Unknowns
- <unknown>
## Result
PASS | FAIL | BLOCKED
## Implementation modified by validator
Нет.
## Следующее действие
<Ровно одно действие.>

⸻

Значение Validation PASS

Validation PASS означает только:

* выполненные проверки подтвердили заявленные условия;
* существенные blocking findings в проверенном scope не обнаружены.

Validation PASS не означает:

* human acceptance;
* commit authorization;
* push authorization;
* merge authorization;
* release authorization;
* product readiness;
* отсутствие дефектов вне проверенного scope.

⸻

Stage 7 — Human Review

Человек рассматривает:

* Task Brief;
* изменённые files;
* diff;
* Execution Report;
* Validation Report;
* findings;
* unknowns;
* NOT_RUN checks.

Human Review должен завершиться одним ограниченным решением:

ACCEPT
REJECT
NEEDS_REVISION

ACCEPT

Результат соответствует задаче.

Это решение не даёт автоматически разрешение на commit, push, merge или release.

REJECT

Результат не принимается.

Следующее действие должно быть конкретным: отменить изменение, закрыть направление или подготовить новую задачу.

NEEDS_REVISION

Требуется отдельная bounded correction task.

Старый Task Brief не должен автоматически расширяться.

⸻

Human Review не должен быть формальностью

Человек должен иметь возможность понять:

* что было изменено;
* соответствует ли это его намерению;
* были ли затронуты неожиданные files;
* какие проверки реально выполнялись;
* что осталось неизвестным;
* требуется ли correction;
* можно ли переходить к следующему Git action.

Review package должен быть достаточно коротким для реального чтения.

⸻

Stage 8 — Git decision

После human acceptance отдельно решается вопрос о commit.

Возможные действия:

не создавать commit;
создать commit;
вернуть на revision;
отменить изменение.

Commit authorization должен относиться к проверенному diff.

После commit отдельно решается push.

После push отдельно решается merge.

После merge отдельно решается release.

Эти действия не входят автоматически в первый manual cycle.

⸻

Stage 9 — Handoff и stop

После завершения цикла необходимо оставить понятное состояние.

Минимальный handoff:

Task:
Stage completed:
Repository:
Branch:
Baseline:
Result:
Changed paths:
Validation:
Findings:
Unknowns:
Git state:
Human decision:
Next action:

После handoff workflow останавливается.

Следующий этап или задача не запускается автоматически.

⸻

Сокращённый routine path

Для малой reversible задачи при полном Task Brief может использоваться сокращённый путь:

bounded Task Brief
→ human execution authorization
→ execution
→ declared local checks
→ short report
→ human review
→ stop

Отдельная independent validation может не требоваться, если:

* задача routine и reversible;
* protected content не затрагивается;
* architecture не меняется;
* change легко проверить по diff;
* Task Brief явно допускает combined local checks;
* человек способен проверить результат напрямую.

Но execution agent не должен самостоятельно объявлять, что independent validation не нужна.

Это определяется Task Brief или человеком.

⸻

Полный validation path

Independent validation обязательна, если задача:

* является первым Product Runtime vertical slice;
* затрагивает protected или canonical content;
* изменяет architecture;
* изменяет safety или approval semantics;
* имеет высокий риск;
* затрагивает external state;
* связана с release;
* создаёт существенную dependency;
* содержит сложную migration;
* имеет высокую цену скрытого defect.

⸻

Correction workflow

Если review или validation обнаружили проблему, correction оформляется как новая bounded task.

Неправильный путь:

validation нашла ошибку
→ validator исправил
→ validator повторил проверку
→ объявил PASS

Правильный путь:

validation нашла ошибку
→ report
→ stop
→ новый correction Task Brief
→ отдельное execution
→ отдельная validation

Для малой routine correction новый Task Brief может быть очень коротким, но scope всё равно должен быть явным.

⸻

Failure workflow

Если execution завершилась failure:

1. не скрывать partial changes;
2. не запускать автоматический retry;
3. зафиксировать executed commands;
4. указать modified paths;
5. сообщить, безопасно ли оставить working tree;
6. указать blocking cause;
7. обозначить unknowns;
8. дать одно следующее действие;
9. остановиться.

Failure не означает необходимость создавать recovery program.

Сначала следует устранить конкретную причину кратчайшим безопасным путём.

⸻

Blocking finding workflow

При первом material blocking finding:

зафиксировать finding
→ определить его влияние
→ прекратить текущий stage
→ сформировать report
→ указать одно следующее действие
→ stop

Не следует продолжать искать дополнительные unrelated findings, если текущая задача уже заблокирована и дальнейший анализ не нужен для понимания причины.

⸻

Scope expansion workflow

Если во время execution обнаружено, что expected result требует большего scope:

1. не менять дополнительные paths;
2. зафиксировать необходимое расширение;
3. объяснить, почему текущего scope недостаточно;
4. предложить revised scope;
5. остановиться;
6. дождаться human decision.

Scope expansion не является обычным implementation detail.

⸻

Baseline change workflow

Если baseline изменился после подготовки Task Brief:

Non-material change

Если изменение не затрагивает target, requirements или assumptions, baseline можно обновить после явной проверки.

Material change

Если изменение затрагивает:

* target paths;
* interfaces;
* dependencies;
* architecture;
* tests;
* expected behavior;

Task Brief должен вернуться на review.

Execution по старому baseline не продолжается.

⸻

Задача

Заполнить один новый README.

Workflow

выбран target file
→ подготовлен готовый Markdown
→ человек вставил текст
→ выполнен target-only diff
→ выполнен git diff --check
→ проведён content review
→ принято или отправлено на revision
→ stop

Минимальные проверки

git status --short
git diff --check
git diff -- <target-file>

Что не выполняется автоматически

commit
push
merge
renumbering соседних objects
обновление generated index
изменение metadata

Пример первого code cycle

Задача

Исправить один deterministic behavior и добавить regression test.

Workflow

зафиксировать defect
→ определить expected behavior
→ ограничить source и test paths
→ human execution decision
→ изменить implementation
→ добавить regression test
→ запустить targeted tests
→ сформировать Execution Report
→ независимая validation
→ human review
→ stop

Запрещённое расширение

Не добавлять в ту же задачу:

* unrelated refactoring;
* dependency update;
* CI change;
* public API redesign;
* architecture migration.

⸻

Наблюдение за manual cycles

Во время первых manual cycles следует фиксировать только реально наблюдаемые проблемы.

Полезно записывать:

* какие данные постоянно приходится искать;
* какие поля Task Brief повторяются;
* где чаще всего теряется context;
* какие checks выполняются каждый раз;
* какие действия являются механическими;
* какие human decisions действительно необходимы;
* где возникают false positives;
* какие этапы не создают ценности;
* сколько времени занимает handoff;
* где появляется риск scope expansion.

Эти наблюдения станут input для будущей Development Factory.

⸻

Сколько manual cycles нужно

До проектирования automation следует выполнить минимум два, предпочтительно три реальных цикла.

Желательно, чтобы они включали разные, но небольшие задачи:

1. documentation task;
2. routine code task;
3. небольшая task с independent validation.

Automation не следует проектировать после одного идеального демонстрационного примера.

⸻

Что считать повторяющейся операцией

Операция является кандидатом на automation, если:

* она повторилась в нескольких реальных cycles;
* её inputs и outputs стабильны;
* решение не требует скрытого human judgment;
* manual version понятна;
* типовые failures известны;
* automation даёт измеримую экономию;
* существует безопасный manual fallback.

Примеры возможных будущих кандидатов:

* preflight collection;
* Task Brief skeleton generation;
* запуск известного набора checks;
* Stage Report assembly;
* changed-path collection;
* session handoff summary.

⸻

Что нельзя автоматизировать по результатам первых cycles

Первые manual cycles не дают автоматического основания для:

* human approval;
* Risk Profile assignment;
* architecture decisions;
* scope expansion;
* protected changes;
* destructive operations;
* commit;
* push;
* merge;
* release;
* автоматического исправления findings.

Эти boundaries требуют отдельного решения даже после появления Development Factory.

⸻

Metrics manual workflow

Для оценки первых cycles можно наблюдать:

* время подготовки Task Brief;
* время execution;
* время validation;
* время human review;
* количество scope deviations;
* количество unrelated changes;
* количество UNKNOWN;
* количество NOT_RUN;
* количество correction cycles;
* время восстановления context;
* количество случаев, когда следующее действие было неясным.

Metrics используются для улучшения workflow.

Они не являются approval.

⸻

Признаки слишком тяжёлого workflow

Workflow нуждается в упрощении, если:

* Task Brief больше самой задачи;
* preflight занимает больше времени, чем execution;
* требуется несколько human reauthorizations без изменения scope;
* создаётся много reports без нового знания;
* routine task проходит через architecture review;
* один unknown блокирует весь проект;
* review невозможно реально прочитать;
* каждый finding создаёт новый lifecycle;
* следующий шаг остаётся неясным;
* formal readiness заменяет реальный результат.

⸻

Признаки слишком слабого workflow

Workflow недостаточен, если:

* scope не зафиксирован;
* baseline неизвестен;
* agent меняет unrelated paths;
* checks определяются после implementation;
* validation исправляет результат;
* NOT_RUN скрывается;
* технический PASS выдаётся за acceptance;
* commit или push выполняются автоматически;
* после session невозможно понять состояние;
* новые задачи возникают внутри execution без отдельного решения.

⸻

Minimal Safety Floor внутри manual workflow

Всегда сохраняются правила:

PASS ≠ approval.
Evidence ≠ approval.
CI PASS ≠ approval.
UNKNOWN ≠ OK.
NOT_RUN ≠ PASS.
Human approval cannot be simulated.
Scope expansion requires explicit human permission.
Protected changes require human checkpoint.
Destructive operations require explicit authorization.
Commit ≠ push ≠ merge ≠ release.

Manual nature процесса не отменяет эти boundaries.

⸻

Критерии успешного manual cycle

Один цикл считается технически успешно завершённым, если:

1. задача была ограничена;
2. baseline был известен;
3. Task Brief был достаточным;
4. write execution было разрешено;
5. изменены только allowed paths;
6. forbidden paths не затронуты;
7. stop conditions соблюдены;
8. declared checks выполнены или честно отмечены как NOT_RUN;
9. blocking findings раскрыты;
10. validation не исправляла artifact;
11. technical result отделён от human decision;
12. Git actions не превысили authorization;
13. оставлен понятный handoff;
14. указано одно следующее действие;
15. workflow остановился.

⸻

Критерии готовности Scaffolding

Раздел 02_Scaffolding можно считать практически проверенным только после того, как manual workflow:

* применён к реальной bounded task;
* завершён без скрытого scope expansion;
* оставил проверяемый diff;
* прошёл заявленные checks;
* был понятен человеку;
* не потребовал полного Control Plane;
* не потребовал recovery loop;
* позволил продолжить работу из handoff.

Документированная структура без практического цикла остаётся только skeleton.

⸻

Что не входит в First Manual Workflow

Этот документ не определяет:

* Product Contract;
* первый product vertical slice;
* автоматический routing;
* task registry;
* automatic prompt generation;
* project database;
* agent orchestration;
* bounded correction engine;
* Runtime Enforcement;
* merge automation;
* release workflow;
* production deployment;
* multi-project operation.

Эти возможности рассматриваются позднее.
