02.02 — Workspace Foundation

Назначение

Этот документ определяет минимальную рабочую среду проекта AOS.

Workspace Foundation нужен для того, чтобы:

* человек и агент одинаково понимали границы рабочей области;
* временные материалы не смешивались с durable artifacts;
* работа выполнялась в правильном repository, branch и directory;
* разные типы задач не конфликтовали между собой;
* состояние проекта можно было восстановить после остановки;
* случайные локальные файлы не становились частью проекта;
* implementation, validation и review выполнялись предсказуемо;
* будущая автоматизация могла опираться на уже понятный ручной процесс.

Workspace Foundation не является Development Factory или Control Plane.

Это минимальная организация рабочей среды, достаточная для последовательной разработки.

⸻

Основная цель workspace

Workspace должен позволять выполнить простой и контролируемый цикл:

открыть правильный repository
→ определить branch и baseline
→ выбрать ограниченную задачу
→ изменить только разрешённые файлы
→ сохранить временные outputs отдельно
→ проверить результат
→ показать diff
→ остановиться

Для этого не требуется:

* registry;
* task database;
* orchestration framework;
* persistent agent runtime;
* автоматический recovery;
* сложная state machine.

⸻

Рабочая область проекта

Активная рабочая область AOS находится внутри Git repository.

В текущей конфигурации документационный проект расположен в subtree:

AOS/

В будущем Product Runtime и implementation могут находиться:

* в том же repository;
* в отдельном repository;
* в нескольких связанных repositories.

Это решение пока не фиксируется окончательно.

Для любой задачи должно быть ясно:

* какой repository используется;
* какая directory является project root;
* какая branch активна;
* какой baseline считается исходным;
* какие paths разрешено изменять.

⸻

Repository root и project root

Необходимо различать:

Git repository root

и

AOS project root

Project root может быть вложенной папкой внутри более крупного repository.

Пример:

Git repository root:
notebook/
AOS project root:
notebook/AOS/

Это допустимая модель, если она выбрана явно.

Агент не должен предполагать, что текущая директория автоматически является project root.

Перед изменениями необходимо определить обе границы.

⸻

Branch model

Для активной сборки документации используется branch:

dev

Предполагаемая модель:

main
→ принятый baseline
dev
→ активная сборка и переработка документации

Работа в dev допускает:

* заполнение новых документов;
* исправление текста;
* restructuring в пределах разрешённого scope;
* добавление sources;
* устранение противоречий;
* подготовку review.

main должен оставаться более устойчивым состоянием.

Переход из dev в main не выполняется автоматически.

⸻

Baseline

Перед изменением существенного artifact необходимо знать исходное состояние.

Минимальный baseline:

repository
branch
commit
target path

Baseline нужен для того, чтобы:

* понимать, от чего рассчитывается diff;
* не смешивать изменения разных задач;
* проверять, что работа выполнялась в ожидаемой branch;
* восстанавливать состояние после ошибки;
* отличать новое изменение от уже существовавшего.

Для простых Markdown-изменений достаточно Git commit и branch.

Для будущих implementation tasks могут потребоваться дополнительные bindings.

⸻

Чистота рабочей области

Workspace не обязан быть полностью clean перед каждой задачей.

Но unrelated changes должны быть:

* видимыми;
* не затронутыми;
* не включёнными в scope;
* не изменёнными форматтерами или agent tools;
* не добавленными случайно в commit.

Если unrelated changes мешают точно проверить результат, работа должна быть остановлена или перенесена в изолированную рабочую область.

⸻

Изоляция задач

Одна задача должна иметь собственный ограниченный scope.

Минимально нужно определить:

target files
allowed supporting files
forbidden paths
expected result
validation command
stop conditions

Агент не должен:

* редактировать соседние документы для согласованности без разрешения;
* исправлять unrelated formatting;
* обновлять весь repository;
* выполнять массовый rename;
* менять configuration;
* добавлять dependencies;
* трогать generated artifacts вне scope.

Если обнаружено соседнее противоречие, его следует записать как отдельный finding.

⸻

Worktree и отдельные рабочие копии

На раннем этапе AOS не требует обязательного использования Git worktree.

Обычной branch достаточно, если:

* одновременно выполняется одна write-задача;
* scope ограничен;
* нет конфликтующих изменений;
* validation выполняется после записи;
* пользователь понимает текущее состояние.

Git worktree становится полезным, если:

* параллельно идут разные независимые задачи;
* нужен отдельный clean validation environment;
* требуется изоляция protected changes;
* нужно сравнивать разные baselines;
* review должен выполняться без риска изменения active workspace.

Parallel write agents в одном рабочем дереве запрещены.

⸻

Один write-процесс

В одном workspace должен существовать только один активный writer.

Допустимы:

* один coding agent;
* человек, вручную редактирующий файл;
* один script, выполняющий bounded change.

Недопустимы:

* два агента, одновременно изменяющие одни и те же paths;
* агент и formatter, массово меняющие файлы параллельно;
* implementation и validation, одновременно изменяющие workspace;
* automatic correction во время review.

Read-only analysis может выполняться параллельно, если он не изменяет files или Git state.

⸻

Разделение режимов работы

Workspace должен поддерживать разные режимы:

Planning workspace

Предназначен для:

* чтения;
* анализа;
* формирования draft;
* определения scope;
* выявления unknowns.

Planning не изменяет implementation.

Execution workspace

Предназначен для:

* ограниченных изменений;
* запуска разрешённых commands;
* формирования результата задачи.

Execution не должен включать review следующего этапа.

Validation workspace

Предназначен для:

* проверок;
* чтения diff;
* запуска tests;
* фиксации findings.

Validation не исправляет результат.

Review workspace

Предназначен для:

* оценки содержания;
* проверки consistency;
* сопоставления с требованиями;
* формирования рекомендаций.

Review является read-only.

⸻

Temporary workspace

Для временных outputs используется:

/.aos-tmp/

или эквивалентная temporary directory внутри project root.

Она предназначена для:

* command outputs;
* временных prompts;
* intermediate comparisons;
* generated scratch files;
* temporary logs;
* unpacked reference materials;
* disposable reports;
* working drafts, которые ещё не являются documentation artifacts.

Temporary workspace должен:

* быть исключён из Git;
* очищаться без влияния на durable state;
* не использоваться как Source of Truth;
* не содержать единственную копию важного результата.

⸻

Что нельзя хранить во временной области

В /.aos-tmp/ нельзя хранить как единственный durable источник:

* canonical documentation;
* accepted decisions;
* human approvals;
* Evidence;
* final validation reports;
* checkpoints;
* Task Briefs;
* architecture decisions;
* release artifacts;
* permanent source register;
* implementation contracts.

Если temporary artifact становится значимым, он должен быть перенесён в подходящий durable path отдельным контролируемым изменением.

⸻

Durable artifacts

Durable artifacts должны находиться в понятных постоянных paths.

К ним относятся:

* содержательная документация;
* contracts;
* code;
* tests;
* accepted reports;
* decisions;
* source references;
* implementation examples;
* configuration;
* release notes.

Durable artifact должен:

* быть отслеживаемым Git;
* иметь понятное назначение;
* находиться рядом с соответствующим объектом;
* не зависеть от случайного local path;
* не требовать знания истории чата для понимания.

⸻

Локальные пользовательские файлы

Workspace может содержать пользовательские локальные настройки, которые не входят в repository.

Например:

* IDE settings;
* local environment variables;
* credentials;
* caches;
* private notes;
* machine-specific paths.

Такие файлы должны быть:

* исключены через .gitignore;
* отделены от canonical configuration;
* необязательны для воспроизведения проекта;
* документированы, если без них нельзя запустить локальную среду.

Secrets никогда не должны попадать в repository.

⸻

Environment variables

Если AOS требует environment variables, необходимо разделять:

documented variable names

и

actual secret values

В repository допустимы:

* .env.example;
* описание переменных;
* safe defaults;
* validation наличия обязательных значений.

В repository недопустимы:

* реальные API keys;
* passwords;
* access tokens;
* private certificates;
* personal identifiers.

⸻

External tools

Workspace не должен предполагать наличие большого набора инструментов.

На раннем этапе достаточно минимального набора:

* Git;
* text editor или IDE;
* shell;
* выбранный runtime после принятия toolchain;
* test runner после появления implementation.

AI tools могут быть разными:

* ChatGPT;
* Codex;
* Antigravity;
* Claude Code;
* Gemini;
* другие coding agents.

Workspace contracts не должны жёстко зависеть от одного provider.

⸻

Agent scratch files

Агент не должен создавать в durable paths файлы вроде:

analysis.txt
notes.md
temp.py
fix_final.py
output.log
draft_latest.md
backup_old.md

Если такие файлы нужны для работы, они должны находиться в /.aos-tmp/.

Исключение — когда файл явно является согласованным artifact задачи.

⸻

Generated files

Generated files должны иметь ясный статус.

Нужно определить:

* из чего они генерируются;
* можно ли их удалить и восстановить;
* должны ли они отслеживаться Git;
* являются ли они derived;
* кто является canonical source.

Generated artifact не должен становиться новым Source of Truth только потому, что он удобнее для чтения.

⸻

Naming rules

Пути должны быть:

* предсказуемыми;
* ASCII-friendly;
* без случайных пробелов;
* без временных suffix;
* с устойчивой нумерацией;
* понятными без внешнего пояснения.

Для документационного слоя используется формат:

NN_Section
NN.MM_Object
NN.MM.KK_Document.md

Существующие номера не меняются без крайней необходимости.

⸻

Работа с большими исходными материалами

Chat exports, legacy snapshots и большие reference documents не должны автоматически копироваться в active documentation folders.

Рабочий процесс:

источник
→ temporary или reference area
→ анализ
→ извлечение знаний
→ очищенный предметный документ

Raw source не должен смешиваться с итоговым знанием.

⸻

Работа с uploaded и external files

Файл из внешнего источника должен быть классифицирован:

* raw source;
* immutable reference;
* temporary input;
* extracted knowledge;
* candidate for import;
* rejected material.

До классификации внешний файл не становится частью active AOS.

⸻

Session handoff

Даже до автоматизации workspace должен позволять передать работу между sessions.

Минимальный handoff должен объяснять:

* где находится repository;
* какая branch активна;
* какой файл или объект изменялся;
* что уже сделано;
* что не сделано;
* какие findings существуют;
* какое одно действие требуется дальше.

На раннем этапе handoff может быть обычным кратким сообщением или Markdown-файлом.

⸻

Stop conditions workspace

Работа должна быть остановлена, если:

* выбран неправильный repository;
* project root не совпадает с ожидаемым;
* branch неожиданно изменилась;
* выполняется незавершённый merge или rebase;
* target path находится вне разрешённого subtree;
* требуется удалить существующие материалы без разрешения;
* unrelated changes невозможно изолировать;
* baseline неизвестен для write-задачи;
* агенту требуется network, хотя оно не разрешено;
* выполнение требует расширения sandbox;
* target file содержит чужие изменения, которые будут потеряны;
* возник scope conflict.

Stop condition должна приводить к короткому отчёту, а не к автоматическому recovery loop.

⸻

Минимальный preflight

Перед write-задачей достаточно проверить:

pwd
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short

Дополнительно при необходимости:

git diff --check
git diff -- <target-path>

Preflight должен быть пропорционален риску.

Для простой замены одного Markdown-файла не нужен full environment audit.

⸻

Минимальный post-change check

После изменения необходимо:

1. показать изменённые files;
2. проверить diff;
3. проверить отсутствие whitespace errors;
4. убедиться, что unrelated files не затронуты;
5. запустить заявленную validation;
6. остановиться до commit, если commit отдельно не разрешён.

Для одного Markdown-файла может быть достаточно:

git diff --check
git diff -- <target-file>

⸻

Commit boundary

Изменение файла и commit — разные действия.

Даже если работа выполнена корректно, commit не выполняется автоматически.

Перед commit пользователь должен понимать:

* какие files изменены;
* что содержит diff;
* прошла ли validation;
* есть ли unrelated changes;
* соответствует ли результат задаче.

Commit не означает push.

⸻

Network boundary

По умолчанию network access выключен.

Network включается только если:

* задача действительно требует внешнего источника;
* источник нельзя получить локально;
* разрешены конкретные hosts или actions;
* пользователь понимает цель доступа.

Documentation editing, local inspection и большинство validation tasks не требуют network.

⸻

Workspace для документационного этапа

На текущем этапе основной рабочий процесс прост:

ChatGPT формирует содержательный документ
→ пользователь вставляет Markdown в файл
→ проверяется git diff
→ документ проходит review
→ позже выполняется commit

Это допустимая ручная модель.

Она предпочтительнее сложного automation, пока:

* документы активно перерабатываются;
* структура ещё уточняется;
* единый authorial style важнее скорости массовой записи;
* агенты могут непреднамеренно менять Markdown formatting.

⸻

Когда потребуется automation workspace

Automation workspace может понадобиться, когда:

* количество документов станет большим;
* структура стабилизируется;
* появятся повторяющиеся migrations;
* нужно будет проверять links;
* потребуется validation numbering;
* нужно будет генерировать derived index;
* появится implementation code;
* потребуется reproducible test environment.

До этого момента ручные действия являются более коротким и безопасным путём.

⸻

Требования к Workspace Foundation

Workspace Foundation должна быть:

Явной

Пользователь знает repository, project root, branch и target path.

Ограниченной

Задача затрагивает только разрешённую область.

Воспроизводимой

Другой человек может повторить preflight и увидеть тот же baseline.

Изолированной

Unrelated changes не смешиваются с текущей задачей.

Минимальной

Не требует отдельного Control Plane для обычной работы.

Безопасной

Secrets, destructive actions и network не включаются неявно.

Продолжаемой

После остановки понятно, где продолжить работу.

⸻

Что не входит в Workspace Foundation

Workspace Foundation не определяет:

* architecture Product Runtime;
* окончательный language stack;
* CI provider;
* production deployment;
* persistent project database;
* agent orchestration;
* Runtime Enforcement;
* multi-repository protocol;
* team access model;
* release workflow.

Эти вопросы решаются позднее.

⸻

Критерий готовности

Workspace Foundation считается достаточно определённой, если человек или агент может:

1. открыть правильный repository;
2. определить project root;
3. подтвердить active branch;
4. увидеть baseline;
5. изолировать target paths;
6. сохранить temporary outputs вне durable paths;
7. выполнить ограниченное изменение;
8. показать точный diff;
9. не затронуть unrelated files;
10. оставить понятное состояние для следующей session.

⸻

Ошибки, которых нужно избежать

Случайный current working directory

Работа не должна начинаться только потому, что shell открыт в какой-то папке.

Temporary files в repository root

Scratch outputs быстро превращаются в неясные artifacts.

Unrelated formatting

Массовое изменение Markdown или code formatting мешает review.

Parallel writers

Несколько write agents могут создать скрытые конфликты.

Validation с исправлением

Проверяющий процесс не должен незаметно изменять результат.

Network by default

Большинство workspace tasks должны быть локальными.

Worktree как обязательная сложность

Worktree полезен, но не нужен для каждой малой задачи.

Workspace как Control Plane

Организация directories и branches не должна превращаться в самостоятельный продукт.

⸻
