# Project Principles

Назначение

Этот документ фиксирует основные принципы разработки AOS.

Они нужны для того, чтобы:

* не повторить фундаментальные ошибки AOS-FARM;
* сохранять product-first направление;
* не смешивать продукт, фабрику разработки и управляющий слой;
* не заменять реальный прогресс формальной готовностью;
* удерживать систему простой, проверяемой и воспроизводимой;
* давать человеку и агенту единые основания для архитектурных и продуктовых решений.

Эти принципы не являются детальной архитектурой или пошаговым roadmap. Они задают критерии, по которым должны оцениваться последующие решения.

⸻

1. Product First

Сначала создаётся наблюдаемая пользовательская ценность.

Приоритет имеют:

* реальный пользовательский сценарий;
* работающий product vertical slice;
* понятное поведение;
* проверяемый результат;
* снижение конкретной пользовательской боли.

Не считаются достаточным product progress:

* новый registry;
* дополнительный validator;
* очередной approval package;
* расширение Governance;
* новый recovery workflow;
* подробный план без реализации;
* готовый skeleton без работающего поведения.

Инфраструктура оправдана только тогда, когда она помогает создавать, проверять или поддерживать пользовательскую ценность.

⸻

2. Product Runtime раньше Development Factory

Product Runtime и Development Factory являются разными слоями.

Product Runtime предоставляет непосредственную ценность пользователю.

Development Factory помогает разрабатывать продукт и управлять работой агентов.

Критическая граница:

Product Runtime не должен зависеть от полного Development Factory.
Development Factory не является первой продуктовой функцией.

Сначала должен существовать минимальный пользовательский путь.

Только затем можно развивать:

* agent routing;
* project memory;
* task generation;
* controlled conveyor;
* automatic correction;
* advanced validation routing;
* operator tooling.

Development Factory не должна становиться обязательным условием запуска или развития Product Runtime.

⸻

3. Minimal Safety Floor с первого дня

Минимальные safety boundaries необходимы с начала проекта.

Они должны предотвращать:

* неявное расширение scope;
* подмену человеческого решения статусом агента;
* выполнение destructive operations без разрешения;
* смешение commit, push, merge и release;
* сокрытие неизвестности;
* ложные claims о готовности.

Минимальный safety floor должен быть небольшим, понятным и стабильным.

Он не должен автоматически превращаться в:

* full Governance;
* сложный lifecycle;
* Control Plane;
* многоуровневую систему approvals;
* обязательный registry;
* Runtime Enforcement.

Safety должна ограничивать опасные действия, а не блокировать весь полезный процесс разработки.

⸻

4. Сначала ручной процесс, затем автоматизация

Нельзя надёжно автоматизировать процесс, который ещё не был понят и стабилизирован вручную.

Правильный порядок:

ручной workflow
→ несколько реальных циклов
→ наблюдение повторяющихся действий
→ уточнение границ
→ формализация контракта
→ минимальная автоматизация
→ проверка пользы

Функция может быть автоматизирована, если:

* действие действительно повторялось;
* ручной процесс понятен;
* известны входы и выходы;
* известны типовые ошибки;
* можно измерить пользу автоматизации;
* существует безопасный способ отключить автоматизацию.

Не следует автоматизировать предполагаемый идеальный процесс.

⸻

5. Simplicity Before Abstraction

Сначала создаётся простое решение для конкретного сценария.

Универсальная abstraction появляется только после нескольких подтверждённых случаев использования.

Не следует заранее строить:

* универсальный registry;
* generic multi-agent framework;
* универсальную task state machine;
* общий orchestration layer;
* сложную plugin architecture;
* многоуровневое inheritance contract;
* универсальный storage model.

Преждевременная abstraction создаёт:

* скрытые зависимости;
* сложные точки отказа;
* больше вариантов состояния;
* трудности review;
* высокую стоимость изменений;
* риск того, что архитектура обслуживает гипотезы, а не реальный продукт.

⸻

6. Progressive Complexity

Система усложняется только тогда, когда простое решение перестаёт удовлетворять подтверждённые требования.

Каждый новый слой должен отвечать на три вопроса:

1. Какую наблюдаемую проблему он решает?
2. Почему существующего простого решения недостаточно?
3. Как проверить, что новый слой действительно улучшил систему?

Если эти вопросы не имеют ясного ответа, усложнение следует отложить.

⸻

7. Documentation Before Implementation

Перед реализацией должно существовать достаточное понимание:

* цели;
* пользовательского результата;
* границ;
* требований;
* критериев проверки;
* известных неизвестных.

Но documentation before implementation не означает:

* писать исчерпывающую спецификацию всей будущей системы;
* блокировать исследование из-за неполной документации;
* заменять реализацию планами;
* создавать большой пакет документов для малой задачи.

Документация должна быть достаточной для безопасного следующего шага.

⸻

8. Observable Behaviour важнее внутренних claims

Готовность должна подтверждаться наблюдаемым поведением.

Предпочтительный порядок доказательств:

observable user behavior
→ acceptance checks
→ tests
→ repository state
→ Evidence
→ documentation claims

Не следует считать доказательством готовности:

* статус COMPLETE;
* наличие документа;
* наличие schema;
* наличие validator;
* CI PASS без понимания coverage;
* заявление агента;
* закрытый planning stage.

Технический результат должен быть воспроизводим и проверяем.

⸻

9. Repository-First Factual State

Текущее техническое состояние проекта определяется repository и точным Git baseline.

История чатов, Project Sources, отчёты и reference packs могут:

* объяснять замысел;
* хранить lessons;
* предоставлять context;
* указывать на возможные решения.

Но они не могут автоматически переопределять фактическое состояние repository.

Если документация и repository расходятся, расхождение должно быть явно зафиксировано и разрешено.

⸻

10. One Source of Truth per Fact Class

Не требуется один документ для всей системы.

Необходимо, чтобы каждый класс фактов имел один понятный canonical owner.

Пример:

* назначение проекта — Project Identity;
* product direction — Product Vision;
* проектные принципы — Project Principles;
* архитектурное решение — соответствующий architecture document или ADR;
* фактическое состояние кода — Git repository;
* результат проверки — validation report;
* решение человека — отдельная human decision;
* исторический источник — reference material.

Generated indexes, dashboards, caches и summaries являются производными представлениями и не должны незаметно становиться новым Source of Truth.

⸻

11. Thin Documentation

Каждый документ должен отвечать на ограниченный набор вопросов.

Не следует создавать документы, которые одновременно содержат:

* product vision;
* architecture;
* roadmap;
* current state;
* approvals;
* implementation details;
* history;
* future ideas;
* validation results.

Большие взаимозависимые документы трудно:

* проверять;
* обновлять;
* сопоставлять с repository;
* использовать агентам;
* безопасно изменять.

Если документ становится слишком широким, его следует разделить по смысловым границам.

⸻

12. Knowledge рядом с объектом

Требования, lessons, validation criteria и sources должны находиться рядом с тем объектом, к которому они относятся.

Например, знания о Task Brief должны находиться в разделе Task Brief, а не быть распределены между несколькими несвязанными каталогами.

Это уменьшает:

* стоимость навигации;
* дублирование;
* противоречия;
* потерю контекста;
* необходимость собирать целостную картину вручную.

Общие cross-cutting правила выносятся отдельно только тогда, когда они действительно применяются к нескольким объектам.

⸻

13. Human Authority должна быть явной

Человек принимает решения, связанные с:

* существенным изменением scope;
* архитектурой;
* protected changes;
* destructive operations;
* принятием результата;
* commit;
* push;
* merge;
* release.

Агент может:

* анализировать;
* предлагать;
* выполнять разрешённую работу;
* проверять;
* формировать Evidence;
* сообщать findings.

Агент не может симулировать решение человека.

Технический статус не заменяет human approval.

⸻

14. Technical Result и Human Decision разделяются

Следующие утверждения неэквивалентны:

изменение выполнено
проверки прошли
Evidence собрано
review завершён
результат принят человеком

Каждый этап должен сохранять собственный смысл.

Обязательные инварианты:

PASS не означает approval.
Evidence не означает approval.
CI PASS не означает approval.
Skeleton не означает implementation.
Documentation не означает technical completion.

Это разделение должно быть видно как во внутренних contracts, так и в пользовательском интерфейсе.

⸻

15. UNKNOWN не превращается в OK

Если существенный факт неизвестен, он должен быть отмечен как неизвестный.

Нельзя:

* предполагать approval;
* придумывать baseline;
* считать отсутствующую проверку успешной;
* скрывать конфликт;
* заменять отсутствие данных оптимистичным выводом.

При этом неизвестность должна блокировать только затронутое решение.

Например:

* неизвестный baseline блокирует execution;
* но не обязательно блокирует read-only analysis;
* неизвестная dependency блокирует dependency decision;
* но не обязательно блокирует описание продукта;
* неизвестный implementation status должен оставаться UNKNOWN, а не превращаться в глобальную остановку проекта.

⸻

16. Fail Closed там, где затрагивается authority или необратимость

Fail-closed применяется, когда ошибка может привести к:

* неразрешённому изменению;
* destructive operation;
* неправильному merge;
* release без решения человека;
* нарушению protected boundary;
* подмене authority.

Fail-closed означает:

* остановиться;
* явно сообщить причину;
* не продолжать действие;
* не симулировать разрешение;
* запросить необходимый input.

Fail-closed не должен использоваться как универсальная причина блокировать низкорисковую документационную или аналитическую работу.

⸻

17. Scope не расширяется неявно

Каждая задача должна иметь ограниченный scope.

Во время выполнения агент не должен самостоятельно добавлять:

* новые features;
* архитектурные изменения;
* дополнительные refactoring areas;
* dependency changes;
* unrelated fixes;
* новую automation;
* изменение соседних документов.

Если обнаружена новая задача, она должна быть:

* зафиксирована;
* отделена от текущей;
* предложена как следующее действие;
* выполнена только после отдельного решения.

⸻

18. Одно следующее действие

После завершения этапа, finding, failure или review должно быть определено одно следующее действие.

Это действие может быть:

* следующая задача;
* требуемое решение человека;
* предоставление недостающего input;
* исправление одного blocking finding;
* остановка или отказ от пути.

Система не должна выдавать длинный список равнозначных направлений и перекладывать маршрутизацию на пользователя.

Если существует реальный конфликт вариантов, конфликт должен быть показан явно.

⸻

19. Один запуск — один этап

Planning, execution, validation и review являются разными типами работы.

Один запуск должен выполнять один этап.

Planning

* анализирует;
* формирует draft;
* не изменяет implementation;
* не выдаёт execution authorization.

Execution

* выполняет только разрешённый scope;
* не расширяет задачу;
* останавливается после результата или finding.

Validation

* проверяет результат;
* не исправляет код;
* не запускает следующий этап автоматически.

Review

* оценивает;
* фиксирует findings;
* не изменяет проверяемый artifact.

Такое разделение предотвращает скрытое исправление результатов во время проверки и потерю трассируемости.

⸻

20. Stop после finding или завершения этапа

После первого blocking finding агент должен:

1. зафиксировать finding;
2. сформировать отчёт;
3. определить одно следующее действие;
4. остановиться.

Не следует автоматически запускать:

* повторную validation;
* новый planning cycle;
* correction loop;
* следующий этап;
* новую recovery-задачу.

Повторные попытки допускаются только в заранее ограниченном и понятном процессе.

⸻

21. Recovery должна быть временной

Recovery — это средство выхода из проблемы, а не постоянный продуктовый слой.

Recovery artifacts могут:

* описывать проблему;
* фиксировать evidence;
* помогать выбрать baseline;
* поддерживать одно решение.

Они не должны:

* становиться новой обязательной архитектурой;
* создавать собственный бесконечный lifecycle;
* порождать новые recovery stages без ограничения;
* становиться permanent dependency Product Runtime;
* заменять решение о пересборке или отказе от неработающего пути.

У recovery должна быть явная exit condition.

⸻

22. Не исправлять сложность дополнительной сложностью

При появлении blocker сначала следует проверить, можно ли:

* упростить задачу;
* уменьшить scope;
* удалить ненужную dependency;
* перейти к ручному процессу;
* принять ограничение;
* изменить архитектурный путь;
* отказаться от малоценной функции.

Новый validator, registry, package, gate или status не должен быть автоматической реакцией на каждую проблему.

⸻

23. Reimplement from Contract by Default

Старый AOS-FARM используется как reference и evidence source.

Полезные возможности должны по умолчанию воспроизводиться по очищенным требованиям и observable contracts.

Прямой перенос допускается только после отдельной оценки:

* код действительно работает;
* его границы понятны;
* он не связан с устаревшим lifecycle;
* зависимости приемлемы;
* tests подтверждают поведение;
* перенос дешевле и безопаснее reimplementation.

Не следует переносить старую repository topology только потому, что она уже существует.

⸻

24. Lessons должны превращаться в проверяемые правила

Каждая значимая ошибка должна привести к одному из результатов:

* новый принцип;
* acceptance criterion;
* test;
* architecture boundary;
* явный anti-pattern;
* уточнение workflow.

Lesson бесполезен, если он остаётся только историческим описанием.

При этом не каждая ошибка требует нового механизма управления.

Иногда правильный результат lesson — удалить сложность или отказаться от функции.

⸻

25. Dependencies должны быть оправданы

Каждая dependency должна иметь ясное назначение.

Перед добавлением зависимости нужно оценить:

* какую проблему она решает;
* можно ли обойтись стандартными средствами;
* насколько она стабильна;
* как она влияет на reproducibility;
* что произойдёт при её недоступности;
* является ли она обязательной для Product Runtime;
* можно ли заменить её позже.

AOS не должен начинаться с обязательных DB, RAG, vector store, orchestration frameworks или SaaS services, если первый пользовательский сценарий может работать без них.

⸻

26. Replaceable Internals

Внутренние механизмы по возможности должны быть заменяемыми.

К ним относятся:

* model provider;
* agent runner;
* routing mechanism;
* storage;
* registry;
* UI;
* validation engine;
* CI provider;
* external integrations.

Product contracts не должны быть жёстко связаны с одной внутренней реализацией без необходимости.

⸻

27. Reproducibility

Существенный результат должен быть воспроизводим другим человеком или агентом.

Для этого должны быть понятны:

* исходное состояние;
* используемые inputs;
* выполненные действия;
* версии dependencies;
* проверки;
* ограничения;
* полученный результат.

«У меня работает» недостаточно для принятия component или workflow.

⸻

28. Tests закрепляют поведение, а не создают authority

Tests полезны для фиксации contracts и защиты от regression.

Но:

наличие test не означает правильность требования;
PASS всех tests не означает approval;
coverage не означает полноту продукта.

Tests должны проверять наблюдаемое и значимое поведение.

Они не должны существовать только для подтверждения структуры файлов или формальных статусов, если это не защищает реальный контракт.

⸻

29. Derived artifacts не являются Source of Truth

Indexes, dashboards, caches, generated reports и projections должны быть воспроизводимыми из canonical sources.

Они могут помогать:

* навигации;
* поиску;
* обзору;
* операционной работе.

Но они не должны незаметно становиться самостоятельным источником решений или статусов.

Если derived artifact конфликтует с canonical source, побеждает canonical source.

⸻

30. Architecture должна объяснять границы

Хорошая архитектура должна помогать понять:

* где находится ответственность;
* какие зависимости разрешены;
* какие слои можно отключить;
* как компонент проверяется;
* что не входит в его scope.

Архитектура не должна оцениваться по количеству слоёв, patterns или abstractions.

Лучшее решение — самое простое из тех, которые сохраняют необходимые границы и допускают дальнейшее развитие.

⸻

31. Product value должна быть измерима

Каждый значимый этап должен иметь observable success condition.

Примеры:

* пользователь быстрее понимает состояние проекта;
* уменьшается время восстановления context;
* снижается количество scope violations;
* другой агент способен продолжить работу;
* уменьшается количество recovery loops;
* пользователь быстрее завершает bounded change;
* количество ложных PASS сокращается.

Если улучшение нельзя наблюдать, его ценность должна быть поставлена под сомнение.

⸻

32. Документация — средство воспроизведения

Документационный слой должен позволить будущему человеку или агенту:

1. понять продукт;
2. определить последовательность построения;
3. восстановить requirements и contracts;
4. реализовать component;
5. проверить observable behavior;
6. избежать известных ошибок.

Документация не должна превращаться в архив, который понятен только участникам исходных обсуждений.

⸻

33. Принцип кратчайшего безопасного пути

При нескольких допустимых вариантах выбирается решение, которое:

* сохраняет обязательные safety boundaries;
* требует меньше новых сущностей;
* имеет меньше зависимостей;
* быстрее создаёт проверяемый результат;
* проще отменяется или заменяется;
* не расширяет scope.

Кратчайший путь не означает игнорирование рисков.

Он означает отказ от необязательной сложности.

⸻

34. Что запрещено повторять

При развитии AOS нельзя снова допустить:

* одновременное строительство Product Runtime, Development Factory, Governance и Control Plane;
* использование незавершённого Control Plane для создания самого себя;
* planning с execution-grade gates без необходимости;
* превращение recovery artifacts в permanent blockers;
* распределение current state между множеством равноправных источников;
* огромные взаимозависимые документы;
* automation до успешных manual cycles;
* подмену user-facing progress formal readiness;
* неограниченные correction loops;
* скрытое расширение scope;
* смешение technical result и human acceptance.

⸻

Применение принципов

Каждое существенное решение по AOS должно проверяться вопросами:

1. Создаёт ли это observable user value?
2. Не строим ли мы фабрику раньше продукта?
3. Можно ли начать с более простого ручного решения?
4. Какую реальную проблему решает новая сложность?
5. Где находится Source of Truth?
6. Как будет проверено поведение?
7. Сохраняется ли human authority?
8. Можно ли отключить или заменить новый слой?
9. Не расширяется ли scope?
10. Какое одно следующее действие требуется?

Если решение противоречит нескольким принципам, оно должно быть пересмотрено до реализации.

⸻

Условие успеха

Project Principles выполняют свою функцию, если они позволяют:

* выбирать между конкурирующими архитектурными вариантами;
* останавливать преждевременную автоматизацию;
* отделять продукт от инфраструктуры;
* сохранять минимальный safety floor;
* уменьшать количество recovery loops;
* удерживать документацию понятной;
* создавать AOS последовательными проверяемыми слоями;
* принимать решения без возвращения к длинной истории старого проекта.

⸻

Источники

Документ сформирован на основе:

* historical control и Governance материалов AOS-FARM, использованных только как reference;
* анализа ветки dev;
* refoundation lessons;
* аудита AOS-02;
* истории recovery и automation plans;
* решений о product-first sequencing;
* разделения Product Runtime и Development Factory;
* правила manual cycles before automation;
* lessons о thin documentation, one next action, fail-closed и repository-first factual state.

Ключевые failure modes старого проекта включали опережение Governance, self-hosting незавершённого Control Plane, превращение recovery в blocker, распределение state между repository и chats, чрезмерно большие документы и automation до успешных manual cycles.

Product-first последовательность требует сначала product discovery и Product Runtime vertical slices, затем ручные development cycles и только после этого оправданную automation и Governance.

Canonical AOS model также разделяет Documentation Assembly Pipeline, Code Assembly Pipeline, Minimal Safety Floor, progressive Governance и более поздний Runtime Enforcement.

## Legacy Reference Boundary

Legacy sources не определяют active state нового AOS.

```yaml
AOS-FARM:
  mode: READ_ONLY_REFERENCE
  authority: NONE

AgentOS/AOS-1:
  mode: READ_ONLY_REFERENCE
  authority: NONE
```

Допустимо извлекать только:

- product intent;
- observable behavior;
- contracts;
- tests;
- schemas;
- lessons;
- failure modes;
- implementation candidates.

Запрещено наследовать без отдельного анализа и human decision:

- active architecture;
- repository topology;
- Source of Truth;
- lifecycle;
- approval;
- Risk Profile;
- execution authority;
- implementation readiness.

Извлечённое правило становится частью нового AOS только после самостоятельной формулировки в соответствующем canonical topic. Сходство с legacy и historical status не создают authority.
