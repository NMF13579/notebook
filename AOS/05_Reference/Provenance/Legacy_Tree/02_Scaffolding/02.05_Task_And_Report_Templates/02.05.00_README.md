02.05 — Task and Report Templates

Назначение

Этот документ определяет минимальные шаблоны постановки задачи и отчёта о результате в проекте AOS.

Шаблоны нужны для того, чтобы:

* задача имела ясный scope;
* агент понимал ожидаемый результат;
* ограничения не терялись между sessions;
* validation можно было выполнить отдельно;
* findings не смешивались с выполненной работой;
* итоговый результат можно было быстро проверить;
* пользователь видел одно следующее действие;
* не требовалась сложная task database или state machine.

Шаблоны должны быть короткими и пропорциональными размеру задачи.

Они не должны превращать каждое изменение в большой Governance package.

⸻

Основной принцип

До начала write-задачи должно быть достаточно информации, чтобы ответить на вопросы:

что нужно сделать
где это нужно сделать
что нельзя менять
какой результат ожидается
как результат будет проверен
когда необходимо остановиться

После завершения задачи должно быть достаточно информации, чтобы ответить:

что было сделано
что изменилось
что было проверено
что осталось неизвестным
какие findings обнаружены
какое действие требуется дальше

⸻

Два основных артефакта

Минимальный workflow использует два смысловых объекта:

Task Brief
Stage Report

Task Brief

Описывает разрешённую работу до её начала.

Stage Report

Фиксирует фактический результат после завершения этапа.

Task Brief не является approval сам по себе.

Stage Report не является human acceptance.

⸻

Task Brief

Task Brief — это ограниченное описание одной задачи.

Он должен позволять агенту выполнить работу без повторного определения scope.

Минимальный Task Brief содержит:

* идентификатор или короткое название;
* цель;
* контекст;
* ожидаемый результат;
* разрешённый scope;
* запрещённый scope;
* исходное состояние;
* validation;
* stop conditions;
* разрешённые действия;
* запрещённые действия.

⸻

Минимальный шаблон Task Brief

# Task Brief — <краткое название>
## Цель
<Какую конкретную проблему нужно решить.>
## Ожидаемый результат
<Что должно существовать или измениться после выполнения задачи.>
## Контекст
<Минимальная информация, необходимая для понимания задачи.>
## Разрешённый scope
- <разрешённый файл, каталог или component>
- <необходимое связанное изменение>
## Запрещённый scope
- <paths или components, которые нельзя менять>
- <виды изменений, которые не входят в задачу>
## Исходное состояние
- Repository: `<repository>`
- Branch: `<branch>`
- Baseline: `<commit или описание исходного состояния>`
- Target: `<target path или component>`
## Требования
1. <проверяемое требование>
2. <проверяемое требование>
3. <проверяемое требование>
## Validation
- <команда или способ проверки>
- <ожидаемый результат>
## Stop conditions
- задача выполнена;
- обнаружен blocking finding;
- требуется расширение scope;
- требуется human decision;
- исходное состояние не совпадает с ожидаемым.
## Разрешённые действия
- <read-only или workspace-write>
- <разрешённые команды>
- <разрешён ли network>
## Запрещённые действия
- не выполнять commit;
- не выполнять push;
- не выполнять merge;
- не выполнять destructive operations;
- не начинать следующий этап.
## Итог
После завершения сформировать Stage Report и остановиться.

⸻

Размер Task Brief

Task Brief должен соответствовать сложности задачи.

Для простой документационной задачи

Достаточно:

цель
target file
что сохранить
что удалить
как проверить diff
stop after report

Для routine code task

Потребуются:

behavior
scope
baseline
tests
constraints
stop conditions

Для complex или protected task

Дополнительно могут потребоваться:

architecture constraints
Risk Profile
human checkpoint
dependency boundaries
rollback approach
validation lanes
protected paths

Не следует использовать большой high-risk шаблон для обычного исправления одного Markdown-файла.

⸻

Критерии хорошего Task Brief

Хороший Task Brief:

* описывает одну задачу;
* имеет ограниченный scope;
* содержит проверяемый expected result;
* отделяет требования от предложенного способа реализации;
* фиксирует forbidden scope;
* определяет validation;
* содержит stop conditions;
* не выдаёт plan за authorization;
* не разрешает следующий этап автоматически;
* может быть передан другому агенту без длинной истории чата.

⸻

Плохой Task Brief

Плохой Task Brief выглядит так:

Улучши проект.
Исправь всё, что найдёшь.
Доведи систему до готовности.
Сделай архитектуру правильно.
Автоматизируй процесс.

Такие формулировки:

* не имеют границ;
* позволяют агенту расширять scope;
* не дают критерия завершения;
* смешивают planning и execution;
* делают validation субъективной;
* провоцируют бесконечную работу.

⸻

Task Brief и Plan

Plan и Task Brief выполняют разные функции.

Plan

Описывает возможный путь.

Plan может содержать:

* этапы;
* варианты;
* зависимости;
* risks;
* proposed sequence.

Task Brief

Разрешает одну ограниченную единицу работы после необходимых human decisions.

Обязательное различие:

Plan output не означает Task Brief.
Task Brief не означает approval, если approval требуется отдельно.
Task Brief не означает commit, push, merge или release authorization.

⸻

Task Brief и Risk Profile

Агент может предложить Risk Profile, но назначает его человек.

Для routine documentation tasks отдельный Risk Profile может не требоваться.

Для задач, затрагивающих:

* protected paths;
* architecture;
* Governance;
* destructive operations;
* external systems;
* merge или release;

Risk Profile и human checkpoint могут быть обязательны до execution.

Если необходимый Risk Profile не назначен, Task Brief не считается executable.

⸻

Task Brief и baseline

Для write-задачи Task Brief должен связывать работу с исходным состоянием.

Минимально:

repository
branch
baseline commit
target paths

Если baseline изменился до начала execution, Task Brief должен быть проверен повторно.

Если изменение baseline не влияет на scope и requirements, может быть достаточно подтвердить новый commit.

Если baseline materially changed, задача возвращается в planning или review.

⸻

Task Brief и observable result

Expected result должен описывать наблюдаемый итог.

Плохо:

улучшить модуль
сделать архитектуру лучше
обеспечить качество
подготовить систему

Хорошо:

CLI возвращает ненулевой exit code при validation failure.
README содержит описание Product Runtime без YAML metadata.
Session summary показывает последнее завершённое действие и одно следующее действие.

Observable result должен быть доступен для validation.

⸻

Requirements

Каждое требование должно быть:

* однозначным;
* ограниченным;
* проверяемым;
* связанным с целью;
* не расширяющим hidden scope.

Требования желательно формулировать как поведение или состояние.

Пример:

При неизвестном approval execution должен быть заблокирован.

Лучше, чем:

Добавить хорошую approval систему.

⸻

Allowed scope

Allowed scope определяет, что агент может менять.

Пример:

AOS/02_Scaffolding/02.05_Task_and_Report_Templates/**

или:

src/aos/task_brief.py
tests/test_task_brief.py

Разрешение каталога не означает, что агент должен менять все файлы внутри него.

Изменяются только файлы, необходимые для expected result.

⸻

Forbidden scope

Forbidden scope нужен, чтобы предотвратить типичное неявное расширение задачи.

Примеры:

не менять architecture documents
не менять dependencies
не менять CI
не менять public API
не менять соседние product contracts
не создавать registry
не добавлять database

Если для выполнения задачи требуется изменение запрещённой области, агент должен остановиться.

⸻

Validation

Task Brief должен определить, как проверить результат.

Validation может включать:

* чтение diff;
* Markdown review;
* test command;
* lint;
* type check;
* acceptance scenario;
* schema validation;
* manual UI check;
* repository inspection.

Validation не обязана быть полностью автоматической.

Важно, чтобы было понятно:

* что проверяется;
* каким способом;
* какой результат считается успешным;
* что не проверяется.

⸻

Stop conditions

Stop conditions ограничивают agent run.

Минимальные stop conditions:

* задача завершена;
* найден blocking finding;
* требуется human decision;
* требуется расширение scope;
* baseline не соответствует Task Brief;
* validation завершена;
* произошёл failure;
* следующий этап не разрешён.

Stop condition должна приводить к report и остановке.

Она не должна автоматически запускать recovery или correction loop.

⸻

Execution authorization

Task Brief должен явно указывать, разрешена ли запись.

Возможные режимы:

read-only
workspace-write

Дополнительные разрешения задаются отдельно:

network
commit
push
merge
release
destructive operations

Если разрешение не указано, оно считается отсутствующим.

⸻

Stage Report

Stage Report фиксирует фактический результат одного этапа.

Он должен отвечать на вопросы:

* какая задача выполнялась;
* какой этап завершён;
* что сделано;
* какие файлы изменены;
* что проверено;
* какие findings обнаружены;
* что осталось неизвестным;
* какие Git actions выполнялись;
* какое одно действие требуется дальше.

Stage Report должен описывать факты, а не создавать approval.

⸻

Минимальный шаблон Stage Report

# Stage Report — <краткое название>
## Задача
<Что было поручено.>
## Этап
<Planning, Execution, Validation или Review.>
## Результат
<Краткое описание фактического результата.>
## Изменённые файлы
- `<path>`
- `<path>`
Если изменений не было:
- Нет изменений.
## Выполненные проверки
- `<команда или способ проверки>` — `<результат>`
- `<команда или способ проверки>` — `<результат>`
## Findings
- <finding>
Если findings нет:
- Blocking findings не обнаружены.
## Unknowns
- <непроверенный или неизвестный факт>
Если unknowns нет:
- Существенные unknowns не обнаружены.
## Git actions
- Commit: `NOT_RUN`
- Push: `NOT_RUN`
- Merge: `NOT_RUN`
- Release: `NOT_RUN`
## Следующее действие
<Ровно одно действие.>

⸻

Report для read-only этапа

Если этап был planning, validation или review, report должен явно указать:

Изменения файлов: нет.

Не следует создавать впечатление, что read-only этап что-то исправил.

Пример:

## Результат
Найдено противоречие между Product Contract и текущим CLI behavior.
## Изменённые файлы
- Нет изменений.
## Следующее действие
Подготовить отдельный Task Brief на исправление CLI behavior.

⸻

Report для execution

Execution report должен описывать:

* что изменено;
* какие требования закрыты;
* какие проверки запускались;
* что не проверялось;
* есть ли отклонения от Task Brief;
* существует ли remaining diff;
* выполнялись ли Git actions.

Не следует использовать формулировку готово, если существуют существенные unknowns или validation ещё не выполнялась.

⸻

Report для validation

Validation report должен отделять:

* PASS;
* FAIL;
* UNKNOWN;
* NOT_RUN;
* findings.

Пример:

Unit tests: PASS
Integration test: NOT_RUN
Manual UX check: UNKNOWN
Scope compliance: PASS
Human acceptance: NOT_APPLICABLE_TO_VALIDATION

Validation report не должен исправлять найденные проблемы.

⸻

Report для review

Review report должен содержать:

* итоговую оценку;
* blocking findings;
* non-blocking findings;
* противоречия;
* assumptions;
* одно следующее действие.

Review не должен автоматически создавать новый accepted revision.

Human acceptance остаётся отдельным решением.

⸻

Findings

Finding — это конкретное обнаруженное несоответствие, риск или отсутствие обязательного условия.

Хороший finding содержит:

факт
влияние
границу
следующее действие

Пример:

CLI возвращает exit code 0 при validation failure.
Это позволяет внешнему automation считать неуспешную проверку успешной.
Finding затрагивает только CLI exit semantics.
Следующее действие: подготовить Task Brief на исправление exit code.

Плохо:

CLI плохой.
Нужно всё переделать.

⸻

Blocking finding

Finding является blocking, если без его устранения нельзя безопасно:

* считать текущий этап успешным;
* выполнять следующий этап;
* принимать результат;
* выполнять protected action;
* выполнять commit, push, merge или release;
* подтверждать заявленное observable behavior.

Blocking finding должен остановить текущий run.

⸻

Non-blocking finding

Non-blocking finding:

* не нарушает expected result текущей задачи;
* не создаёт существенного safety risk;
* может быть оформлен отдельной задачей;
* не требует скрытого расширения scope.

Он фиксируется в report, но не исправляется автоматически.

⸻

Unknowns

Unknown — это существенный факт, который не был подтверждён.

Примеры:

* test не запускался;
* external integration недоступна;
* approval отсутствует;
* production behavior не проверено;
* baseline другого repository неизвестен;
* compatibility не исследована.

Unknown нельзя скрывать.

Но unknown должен блокировать только затронутый claim или action.

⸻

Статусы проверок

Рекомендуемые базовые значения:

PASS
FAIL
UNKNOWN
NOT_RUN
BLOCKED

PASS

Проверка выполнена и ожидаемое условие подтверждено.

FAIL

Проверка выполнена и условие не выполнено.

UNKNOWN

Недостаточно данных для вывода.

NOT_RUN

Проверка не запускалась.

BLOCKED

Проверка не могла быть выполнена из-за конкретного blocker.

Обязательные различия:

UNKNOWN не означает PASS.
NOT_RUN не означает PASS.
BLOCKED не означает FAIL результата.
PASS не означает approval.

⸻

Git actions в report

Report должен отдельно указывать:

Commit
Push
Merge
Release

Если действие не выполнялось, писать:

NOT_RUN

Не следует писать N/A, если действие просто не было разрешено или не запускалось.

Если действие было запрещено, можно указать:

Commit: NOT_RUN — authorization отсутствует.

⸻

Одно следующее действие

Report завершается ровно одним следующим действием.

Оно должно быть:

* конкретным;
* выполнимым;
* связанным с результатом;
* не скрывающим human decision;
* не содержащим несколько этапов.

Хорошо:

Провести read-only review изменённого документа.

Плохо:

Проверить документ, исправить findings, создать commit, push и перейти к следующему разделу.

⸻

Отчёт без следующего действия

Отсутствие следующего действия допустимо только если:

* работа завершена окончательно;
* пользователь явно попросил остановиться;
* проектный путь закрыт;
* дальнейшие действия отсутствуют.

В таком случае следует явно написать:

Следующее действие: отсутствует; работа остановлена.

⸻

Простая документационная задача

Для текущего этапа заполнения документации можно использовать сокращённый Task Brief.

# Task Brief — заполнить <документ>
## Цель
Создать содержательный Markdown-документ для `<path>`.
## Требования
- сохранить принятую структуру;
- не использовать YAML metadata;
- не добавлять служебный Status;
- не изменять соседние файлы;
- не выдавать документ за implementation или approval.
## Validation
- проверить Markdown;
- проверить diff;
- убедиться, что изменён только target file.
## Stop conditions
- документ создан;
- найдено существенное противоречие;
- требуется изменение структуры.
## Git actions
- Commit: запрещён без отдельного решения.
- Push: запрещён.
- Merge: запрещён.

⸻

Простая документационная отчётность

После заполнения одного документа достаточно:

# Stage Report — <документ>
## Результат
Документ заполнен содержательным Markdown.
## Изменённые файлы
- `<path>`
## Проверки
- Markdown structure — PASS
- Target-only diff — PASS
- Content review — NOT_RUN
## Findings
- Blocking findings не обнаружены.
## Git actions
- Commit: NOT_RUN
- Push: NOT_RUN
- Merge: NOT_RUN
## Следующее действие
Провести read-only review документа.

⸻

Routine code task

Для небольшой code-задачи Task Brief должен дополнительно включать:

* expected behavior;
* affected interface;
* tests;
* compatibility constraints;
* error handling;
* forbidden refactoring.

Report должен указать:

* implementation result;
* test result;
* remaining limitations;
* exact files;
* commands;
* Git state.

⸻

Complex task

Для complex task Task Brief может быть разделён на:

Context
Scope
Requirements
Architecture constraints
Dependencies
Validation
Risk
Stop conditions
Authorization

Но даже complex Task Brief должен описывать одну executable unit.

Нельзя превращать его в master plan всей системы.

⸻

Protected task

Для protected task дополнительно требуются:

* explicit human checkpoint;
* assigned Risk Profile;
* exact protected paths;
* rollback approach;
* approval boundary;
* отдельная validation;
* отдельный review;
* запрет автоматического следующего этапа.

Task Brief без обязательного human decision остаётся неисполняемым.

⸻

Где хранить шаблоны

На раннем этапе достаточно хранить шаблоны рядом с этим документом.

В будущем возможна структура:

02.05_Task_and_Report_Templates/
├── 02.05.00_README.md
├── 02.05.01_Task_Brief_Template.md
├── 02.05.02_Stage_Report_Template.md
├── 02.05.03_Validation_Report_Template.md
└── 02.05.04_Review_Report_Template.md

Не следует создавать дополнительные шаблоны до реальной необходимости.

⸻

Где хранить Task Briefs и Reports

До появления устойчивого workflow конкретные Task Briefs и Reports могут храниться рядом с соответствующим объектом.

Например:

03.02_Project_Intake/
├── 03.02.00_README.md
├── 03.02.01_Task_Brief.md
└── 03.02.02_Validation_Report.md

Альтернативный централизованный task registry не нужен на раннем этапе.

Главное — чтобы artifact было легко связать с объектом и результатом.

⸻

Не создавать Task Database заранее

На первом этапе не требуется:

* SQLite;
* event store;
* task registry service;
* lifecycle engine;
* status synchronization;
* web dashboard;
* workflow database.

Markdown и Git достаточны для нескольких manual cycles.

Persistent system появляется только после подтверждения:

* какие поля действительно нужны;
* какие transitions повторяются;
* какие запросы должен поддерживать продукт;
* почему файлового подхода недостаточно.

⸻

Не создавать сложный lifecycle заранее

Минимальные этапы:

Planning
Execution
Validation
Review

Не требуется сразу вводить десятки состояний:

READY_FOR_PRE_REVIEW
PROVISIONALLY_VALIDATED
TECHNICALLY_CLOSED
CONDITIONALLY_ACCEPTED
AWAITING_LIFECYCLE_RECONCILIATION

Новый status оправдан только если он меняет реальное допустимое действие и не может быть выражен существующими фактами.

⸻

Шаблон не является execution engine

Markdown template:

* помогает формулировать задачу;
* сохраняет границы;
* улучшает handoff.

Но он не может сам:

* проверить authorization;
* гарантировать scope;
* запустить validation;
* назначить Risk Profile;
* подтвердить human approval.

Runtime enforcement появляется позднее для стабильных и критических правил.

⸻

Типичные ошибки

Слишком общий Task Brief

Агент вынужден сам определять scope и architecture.

Слишком подробный Task Brief

Документ превращается в попытку заранее описать всю implementation.

Plan вместо Task Brief

Список этапов ошибочно используется как разрешение на execution.

Task Brief без stop conditions

Агент продолжает находить и исправлять новые задачи.

Validation внутри execution без границы

Исполнитель сам принимает собственный результат.

Report как approval

Технический отчёт ошибочно формулируется как принятие человеком.

Список следующих действий

Пользователь снова вынужден самостоятельно маршрутизировать процесс.

Status inflation

Появляется множество статусов без реального operational meaning.

Template bureaucracy

Простая задача требует больше времени на оформление, чем на выполнение.

⸻

Критерий готовности

Task and Report Templates считаются достаточно определёнными, если:

1. простую задачу можно описать коротко;
2. complex task можно ограничить без ambiguity;
3. allowed и forbidden scope различаются;
4. baseline понятен;
5. validation задана до execution;
6. stop conditions присутствуют;
7. planning, execution, validation и review разделены;
8. report фиксирует факты;
9. unknowns и NOT_RUN раскрываются;
10. Git actions указаны отдельно;
11. human approval не симулируется;
12. report заканчивается одним следующим действием.

⸻

Что не входит в этот документ

Этот документ не определяет:

* окончательный task registry;
* database schema;
* автоматическую state machine;
* routing algorithm;
* конкретные provider prompts;
* Evidence package format;
* merge authorization package;
* release workflow;
* Runtime Enforcement;
* UI task board.

Эти элементы появляются только после подтверждения необходимости.
