# 04.02.00 Task Model

## Назначение документа

Task Model определяет, что в новом AOS считается задачей, как ограничивается её Scope и когда возникает отдельная follow-up task.

Task — минимальная управляемая единица разработки, направленная на один проверяемый результат.

## Legacy Reference Boundary

Материалы `NMF13579/AOS-FARM`, `AgentOS/AOS-1`, старые планы, отчёты, чаты и recovered artifacts используются только как `READ_ONLY_REFERENCE` с `authority: NONE` для нового проекта.

Из них разрешено извлекать:

- product intent;
- observable behavior;
- candidate contracts;
- повторяющиеся failure modes;
- доказанные lessons;
- полезные implementation ideas.

Из них нельзя автоматически переносить:

- active architecture;
- repository topology;
- Source of Truth;
- lifecycle или status;
- approvals;
- Risk Profiles;
- execution, Commit, Push, Merge или Release authorization;
- implementation readiness;
- незавершённые recovery chains;
- legacy complexity.

Любая идея из reference material становится частью нового AOS только после независимого анализа, явного описания в документации нового проекта и соответствующего human decision. Сходство с legacy не является основанием для принятия.

## Почему нужна Task Model

В предыдущих cycles под словом «задача» одновременно понимались:

- идея;
- исследование;
- plan;
- implementation;
- validation;
- repair;
- recovery program;
- серия связанных изменений.

Это создавало scope drift и отсутствие terminal state.

Task Model устраняет такую неоднозначность.

## Определение Task

Task — bounded unit of work, которая имеет:

- одну основную цель;
- ожидаемый observable result;
- известный context;
- allowed scope;
- forbidden scope;
- baseline;
- requirements;
- validation expectations;
- stop conditions;
- permissions.

Если ожидаемый результат невозможно сформулировать, Task ещё не определена.

## One Task — One Primary Result

Одна Task стремится к одному основному результату.

Допустимые примеры:

- подготовить один документ;
- реализовать один bounded behavior;
- исправить один определённый defect;
- проверить один candidate;
- исследовать один architecture question.

Несколько независимых результатов требуют декомпозиции.

## Task Is Not an Artifact

Следующие объекты не являются Task сами по себе:

- plan;
- Task Brief;
- Stage Report;
- Validation Report;
- chat;
- checklist;
- document;
- Evidence package.

Они могут описывать или сопровождать Task, но не заменяют её.

## Task Brief

Task Brief является исполнимым описанием Task.

Минимальные элементы:

- objective;
- expected result;
- repository и project root;
- branch;
- baseline;
- allowed scope;
- forbidden scope;
- requirements;
- validation;
- stop conditions;
- permissions;
- forbidden Git actions.

Task Brief не является approval.

```text
Plan output ≠ Task Brief
Task Brief ≠ execution authorization
```

## Scope Boundary

Allowed scope определяет, что можно изменить или исследовать.

Forbidden scope определяет, что нельзя затрагивать.

В Task нельзя скрыто добавлять:

- unrelated refactoring;
- новый subsystem;
- architecture change;
- protected change;
- новую dependency;
- legacy import;
- дополнительный lifecycle;
- исправление соседних findings.

## Scope Expansion

Scope expansion требует explicit human permission.

Если новая необходимость обнаружена во время Execution:

1. finding фиксируется;
2. оценивается, блокирует ли он текущий result;
3. текущий stage формирует report;
4. работа останавливается;
5. новая работа оформляется отдельной Task.

## Baseline

Task привязывается к baseline.

Baseline определяет исходное состояние, относительно которого:

- планировалась работа;
- создавался candidate;
- выполнялась Validation;
- оценивались изменения.

Изменившийся baseline требует повторной проверки применимости Task Brief.

## Task Classes

Task может относиться к одному основному классу:

- research;
- documentation;
- planning;
- implementation;
- validation;
- review;
- recovery;
- process improvement.

Task class помогает выбрать role и permissions, но не назначает Risk Profile или authorization.

## Planning Requirement

Planning обязателен, когда:

- Scope неоднозначен;
- отсутствует полный Task Brief;
- затрагивается architecture или Source of Truth;
- требуется новая dependency;
- затрагиваются protected или canonical artifacts;
- неизвестен baseline;
- не назначен обязательный Risk Profile;
- есть destructive risk;
- validation или stop conditions не определены.

Planning остаётся read-only и создаёт DRAFT.

## Executable Task

Task считается executable только когда:

- Task Brief достаточно полон;
- исходные условия проверяемы;
- обязательные human decisions записаны;
- role и permissions соответствуют задаче;
- execution authorization существует отдельно.

Наличие плана не делает Task executable автоматически.

## Lifecycle Without Premature State Machine

Концептуальная последовательность:

```text
PROPOSED
→ DEFINED
→ PLANNED, если требуется
→ AUTHORIZED
→ IN_PROGRESS
→ EXECUTED
→ VALIDATED
→ REVIEWED
→ CLOSED
```

Дополнительные terminal states:

- BLOCKED;
- UNKNOWN_BLOCKED;
- ABANDONED.

Это смысловая модель, а не обязательная runtime state machine.

## Interrupted Task

При прерывании фиксируются:

- завершённый stage;
- candidate state;
- изменённые файлы;
- findings;
- unknowns;
- проверки;
- одно следующее действие.

Resume начинается с проверки repository, branch, baseline и применимости Task Brief.

## Abandoned Task

Task может быть прекращена без реализации, если:

- value исчезла;
- направление изменилось;
- restart безопаснее recovery;
- найден более простой путь;
- cost превышает benefit.

Abandonment не является failure само по себе, если решение явно зафиксировано.

## Closure

Closure означает окончание данной Task.

Closure не означает автоматически:

- human acceptance;
- Commit;
- Push;
- Merge;
- Release.

Git decisions и lifecycle decisions принимаются отдельно.

## Критерий качественной Task

Качественная Task:

- имеет один результат;
- ограничена;
- проверяема;
- привязана к baseline;
- допускает безопасную остановку;
- не наследует legacy authority;
- не создаёт скрытое продолжение;
- может быть передана другому участнику через handoff.
