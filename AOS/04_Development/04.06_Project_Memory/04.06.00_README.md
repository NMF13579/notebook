# 04.06.00 Project Memory

## Назначение документа

Project Memory определяет, какие знания сохраняются для продолжения нового AOS и как они отделяются от временного context и legacy reference material.

## Legacy Reference Boundary

Материалы `NMF13579/AOS-FARM`, `AgentOS/AOS-1`, старые планы, отчёты, чаты и recovered artifacts используются только как `READ_ONLY_REFERENCE` с `authority: NONE` для нового проекта.

Из них разрешено извлекать:

- product intent;
- observable behavior;
- candidate contracts;
- повторяющиеся failure modes;
- доказанные lessons;
- полезные implementation ideas.

Из них нельзя автоматически переносить:

- active architecture;
- repository topology;
- Source of Truth;
- lifecycle или status;
- approvals;
- Risk Profiles;
- execution, Commit, Push, Merge или Release authorization;
- implementation readiness;
- незавершённые recovery chains;
- legacy complexity.

Любая идея из reference material становится частью нового AOS только после независимого анализа, явного описания в документации нового проекта и соответствующего human decision. Сходство с legacy не является основанием для принятия.

## Repository-First Factual State

Фактическое состояние реализации определяется новым repository и проверяемыми artifacts нового проекта.

При расхождении между handoff и repository проверяются:

- branch;
- HEAD;
- working tree;
- tracked artifacts;
- decision records;
- reports;
- test results.

Chat summary не переопределяет фактический repository state.

## One Source of Truth per Fact Class

Для каждого класса фактов существует один active Source of Truth.

Примеры:

- product contracts;
- architecture decisions;
- task definition;
- validation results;
- human decisions;
- implementation state;
- Git history.

Reference documents могут ссылаться на факт, но не создают конкурирующую active version.

## Durable Knowledge

Сохраняются:

- принятые contracts;
- architecture decisions нового проекта;
- significant Task Briefs;
- Stage Reports;
- Validation Reports;
- human decisions;
- unresolved findings;
- superseded relationships;
- confirmed lessons;
- current stop point;
- одно следующее действие.

## Non-Canonical Working Material

По умолчанию не являются canonical:

- черновые рассуждения;
- prompts;
- intermediate outputs;
- caches;
- local logs;
- speculative alternatives;
- полный текст чатов;
- legacy reports;
- recovered packages.

Они могут служить Evidence или reference только с явно ограниченной authority.

## Handoff

Минимальный handoff содержит:

- current objective;
- repository и project root;
- branch;
- baseline или candidate;
- completed stage;
- actual changes;
- checks;
- findings;
- unknowns;
- active boundaries;
- one next action.

Handoff должен различать repository facts и непроверенные claims.

## Resume Verification

Перед продолжением проверяются:

- repository;
- branch;
- baseline;
- candidate;
- artifacts;
- working tree;
- применимость Task Brief;
- наличие superseding decision.

Resume не начинается автоматически при изменившихся условиях.

## Superseded Artifacts

Superseded artifact должен указывать:

- чем заменён;
- почему не действует;
- какие части остаются reference;
- что не должно импортироваться дальше.

Устаревший документ не должен выглядеть как active Source of Truth.

## Findings and Unknowns

Findings и unknowns сохраняются до проверяемого closure.

Они не исчезают из-за:

- нового plan;
- смены чата;
- CI PASS;
- Commit;
- новой формулировки report.

## Lessons

Lesson становится durable rule через путь:

```text
observed problem
→ Evidence
→ root cause
→ candidate lesson
→ review
→ independent restatement in new project
```

Legacy lesson не принимается автоматически.

## Temporary Workspace

`/.aos-tmp/` используется только для disposable outputs.

Там нельзя хранить:

- approvals;
- Evidence;
- checkpoints;
- canonical files;
- final reports;
- durable decisions.

## Minimalism

На раннем этапе Project Memory использует:

- Markdown;
- Git;
- predictable paths;
- links;
- lightweight manifests, когда нужны.

Database или graph registry вводятся только при доказанной operational need.

## Критерий качественной Project Memory

Новый участник должен уметь:

- определить active state;
- отличить legacy reference от new canon;
- найти open findings;
- понять последнее human decision;
- продолжить с правильного next action;
- не восстановить несуществующую authority.
