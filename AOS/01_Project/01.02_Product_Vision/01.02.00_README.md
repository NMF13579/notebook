01.02 — Product Vision

Назначение

Этот документ описывает видение продукта AOS.

Он отвечает на вопросы:

* для кого создаётся AOS;
* какую пользовательскую проблему он должен решать;
* какую ценность пользователь получает;
* как должен выглядеть основной пользовательский путь;
* каким должен быть первый работающий product vertical slice;
* какие качества должны отличать AOS от обычного AI coding assistant;
* что не должно входить в первую версию продукта;
* по каким признакам можно понять, что AOS действительно полезен.

Этот документ не определяет детальную архитектуру, внутренние реализации или окончательный roadmap.

⸻

Видение

AOS должен стать понятной рабочей средой для создания и развития программных проектов с помощью AI-агентов.

Пользователь должен иметь возможность начать с идеи, постепенно уточнить её, получить ограниченную и понятную задачу, разрешить агенту выполнить изменение, увидеть результаты проверок и понять, что делать дальше.

AOS должен превращать хаотичный AI-assisted development в последовательный и воспроизводимый процесс, не заставляя пользователя изучать сложную систему Governance.

Основная идея продукта:

Пользователь должен управлять разработкой через понятные намерения и решения, а AOS должен преобразовывать их в контролируемую работу агентов и возвращать результат в форме, которую человек способен проверить.

⸻

Целевой пользователь

Основной предполагаемый пользователь AOS — человек, который создаёт цифровой продукт с помощью AI, но не хочет или не может самостоятельно управлять всей инженерной сложностью разработки.

К таким пользователям относятся:

* vibe coders;
* непрограммисты, создающие собственные приложения;
* solo builders;
* product owners;
* основатели небольших проектов;
* разработчики, активно использующие AI-агентов;
* небольшие команды без выделенной DevOps или Platform Engineering функции.

Primary target user должен быть уточнён позднее на основе реальных сценариев использования.

На текущем этапе AOS должен проектироваться так, чтобы им мог пользоваться человек без глубокого знания:

* Git;
* branching models;
* CI;
* architecture governance;
* agent orchestration;
* context management;
* software delivery lifecycle.

При этом продукт не должен скрывать существенные технические факты или риски.

⸻

Основная пользовательская проблема

Пользователь AI coding tools обычно сталкивается не с недостатком способности генерировать код, а с недостатком управляемости процесса.

Типичные проблемы:

* требования распределены между чатами и сообщениями;
* агент не понимает актуальный scope;
* новый prompt противоречит предыдущему;
* невозможно точно определить текущее состояние проекта;
* задачи расширяются во время выполнения;
* несколько агентов работают по разным предположениям;
* проверки выполняются непоследовательно;
* PASS воспринимается как готовность или approval;
* после перерыва трудно понять, где остановилась работа;
* пользователь не понимает, какое действие требуется дальше;
* документация и реальный код расходятся;
* восстановление контекста занимает больше времени, чем само изменение.

AOS должен уменьшить эту стоимость координации.

⸻

Основная ценность

AOS должен давать пользователю четыре главных результата.

1. Ясность

Пользователь понимает:

* что сейчас известно о проекте;
* что предлагается сделать;
* какие ограничения действуют;
* что изменится;
* что останется без изменений.

2. Контроль

Пользователь может явно:

* принять или изменить scope;
* разрешить выполнение;
* остановить работу;
* принять или отклонить результат;
* отдельно разрешить commit, push, merge или release.

3. Воспроизводимость

Другой агент или новая session должны иметь возможность продолжить работу без полного повторного чтения всей истории.

4. Доверие

Система должна честно различать:

* выполненное;
* проверенное;
* неизвестное;
* заблокированное;
* технически успешное;
* принятое человеком.

⸻

Product promise

AOS должен обеспечивать следующий пользовательский результат:

В любой момент пользователь может открыть проект и понять, что происходит, что уже сделано, что требует решения и какое одно действие следует выполнить дальше.

Дополнительное обещание:

Агент не должен самостоятельно расширять задачу, скрывать неизвестность или выдавать технический результат за человеческое решение.

⸻

Основной пользовательский путь

Базовый workflow должен быть коротким и понятным.

1. Пользователь описывает идею или проблему.
2. AOS помогает собрать необходимый контекст.
3. AOS формирует понятный scope задачи.
4. Пользователь подтверждает или корректирует scope.
5. Агент выполняет ограниченное изменение.
6. Запускаются предусмотренные проверки.
7. AOS показывает результат понятным языком.
8. Пользователь принимает решение.
9. AOS показывает одно следующее действие.

Этот workflow должен быть возможен вручную до появления сложной автоматизации.

⸻

Предполагаемый интерфейс

Наиболее естественный интерфейс AOS — chat-first.

Пользователь должен взаимодействовать с системой через обычный язык, а не через сложные формы и таблицы.

При этом chat не должен быть единственным представлением состояния.

AOS должен уметь показывать:

* текущее состояние проекта;
* активную задачу;
* scope;
* найденные риски;
* проверки;
* результат;
* открытые решения;
* историю изменений;
* следующее действие.

Возможная простая поверхность команд:

/help
/analyze
/plan
/execute
/validate
/status
/next
/details
/stop

Команды являются только возможным UX pattern. Окончательный интерфейс должен определяться после проверки первого пользовательского сценария.

⸻

Принцип progressive disclosure

AOS должен быть простым на поверхности и подробным по запросу.

По умолчанию пользователь должен видеть:

* краткий статус;
* главный риск;
* одно необходимое решение;
* одно следующее действие.

Подробности должны открываться отдельно:

* полный Task Brief;
* diff;
* validation results;
* Evidence;
* architecture notes;
* source references;
* execution logs.

Пользователь не должен быть вынужден читать длинный технический отчёт, чтобы понять, успешно ли завершена задача.

⸻

Восстановление контекста

Одна из ключевых функций AOS — ответ на вопрос:

На чём мы остановились?

При возвращении к проекту пользователь должен видеть:

* последний завершённый этап;
* текущую активную задачу;
* последний известный результат;
* незакрытые findings;
* ожидаемое решение человека;
* одно следующее действие.

Система не должна требовать повторного чтения всей истории чатов.

⸻

Bounded scope

Перед выполнением изменения AOS должен сформировать ограниченный scope.

Пользователь должен понимать:

* какие файлы или области могут быть изменены;
* какие области запрещены;
* какой результат ожидается;
* какие проверки должны быть выполнены;
* при каких условиях агент обязан остановиться.

Scope не должен расширяться автоматически.

Если во время работы обнаруживается новая задача, она должна быть отделена от текущей.

⸻

Один следующий шаг

AOS должен устранять ситуацию, когда после каждого отчёта пользователь получает длинный список равнозначных рекомендаций.

В нормальном состоянии система должна показывать одно действие:

следующая задача
или
требуемое решение
или
необходимый источник
или
исправление конкретного finding

Если существует конфликт нескольких возможных действий, AOS должен показать конфликт, а не выбирать путь скрытно.

⸻

Отделение результата от решения

AOS должен строго различать:

* агент выполнил изменение;
* проверки прошли;
* Evidence собрано;
* review завершён;
* человек принял результат.

Технический PASS не означает принятие человеком.

Это различие должно быть видно в пользовательском интерфейсе без необходимости читать внутренние документы.

⸻

Первый product vertical slice

Первый vertical slice должен доказать пользовательскую ценность, а не готовность управляющей инфраструктуры.

Рекомендуемый сценарий:

пользователь описывает небольшое изменение существующего проекта
→ AOS помогает уточнить задачу
→ формирует bounded scope
→ coding agent выполняет изменение
→ запускаются проверки
→ пользователь получает понятный результат
→ система показывает одно следующее действие

Vertical slice должен охватывать полный путь от пользовательского намерения до review результата.

Он не должен начинаться с:

* universal registry;
* full Control Plane;
* autonomous loop;
* persistent task database;
* Runtime Enforcement;
* сложной multi-agent orchestration;
* merge authorization machinery;
* dashboard;
* SaaS infrastructure.

⸻

Минимальная версия продукта

Минимальная версия AOS должна уметь:

1. принять пользовательское намерение;
2. собрать минимально необходимый контекст;
3. сформировать понятную ограниченную задачу;
4. подготовить инструкцию coding agent;
5. получить результат выполнения;
6. показать проверки и неизвестные;
7. сформировать короткий review;
8. показать одно следующее действие;
9. сохранить контекст для продолжения.

Часть этих операций может первоначально выполняться вручную или полуавтоматически.

MVP определяется пользовательским результатом, а не уровнем автоматизации.

⸻

Что не входит в первую версию

Первая версия AOS не должна требовать:

* собственного persistent Control Plane;
* универсального registry;
* базы данных состояний;
* RAG или vector database;
* автономного execution loop;
* полного runtime enforcement;
* сложной cryptographic authorization system;
* обязательного SaaS backend;
* сложной системы ролей;
* автоматического исправления всех findings;
* multi-repository orchestration;
* автоматического merge или release;
* поддержки всех типов проектов.

Эти возможности могут появиться позже, если их необходимость подтверждена реальными сценариями.

⸻

Product Runtime и Development Factory

Product Runtime должен быть полезным пользователю независимо от готовности Development Factory.

Development Factory может помогать:

* готовить задачи;
* выбирать агента;
* выполнять validation;
* сохранять состояние;
* автоматизировать повторяющиеся действия.

Но пользовательская ценность не должна исчезать, если эти механизмы временно отключены.

Правило:

Продукт должен работать с минимальными строительными лесами.
Advanced Control Layer должен быть заменяемым и отключаемым.

⸻

Роль автоматизации

Автоматизация должна уменьшать реально наблюдаемую ручную работу.

Она не должна добавляться только потому, что действие теоретически можно автоматизировать.

Функция автоматизируется, если:

* она повторялась в нескольких реальных циклах;
* ручной процесс понятен;
* известны входы и выходы;
* известны типовые ошибки;
* автоматизация сокращает время или риск;
* существует безопасный способ её отключить.

⸻

Product principles

Понятность важнее полноты

Лучше показать пользователю пять важных фактов, чем пятьдесят полей состояния.

Human control без постоянной бюрократии

Human decision нужен там, где он действительно влияет на scope, риск или необратимые действия.

Product value раньше infrastructure maturity

Первый работающий пользовательский цикл важнее готовности всего внутреннего Control Plane.

Documentation supports product

Документы должны помогать строить и понимать продукт, а не становиться самостоятельной системой, блокирующей работу.

Honest state

AOS должен показывать UNKNOWN, NOT_RUN, BLOCKED и findings без попытки скрыть их за общим положительным статусом.

Safe by default

Опасные и необратимые действия не выполняются автоматически.

Replaceable internals

Routing, registry, storage, model provider и automation mechanisms должны по возможности быть заменяемыми.

⸻

Отличие от обычного AI coding assistant

Обычный coding assistant в основном отвечает на prompt и создаёт изменение.

AOS должен дополнительно обеспечивать:

* связь с состоянием проекта;
* сохранение scope;
* явные границы действий;
* разделение stages;
* validation;
* traceability;
* session continuity;
* human decision boundaries;
* одно следующее действие.

AOS — это не «более умная модель», а более управляемая система работы человека и AI.

⸻

Отличие от project management system

AOS не должен превращаться в обычный task tracker.

Задачи, статусы и история нужны только для поддержки реального development workflow.

Главный объект AOS — не карточка задачи, а контролируемый путь:

намерение
→ изменение
→ проверка
→ решение

⸻

Отличие от autonomous development platform

AOS не должен стремиться полностью исключить человека.

Автономность допустима внутри заранее разрешённых безопасных границ.

Решения о:

* scope;
* существенной архитектуре;
* protected changes;
* destructive operations;
* commit;
* push;
* merge;
* release;

остаются явными human decisions, пока человек отдельно не установит другую политику.

⸻

Критерии продуктовой ценности

AOS полезен, если пользователь:

* быстрее понимает текущее состояние проекта;
* реже теряет контекст между sessions;
* реже получает неожиданные изменения;
* тратит меньше времени на повторное объяснение задачи;
* понимает, какие проверки выполнены;
* видит различие между техническим результатом и approval;
* может продолжить работу с другим агентом;
* получает одно понятное следующее действие;
* быстрее доводит небольшие изменения до завершения.

⸻

Возможные product metrics

На ранних этапах можно измерять:

* время от идеи до bounded task;
* время восстановления контекста после перерыва;
* количество scope violations;
* количество повторных объяснений задачи;
* долю задач с понятным результатом validation;
* количество manual recovery loops;
* количество случаев ложного PASS;
* долю задач, которые другой агент может продолжить без повторного discovery;
* время пользователя на review;
* количество завершённых vertical slices.

Metrics не являются approval и не заменяют qualitative user feedback.

⸻

Условия успеха первого продукта

Первый product vertical slice считается успешным, если реальный пользователь может:

1. описать небольшую задачу;
2. понять предложенный scope;
3. разрешить выполнение;
4. получить контролируемое изменение;
5. увидеть результат проверок;
6. понять оставшиеся риски;
7. принять или отклонить результат;
8. понять, что делать дальше.

Для этого не требуется полная автоматизация всех этапов.

⸻

Основные риски продукта

Риск чрезмерной сложности

AOS может повторить ошибку AOS-FARM и превратить простой workflow в тяжёлую систему управления.

Риск ложной простоты

Слишком простой интерфейс может скрыть важные риски и техническое состояние.

Риск подмены продукта инфраструктурой

Команда может снова начать улучшать registry, routing и Governance вместо пользовательского сценария.

Риск чрезмерной автоматизации

Автоматизация может закрепить ещё неустойчивый workflow.

Риск потери human authority

Удобство может привести к неявному выполнению действий, которые должны оставаться решениями человека.

Риск отсутствия measurable value

Большое количество документов и статусов может не давать реальной экономии времени пользователю.
