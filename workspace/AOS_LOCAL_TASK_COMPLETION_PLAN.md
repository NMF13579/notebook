## 1. Результат и границы самостоятельности

Один исходный пользовательский запрос и bounded допуск → подготовка входа →
исследование → исправление → проверка → обычные corrections при необходимости →
независимое финальное ревью → изменённый локальный проект и K4.
Между исходным допуском и итогом человек не управляет техническими переходами.

В общий объём входят необходимые изменения существующих consumers AOS,
исправления подготовки, тестов и реализации, повторные проверки и устранение
существенных findings reviewer. Внутренние этапы ниже не являются Human Gates.

| Кто | Работа в этом результате |
|---|---|
| Текущий App-агент | Понимает запрос, выбирает проверки, исследует причину, предлагает новые решения, организует исполнение и финальное ревью |
| AOS | Сохраняет вход и identities; принимает решения агента через реальные consumers; проверяет scope/current authority; ведёт state, историю и бюджет; допускает correction; проверяет candidate и формирует K4 |
| Человек | Даёт один исходный допуск; решает только material boundary; принимает конечный результат |

Успех не доказывает внутренний универсальный AI-диагност AOS, native trusted
capture, автоматический resume после остановки host, все 13 семейств или HD-28.
Полный принятый состав ядра сохраняется; эта задача закрывает конкретный путь.

## 3. Полезная задача и отдельная проверка correction

Для запуска нужен один конкретный запрос и известный локальный предмет.
Чтобы не требовать отдельного выбора демонстрации, предлагаемый запрос по умолчанию:

> В изолированной копии текущего first_core проверь обработку локального входа
> задачи и исправь один новый воспроизводимый дефект, нарушающий существующий
> контракт. Сохрани остальные файлы и верни проверенный проект с объяснением
> исходной ошибки и исправленного поведения.

Граница поиска: текущий local Python entry и его непосредственные readers;
не общий аудит AOS. Дефект должен быть наблюдаемым в исходном candidate, без
искусственного внесения, повторения исторических R8/R9 ошибок или нового требования.
Агент выбирает конкретный дефект и oracle по Evidence внутри этого задания.
Если подходящий дефект не обнаружен или нужен выход за профиль — точный неполный
результат; не подменять полезную задачу synthetic fixture ради PASS.
Другой пользовательский Python-проект может заменить этот предмет при исходном
запуске после задания его точного пути и достаточного запроса, не молча.

Полезный проект — отдельная копия; итогом является эта проверенная копия и diff.
Автоматическое применение её изменений к исходному проекту не подразумевается.
Она отделена от исполняющего AOS kernel. Проверенный kernel фиксируется до
полезного journey; его изменение требует новой привязки и затронутых проверок.

Отдельный controlled case проверяет повторную correction:
реальный FAIL → первое допущенное исправление → свежий FAIL → новое различающее
Evidence/уточнённый диагноз → второе допущенное исправление → PASS → K4.
Здесь искусственный дефект и намеренно недостаточная первая correction обозначены
как fixture. Это доказательство стыка, не самостоятельного поиска причины AOS.

## 4. Выполнение внутри одной задачи

### Шаг 1. Preflight и единый рабочий предел

- Сверить source/runtime, current state, ownership и точные пути; сохранить drift,
  чужую работу и историю. Проверить отсутствие конфликтующего effectful owner.
- Зафиксировать один текущий task record, критерии, исходную authority и общий
  конечный бюджет. Исторический расход не сбрасывать и не считать новым ресурсом.
- Проверить одну конфигурацию среды на disposable fixture до полезного effect:
  необходимые записи разрешены, посторонние запрещены; network запрещён.
  Внутренний checker наследует parent scope; внешний observer — deny-write.
- Отказ automatic approval не обходить. Исправить покрытую ошибку подготовки
  самостоятельно при доказанном отсутствии эффекта; UNKNOWN сначала reconcile.

### Шаг 2. Закрыть повторную correction в существующем AOS

Подтверждённые места: `correction.continue_run` паркует задачу после неудачной
завершённой correction; `pilot.action` фиксирует одну generation; manual grant
связан с exact request/action. Изменить необходимые consumers этих данных.

- Принимать поздний новый диагноз и replacement от текущего supervising agent
  после свежего failing check, внутри той же product task и исходного parent.
- Разделить неизменный человеческий parent scope и выводимый controller узкий
  action/envelope по существующим C-006A/C-009/C-009A; generated action не является
  новым решением человека. Не ослаблять exact hash/state/freshness проверки.
- Каждая correction получает новые candidate/action/generation bindings и
  одноразовый admission. Сохранить прежние операции, результаты, ledger и бюджет.
- Реализовать допустимый выход из WAIT_EVIDENCE после нового достаточного
  Evidence. Само повторение команды или новый каталог такой возможности не даёт.
- Сохранить исходный запрос, критерии, scope, oracle identity и protected files.
  Изменение oracle требует объяснённого дефекта проверки, нового binding и
  повторной проверки исходного поведения; подгонка проверки под patch запрещена.
- Status/Next/Details отражают последнюю попытку, вклад предыдущих, blockers и
  ровно одно допустимое действие. Диагностический PASS не закрывает acceptance.
- Старые принятые records остаются читаемыми; новый consumer не возобновляет
  terminal task и не использует её grant для нового эффекта.

HOW выбирает агент. Новый controller, scheduler, adapter или authority service
не входит в решение. Если существующие принятые contracts не позволяют нужную
семантику, вернуть exact conflict; не исправлять owner под реализацию.

### Шаг 3. Проверить стыки и выполнить полезный путь

Сначала доказать controlled повторную correction через реальные consumers.
Затем провести полезную задачу от сохранённого исходного запроса через публичный
entry до результата. Агент не просит разрешения на каждую диагностику, исправление,
внутренний запуск или новую проверку внутри исходных границ.

Не использовать test helpers для подготовки полезной задачи. Не выполнять patch
в обход AOS и затем не приписывать эффект core. Не требовать искусственной неудачи
первого решения в полезной задаче: это уже проверено отдельным controlled case.

### Шаг 4. Проверить конечный предмет и завершить

- Выполнить affected checks после corrections. Изменение admission/state и
  shared consumers требует полной регрессии на конечном source candidate;
  разбиение набора допускается с единым manifest и явной полнотой покрытия.
- Заморозить source и Evidence. Свежий read-only reviewer проверяет критерии,
  реальные consumers и отсутствие подмены работы AOS действиями driver.
- Reviewer не исправляет subject. Executor устраняет material findings внутри
  того же задания; затем affected checks, необходимая регрессия и свежее ревью.
- Вернуть изменённый полезный проект, diff, K4, исходы критериев, ограничения,
  расход и количество фактических вмешательств человека. Затем STOP.

## 5. Обязательные проверки результата

| Случай | Что должно наблюдаться |
|---|---|
| Полезная задача | Новый реальный дефект; request сохранён до решения; настоящий core effect; свежие acceptance/preservation/FINAL; доступный изменённый проект |
| Повторная correction | Два разных допущенных решения после разных Evidence в одной task; первая неудача сохранена; вторая проверена; общий ledger без reset |
| Нет новых оснований | Прежний patch/диагноз не повторяется как прогресс; точный WAIT_EVIDENCE |
| Stale/mixed input | Старые candidate, solution, state, diagnosis, grant, envelope и Evidence отвергаются без нового эффекта |
| Authority | Новые пути/операции, истёкший или отозванный parent, превышенный бюджет, replay envelope не дают effect; generated NOT_GRANTED не становится ALLOW |
| Неизвестный эффект | Reconciliation до retry; без дублирования, нового parent или очистки истории |
| Проверка неверна/неполна | Wrong reader, missing check, изменённый oracle, diagnostic PASS и worker text не дают ложного acceptance |
| Сохранность и завершение | Protected inputs неизменны; пропущенный следующий check/child не даёт completion; terminal replay не пишет и не возобновляет task |
| Legacy | Принятые records R1–R9 не переписаны и не переинтерпретированы как свежая authority |
| Участие человека | После исходного допуска не было технических «продолжай»; если был material вопрос, он учтён и claim ограничен |

Связать результаты с применимыми SC-T/контрактами по смыслу проверенного случая.
Runtime каждого required случая имеет собственный исход; счёт тестов не заменяет
покрытие. Native/host interruption cases остаются NOT_RUN в этом scope, не N/A
для общей готовности ядра. Controlled case с одной неудачной correction не
доказывает полный D0–D5 или правило двух неудачных corrections в реальной задаче.

## 7. Остановки и запуск

Зависимое действие останавливается при material изменении scope/authority,
защищённой границы, отсутствующем существенном решении, опасном неустранённом
UNKNOWN, недоступном обязательном ресурсе, исчерпании бюджета/срока или повторе без
нового различающего Evidence. Независимая покрытая работа продолжается, где это
безопасно. Обычный FAIL и исправимый finding сами по себе не требуют человека.

Если host прерван, сохранить checkpoint; автоматический wake/resume этим планом
не обещается и не испытывается. Ручное восстановление не выдавать за автономное.

Для запуска достаточно одного явного решения выполнить этот план с границами §6
и задачей по умолчанию из §3 либо с конкретным заменяющим запросом и project path.
Дальнейшие согласования внутренних стадий, обычных corrections и проверки итога
не нужны. Текущий запрос пользователя поручает только составить план.
