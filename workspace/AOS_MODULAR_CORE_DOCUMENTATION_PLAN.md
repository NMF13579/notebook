# AOS — план документации модульного ядра

Дата: 2026-09-13. Статус: документальные результаты этапов 1–8 подготовлены и проверены; принятие точного состава MOD-DEC-01 ожидает ответа пользователя. Полное закрытие плана до этого решения не заявляется.

**Цель:** сформировать согласованную проектную документацию небольшого обязательного ядра AOS и включённых модулей с полными, конечными контрактами поведения и понятными правилами сопровождения.

**Основание:** пользователь согласился с предложением полностью описать выбранные фичи, сохранив минимальный обязательный набор для одного завершённого рабочего цикла, и запросил план. Это подтверждает направление модульности; приведённое ниже распределение конкретных возможностей остаётся предложением до решения по составу.

**Подход:** существующие семь документов сохраняют владельцев фактов. Feature family не равна одному неделимому компоненту: обязательная гарантия может относиться к ядру, а дополнительные сценарии той же фичи — к модулю. Полное ТЗ сохраняет все согласованные возможности, даже если часть не обязательна для каждой задачи.

**Формат:** Markdown и таблицы контрактов, примеры входов/результатов и документальные сценарии. Язык программирования, библиотеки и техническое устройство хранения не выбираются.

**Исполнителю:** после отдельного запуска работать последовательно по этапам, применяя `superpowers:executing-plans` с приоритетом правил проекта для документационных задач. Каждый этап имеет проверяемый результат; создание кода, пилот и запуск runtime не являются шагами этого плана.

## 1. Границы и исходное состояние

- Создание плана завершено. Текущая команда пользователя разрешает выполнение документационных этапов в перечисленных путях; принятие новых продуктовых решений не подразумевается.
- Рабочее дерево: `notebook/.worktrees/aos-development-loop`, ветка `work/aos-development-loop`; наблюдавшийся baseline — `97ee1e3e71b47c211b3567d8b4b052e8d5e44b45`. При запуске проверить актуальное состояние заново, сохранить посторонние изменения.
- [Core](../docs/00_Core.md) сохраняет роль knowledge repository, Minimal Safety Floor и `implementation_repository: UNASSIGNED`.
- [Product](../docs/01_Product.md) содержит product journeys и предложение MVP; [Features](../docs/06_Features.md) содержит 30 семейств с частичными решениями для X1 и общими шаблонными полями. Полные ТЗ ещё предстоит сформировать.
- [Architecture](../docs/02_Architecture.md) владеет архитектурными контрактами; [Development](../docs/03_Development.md) — workflow, проверками и завершением.
- Существующая модель петли с D0…D5, отдельными task/run states, ограниченными полномочиями и доказуемым завершением сохраняется по существу.
- Без runtime implementation, scaffold, product tests, CI configuration, deployment, пилота, установки зависимостей или выбора implementation repository. Проверочные сценарии описываются, их будущая исполнимость не выдаётся за выполненные тесты.
- Без Commit, Push, Merge, Release, удаления веток/деревьев и изменения ранее замороженного пакета `AOS/`. Авторизации Git для предыдущего коммита не распространяются на этот план.

### Этап 7. Проверить цепь на документационных сценариях

**Пути:** сценарии приёмки в `docs/06_Features.md`, cross-feature проверки и краткий итог в `docs/03_Development.md`. Без отдельного runtime harness.

Для каждой строки проследить actor/input → владельцев contracts → разрешённые действия → результат/состояние → следующий шаг и требуемые Evidence. Статус документального разбора хранить отдельно от будущего runtime test status.

| Сценарий | Ожидаемый документальный исход |
|---|---|
| Простая задача при отсутствии необязательных модулей | Основной цикл определён и не требует скрытого CI, индекса, установщика или библиотеки patterns |
| Неполное намерение | Существенные вопросы видимы; требования и полномочия не выдумываются |
| Причина не найдена либо наблюдатель ненадёжен | Расширение диагностики; нет необоснованной mutation |

## 5. Критерии завершения и контроль объёма

1. Есть определённый основной цикл, точный состав обязательных возможностей и включённых модулей.
2. Все согласованные возможности включённых фич имеют полные конечные ТЗ; обязательность для каждого запуска выделена отдельно.
3. Для каждой зависимости известны назначение и условие необходимости. Необъяснённых циклов обязательного запуска/владения нет.
4. Владельцы состояния, rules совместимости, failure/recovery и границы отключения определены.
5. Каждое существенное требование связано с проверяемым результатом и отрицательным сценарием; межмодульные сценарии разобраны.
6. Состав не растёт автоматически из-за навигационных ссылок, нового finding или выбранного способа реализации. Новое семейство, внешний сервис, платформа или полномочие требует явного решения по scope.
7. Сохраняются Minimal Safety Floor, текущие item-level решения в их области и семь canonical владельцев. Нельзя записать принятие конкретного состава только на основании согласия с общим принципом модульности.
8. Runtime implementation, runtime tests, пилот и Git для новых изменений остаются NOT_RUN.

Объём работы оценивается по завершённым контрактам и закрытым материальным пробелам, а не по страницам. Сроки и стоимость реализации не заявляются без сведений о платформе и реализационных решениях. План запущен командой пользователя «Выполни план». Следующий bounded шаг — решение MOD-DEC-01 по подготовленной матрице, затем отражение только принятого решения в его exact scope. Повторного проектирования общего принципа модульности не требуется.
