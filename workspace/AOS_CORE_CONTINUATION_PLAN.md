- Составить компактное соответствие: обязательство текущего пути → реализация →

  supervised исполнение и недоказанные recovery/host гарантии.
- Исправить устаревшие описания текущего состояния в first_core README/CONTRACTS,
  если они мешают использованию: например, историческое «21 файл» при текущих 23
  и старые глобальные NOT_RUN. Не повышать полноту продукта по факту этой правки.

Готово: исполнитель понимает действительный следующий шаг без нового интервью.
Новый product/architecture конфликт возвращается точно; обычный HOW выбирается агентом.

### Фаза 2. Использовать одну проверенную среду

- Перенести исправленную схему профиля run-002 на новый разрешённый scratch root;
  повторно привязать пути и команды. Не копировать старую authority или root буквально.
- Локально проверить необходимые записи/публикацию и запрет посторонних записей
  на disposable fixture до основного journey. Network остаётся запрещённым.
- Сохранить рабочую конфигурацию для следующих внутренних попыток. При ошибке
  подготовки и доказанном отсутствии эффекта исправлять её самостоятельно;
  новую попытку помещать в новый подкаталог, сохраняя предыдущую историю.
- При неопределённом эффекте сначала reconciliation; новый каталог не разрешает
  дублировать эффект, сбрасывать lock/ledger или скрывать UNKNOWN.

Готово: setup проверен до полезного запуска. Вложенный sandbox не предполагать
работающим: фиксированный внутренний checker наследует parent write scope;
отдельный финальный observer запускается с deny-write. Ограничение видно в отчёте.

### Фаза 3. Реализовать K4 и необходимые стыки supervised пути

- Реализовать CLI Status / Next / Details на текущем durable state: понятный
  результат, blocker, freshness, ограничения и ровно одно допустимое действие.
- Собрать compact review: критерий → фактическая проверка/Evidence → результат,
  exact candidate и действие человека. PASS, generated text и queue ACK не ACCEPT.
- Передавать candidate/task/state identities через реальные consumers. Missing,
  stale, mixed-version или malformed данные не дают ложного PASS или разрешения.
- Связать результат исполнения, проверок и correction с представлением K4;
  закрыть необходимые пробелы внутри выбранных core contracts. Не имитировать
  отсутствующий обязательный consumer фиктивным успешным ответом.
- Запись решения человека сохраняет источник и exact subject. Synthetic fixtures
  проверяют интерфейс, но не доказывают native capture. Недоказанное показывать явно.

Готово: работающий сквозной supervised сценарий завершается проверяемым review,
а статус корректно отражает и успешные, и заблокированные/неполные результаты.
Действующие contracts C-006A/C-009/C-009A, V3, C-015/C-016 сохраняются.

### Фаза 4. Проверить целый результат и завершить задачу

- Positive: согласованные inputs → реальные core consumers → effect/check →
  correction при controlled defect → следующий child → актуальный status/review.
  Простая файловая цель подходит как oracle, но не доказывает сборку любого проекта.
- Negative: неверный результат/reader; stale candidate/Evidence/decision;
  missing required check; UNKNOWN effect; diagnostic PASS вместо acceptance;
  пропущенное продолжение; попытка выдать PASS или worker text за Human ACCEPT.
- Связать проверки с применимыми SC-T, особенно SC-T03/04/09/11/14/21/22 и
  проверяемыми queue/state стыками SC-T23…26. Для каждого required случая дать
  отдельный исход. Пропущенный host/recovery case сохраняет NOT_RUN и ограничивает
  соответствующий общий claim; его нельзя объявить N/A ради зелёного итога.
- Проверить регрессию конечного source candidate. Повторять affected checks после
  коррекций; полный набор — когда изменение/неясный impact этого требует.
- Заморозить candidate и дать свежему read-only reviewer исходные критерии,
  код и Evidence. Он не исправляет предмет. Material findings исправляет executor
  в той же задаче; затем затронутые проверки и свежая финальная проверка.
- Итог: что работает в supervised boundary, что осталось недоказанным,
  оставшиеся дефекты, расход бюджета и одно действие человека. STOP.

Критерий завершения этой задачи: работающий заявленный supervised путь, отсутствие
несовместимых с ним material findings, фактически выполненные required проверки
для этого профиля и честный остаток. При блокере — точный неполный результат;
«K4 implemented» не считается доказательством готовности всего ядра.
