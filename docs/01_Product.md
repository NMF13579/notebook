# 01 — Продукт

## 1. Граница статуса

Документ является принятым product baseline. Подтверждённые product facts имеют fact-class-scoped authority; разделы, помеченные `PROPOSAL`, `OPTIONAL` или `UNDECIDED`, не становятся принятыми решениями. Ни один раздел не разрешает implementation.

## 2. Проблема продукта

Непрограммист может описать желаемый результат, но не способен надёжно контролировать каждую repository operation, permission, test и implementation detail. AI-агенты могут потерять product intent, расширить scope, завысить completion или создать maintenance debt.

| ID | Проблема | Последствие |
|---|---|---|
| `P-001` | State распределён между chats, worktrees, reports и decisions | Потеря context и повторный planning |
| `P-002` | Неясно, где остановились | Unsafe assumptions on resume |
| `P-003` | Free-form request превращается в implementation assumptions | Wrong feature/problem fit |
| `P-004` | Scope расширяется скрыто | Contamination и difficult rollback |
| `P-005` | PASS/Evidence/readiness смешиваются с approval | False completion |
| `P-006` | Implementation и validation смешиваются | Self-validation и hidden fixes |
| `P-007` | Git operations считаются одним действием | Unauthorized publication |
| `P-008` | Legacy содержит ценность и obsolete complexity | Wrong target architecture |
| `P-009` | Exhaustive extraction имеет low ROI | Product work delayed |
| `P-010` | Documentation дублирует fact owners | Drift и unclear SoT |
| `P-011` | Feature descriptions shallow | Agent invents behavior/tests |
| `P-012` | Install/update ownership unclear | User data loss |
| `P-013` | Model/agent routing lacks measurements | Cost/quality unpredictability |
| `P-014` | Automation precedes manual flow | Bad process automated |
| `P-015` | Blockers/next action не понятны | Dependence on specialists |

## 3. Обещание продукта

```text
пользователь формулирует проблему или идею
→ AOS делает понимание и uncertainty видимыми
→ создаёт bounded, reviewable development cycle
→ показывает Evidence и remaining risk
→ человек принимает решение
→ работа безопасно возобновляется
```

## 4. Пользователи и JTBD

### Непрограммист / domain expert

- объяснить problem обычным языком;
- увидеть understood/missing/assumed;
- утвердить product intent и high-risk actions;
- оценить user-visible result без чтения всего кода;
- resume after interruption.

### Vibe-coder / product builder

- получить safe default workflow;
- предотвращать scope drift и false completion;
- менять coding agents без переписывания rules;
- сохранять maintainable project knowledge.

### Agent / implementer / reviewer

- получить bounded context и one task;
- знать allowed/forbidden changes;
- связать acceptance criteria с Evidence;
- сообщить uncertainty/remaining risk;
- оставить recoverable handoff.

### Maintainer / operator

- inspect current state/drift;
- понимать ownership/rationale;
- reproduce checks;
- отличать historical report от current result.

### Примеры проектов пользователей AOS

В текущем интервью пользователь назвал три примера систем, которые хочет
создавать с помощью AOS:

- система учёта оборудования;
- система управления графиками работы;
- RAG-система: помощник ищет информацию в документах пользователя и отвечает
  на вопросы со ссылками на источники; пользователь подтвердил это понимание.

Это примеры целевых пользовательских проектов для проработки возможностей
интервью и подготовки требований. Они не являются отдельными модулями самого
AOS, исчерпывающим списком поддерживаемых предметных областей или поручением
реализовать эти системы сейчас. Упоминание RAG-системы как результата работы
пользователя не выбирает внутренний RAG/index FTR-017 в составе AOS. Конкретные
детали процессов, данные и критерии каждого примера ещё не определены.
Работоспособность AOS на этих примерах — NOT_RUN.

Текущая документационная работа проектирует сам AOS. Сначала соответствующие
возможности AOS должны быть утверждены, реализованы и практически проверены;
только затем на их основе создаются отдельные пользовательские проекты. Проверка
методологии на примерах выше не меняет этот порядок и не запускает их разработку.

Пользователь также подтвердил сводку пяти ответов: разработка ведётся с AOS,
ручные правки программиста разрешены, перед продолжением они проверяются с
уточнением намерения при расхождении с ТЗ, решения задаёт один ответственный
человек, три названных системы являются примерами целевых проектов. Сводка
подтверждает эти требования, а не runtime-готовность или весь пакет документации.

## 5. Адаптивный intake

### Основа методологии интервью

Пользователь принял методологию сбора ТЗ AOS-FARM как основу для адаптации
в AOS, с дополнениями из AgentOS по сохранению ответов и выявлению пробелов.
Простыми словами: агент использует готовые способы разбирать задачу и проверять
полноту, а не составляет интервью заново для каждого проекта. Основу составляют
разбор жизненного цикла значимых объектов и пошаговый разбор сценариев;
остальные методы применяются к соответствующим пробелам.

Принятые в текущем интервью правила имеют приоритет: понятный язык, один вопрос
за раз, сводка после пяти ответов, отсутствие повторов уже раскрытых тем,
возвращение к конфликтам в конце, отдельное утверждение ТЗ и отдельная команда
на разработку. Подтверждённые решения пользователя не превращаются обратно
в неподтверждённые подсказки. Режимы и ограничения reference-пакетов не
переносятся автоматически. [Источники и ограничения адаптации](05_Reference.md#interview-methodology-sources)
сохраняют provenance; выбор основы не означает завершения адаптации или
проверки её исполнения агентом.

### Понятное интервью и аудитория документации

В текущем интервью по устранению пробелов документации пользователь назвал первый
желаемый реальный сценарий: проведение интервью и формирование технического
задания. Уточнение от 2026-09-14: диалог должен быть максимально понятен
непрограммисту; собранная документация должна быть понятна как агенту, так и
программисту. Непрограммист может в любой момент попросить агента объяснить
содержание документации простыми словами.

Для первой версии сценария интервью пользователь выбрал привычный чат с агентом:
AOS помогает вести диалог и собирать документацию в этой среде. Отдельное окно
или приложение AOS для проведения интервью не требуется. Выбор относится к
поверхности интервью; способ подключения AOS этим ответом не определён.
Хранение результатов уточнено ниже. Он не выбирает интерфейсы остальных
возможностей продукта и не меняет disposition FTR-028.

В качестве желаемых инструментов и сред пользователь назвал Codex, Claude Code,
VS Code, Antigravity и Cursor. Это перечень целевых сред, а не подтверждение
существующей совместимости AOS. Последующим подтверждением пользователь уточнил:
AOS изначально проектируется независимо от конкретного агента. Общие процессы,
документы и правила не привязываются к среде; подключение другой среды не должно
требовать переделки ядра. Codex выбран для первой проверки AOS, а не как
ограничение продукта. Claude Code остаётся следующим выбранным направлением;
сроки подключения остальных сред пока не определены.

Различия сред обслуживаются адаптерами по разделу «Адаптеры агентов» в
[Architecture](02_Architecture.md). Возможность автономной работы проверяется
отдельно для каждой среды: общие инструкции сами по себе её не доказывают.
Для VS Code предстоит определить используемого внутри редактора агента.
Конкретные варианты запуска и интеграции пока не определены. Независимость
общих документов не доказывает переносимость незавершённого исполнения:
порядок передачи активной работы между агентами ещё предстоит уточнить.

При возобновлении прерванного интервью, в том числе в новом чате Codex, агент
должен самостоятельно прочитать сохранённые материалы проекта и продолжить
с ближайшего неотвеченного вопроса. Пользователь не должен повторно пересказывать
уже сохранённые ответы и решения. Обязательное напоминание перед продолжением
этим ответом не выбрано. Порядок действий при отсутствии, недоступности или
противоречии сохранённых материалов остаётся открытым вопросом.

По просьбе пользователя остановиться, например «на сегодня достаточно»,
агент сохраняет текущее состояние интервью и останавливается, не требуя
завершить обсуждаемую тему. При ошибке сохранения действует правило явного
сообщения об ошибке; продолжение после перерыва использует сохранённые записи.

Для первой версии пользователь выбрал одного ответственного человека, который
отвечает на вопросы интервью, задаёт требования и принимает решения. Совместное
интервью нескольких участников и разрешение разногласий между ними не входят
в этот scope. Это ограничение участников интервью и принятия решений в AOS,
а не числа пользователей создаваемой системы; ручная работа программиста с
кодом остаётся допустимой по правилам ниже.

Агент задаёт по одному вопросу за раз и добавляет пример, когда он помогает
понять вопрос. Если один ответ раскрывает несколько тем, агент учитывает их
все и не задаёт повторно вопросы, на которые уже получен ответ. Оставшиеся
пробелы и неоднозначности обрабатываются по общим правилам интервью.
Вопросы интервью формулируются обычным языком. Если вопрос непонятен, агент
объясняет его контекст и приводит понятный пример; технические термины, когда
они необходимы, поясняются. От пользователя не требуется знание программирования
для описания своей задачи и желаемого результата.

Агент самостоятельно выявляет важные для конкретной системы условия, даже
если пользователь их не упомянул: права доступа, одновременную нагрузку,
сохранность данных и поведение при сбоях. Он задаёт вопросы простыми словами,
на примерах задачи, объясняет последствия и помогает выбрать решение.
Пользователь определяет правила работы; агент переводит их в технические
требования. Принятие этого порядка не выбирает автоматически RBAC/ABAC
или иной способ реализации доступа для AOS либо создаваемого проекта.

Агент выясняет, какие требования законодательства и внутренние правила
организации применимы к создаваемой системе. Например: правила работы
с персональными данными или сроки хранения документов. Пользователь сообщает
известные ему требования и ответственных за внутренние правила. Если ответа
нет, агент продолжает интервью и подготовку ТЗ без добавления предполагаемых
требований законодательства или внутренних правил. Эти пункты не блокируют
утверждение ТЗ и принимаются как неучтённые по решению пользователя.
В документах явно указывается, что применимые требования не были предоставлены
и их соблюдение не проверено; отсутствие ответа не означает, что применимых
законов нет или что их можно отменить решением проекта. Исследование проводится
только если пользователь выбрал такой путь. Агент не придумывает юридическое
требование и не представляет исследование как решение уполномоченного человека.

Агент выясняет, где и с каких устройств люди будут пользоваться создаваемой
системой, чтобы учесть условия использования и удобство. Например: складской
компьютер, телефон при выдаче оборудования или работа из дома. Конкретные
устройства и места определяются ответами пользователя; примеры не означают
обязательной поддержки всех перечисленных вариантов.

Агент спрашивает об особых требованиях к удобству и доступности создаваемой
системы, например о крупном тексте, управлении без мыши или использовании
людьми с ограничениями зрения. Если информации нет, этот пункт отмечается
как не предоставленный, но не блокирует завершение или утверждение ТЗ.
Агент не придумывает специальные требования вместо ответа пользователя.

Агент выясняет, должна ли создаваемая система продолжать работу без интернета
и что должно происходить при потере связи. Например, нужно определить,
останавливается ли работа склада или операции временно сохраняются для
последующей передачи. Конкретное поведение определяется ответом пользователя;
технический способ автономной работы выбирается после этого.

Агент спрашивает, как должны восстанавливаться работа и данные после серьёзного
сбоя, включая допустимую потерю последних изменений и требуемую скорость
возобновления работы. Если ответа нет, пункт отмечается как не предоставленный,
но не блокирует завершение или утверждение ТЗ. Агент не придумывает гарантии
восстановления и не представляет непроверенное восстановление как обеспеченное.

Агент выясняет, как пользователи входят в создаваемую систему и как
подтверждается их личность. Например: отдельный пароль, корпоративная учётная
запись или работа без входа. Конкретный способ определяется ответом пользователя;
пример не выбирает механизм авторизации и не отменяет правила доступа.

Агент спрашивает, что происходит с доступом пользователя при смене должности
или увольнении: когда доступ изменяется или закрывается и что происходит
с созданными этим человеком записями. Если ответа нет, пункт отмечается
как не предоставленный, но не блокирует завершение или утверждение ТЗ.
Агент не назначает правило управления доступом самостоятельно.

Агент выясняет, кто будет управлять создаваемой системой после запуска:
добавлять и изменять пользователей, поддерживать справочники и разбирать
возникающие ошибки. Эти обязанности могут принадлежать разным людям;
конкретные ответственные и их полномочия определяются ответами пользователя.

Агент не обязан выяснять, куда пользователь обращается после запуска,
если система работает неправильно или ему нужна помощь. Канал пользовательской
поддержки не входит в обязательные темы интервью и не добавляется в ТЗ
без отдельного требования пользователя.

Агент выясняет, где должны храниться данные готовой системы: например,
на компьютере пользователя, сервере организации или во внешнем облачном
сервисе. Он объясняет понятным языком последствия вариантов для доступности,
работы без интернета и ограничений системы. Пользователь выбирает требуемое
поведение и место; конкретную технологию хранения агент определяет позднее
в пределах утверждённых требований.

Агент выясняет, нужна ли создаваемой системе история действий пользователей,
например сведения о том, кто и когда изменил запись об оборудовании.
Это обязательная тема уточнения, а не автоматическое включение истории
действий во все создаваемые системы; необходимость определяется ответом
пользователя.

Агент выясняет, о каких событиях создаваемая система должна уведомлять людей.
Например: просроченный возврат оборудования или изменение рабочего графика.
Конкретные события определяются ответами пользователя; примеры не включают
уведомления автоматически во все создаваемые системы.

Агент выясняет, какие отчёты и сводки нужны пользователям для работы.
Например: список невозвращённого оборудования или количество смен у каждого
сотрудника. Необходимость и состав отчётов определяются ответами пользователя;
примеры не назначают обязательные отчёты для всех создаваемых систем.

Агент выясняет, как исправлять ошибочные действия в создаваемой системе:
допустима ли отмена и какие сведения об исправлении необходимо сохранять.
Например, оборудование ошибочно выдали не тому сотруднику. Конкретный порядок
исправления определяется ответами пользователя; возможность отмены любого
действия не предполагается автоматически.

Агент выясняет, что должно происходить при одновременных конфликтующих
изменениях несколькими людьми. Например, два руководителя назначают одному
сотруднику разные смены на одно время. Правило разрешения конфликта определяется
ответами пользователя, а не выбирается агентом как неявное поведение системы.

Агент выясняет, как система должна реагировать на повтор одного действия.
Например, если сотрудник дважды нажал «Отправить заявку», нужно определить,
должна ли появиться одна заявка или две. Ожидаемый результат определяется
ответом пользователя; правило обработки повторов не предполагается автоматически.

Агент выясняет, что происходит с данными, которые больше не используются.
Например, сведения о списанном оборудовании могут сохраняться в архиве
или быть доступны для удаления. Порядок хранения, архивирования или удаления
определяется ответами пользователя; само обсуждение не разрешает удаление данных.

Агент выясняет, какие правила создаваемой системы нельзя нарушать ни при
каких обстоятельствах. Например, один экземпляр оборудования нельзя
одновременно выдать двум сотрудникам. Конкретные обязательные правила
определяются ответами пользователя и фиксируются в ТЗ; пример не назначает
предметное правило всем проектам.

Агент выясняет наиболее опасные последствия ошибки создаваемой системы,
например потерю данных, доступ постороннего человека или назначение сотрудника
одновременно на две смены. Выявленные последствия определяют глубину дальнейших
вопросов, защитные требования и проверяемые примеры. Агент не объявляет риск
устранённым только потому, что он записан в ТЗ.

Агент выясняет, какие действия создаваемая система не может выполнять без
подтверждения человека. Например: списание оборудования, удаление данных
или публикация рабочего графика. Для каждого такого действия уточняются
подтверждающий человек и момент подтверждения. Примеры не назначают
обязательные подтверждения всем проектам; правила определяет пользователь.

Агент выясняет полный путь каждой значимой сущности от попадания в систему
до завершения её жизненного цикла. Простыми словами, это путь заявки,
оборудования, смены или другого объекта, с которым работает система.
Для каждого шага выясняются ответственный и передача работы следующему
участнику; путь включает состояния, условия переходов, исключения и варианты
завершения по общим правилам полноты процесса. Например: сотрудник подаёт
заявку, руководитель согласовывает, кладовщик выдаёт оборудование; дальнейший
путь и завершение также должны быть выяснены, а не оставлены за рамками интервью.

Агент выясняет все типы пользователей создаваемой системы и для чего система
нужна каждому из них. Для каждого типа определяются его цель и участие
в целевом процессе. Например: сотрудник подаёт заявку, руководитель принимает
решение, кладовщик выдаёт оборудование. Пример не назначает обязательные роли;
конкретный состав пользователей определяется ответами пользователя.

Для каждого главного объекта агент выясняет, какие сведения должна хранить
создаваемая система. Например, для оборудования это могут быть название,
номер, состояние, местонахождение и ответственный сотрудник. Конкретный набор
сведений определяется ответами пользователя; пример не задаёт обязательные
поля для всех проектов. Это описание необходимых данных, а не готовая схема
базы данных.

Агент выясняет правила заполнения сведений: что обязательно, какие значения
допустимы, что должно быть уникальным и какие ошибки ввода нужно предотвращать.
Например, необходимо определить, может ли номер оборудования повторяться
и какие состояния оборудования разрешены. Эти правила формулируются через
ожидаемое поведение системы, а способ технического хранения выбирается позднее.

Агент не выясняет примерный объём данных при запуске и скорость их дальнейшего
роста. Например, от пользователя не требуется оценивать количество единиц
оборудования сейчас или прирост записей в месяц. Это исключение не отменяет
принятого требования выяснять, сколько людей могут работать с системой
одновременно, когда это существенно для её поведения.

Полный разбор применяется к главным и рискованным сущностям: влияющим на
основной результат, меняющим состояния, переходящим между несколькими людьми,
связанным с доступом, согласованием, важными данными, историей изменений
или серьёзными последствиями ошибки. Для простых справочников допустим краткий
разбор: кто заполняет, кто использует и можно ли изменять записи. Если внешне
простой справочник управляет правилами системы, например переходами статусов,
он разбирается подробнее. Агент предлагает глубину и объясняет причину;
пользователь может попросить углубить или сократить разбор.

Агент обязательно выясняет необходимость обмена данными с другими системами,
даже если пользователь не упомянул её сам. Если обмен нужен, агент последовательно
уточняет, какие сведения и между какими системами передаются, автоматически
или по команде человека, какая система является источником верных данных
при расхождении и что делать при недоступности связи или ошибке передачи.
Способ подключения исследуется после выяснения процесса. При недостатке
сведений о внешней системе агент сохраняет пробел и не обещает неподтверждённую
совместимость. Пример: кадровая система сообщает об увольнении, а система
учёта оборудования показывает, что сотрудник ещё должен вернуть.
Пример поясняет форму требования, а не назначает обязательную интеграцию AOS.

Агент выясняет, какие данные понадобятся при первом запуске создаваемой системы
и откуда их получить. Например, учёт оборудования может начинаться с пустого
списка или с загрузки существующей таблицы Excel; вариант выбирается по ответам
пользователя. Пример не устанавливает обязательную поддержку Excel и не
разрешает фактическую загрузку данных в рамках подготовки ТЗ.

Агент выясняет, по какому наблюдаемому полезному результату пользователь
поймёт, что система решила его задачу. Этот результат фиксируется в ТЗ
как основание для проверки готовности и связывается с проверяемыми примерами.
Например: «В любой момент видно, у кого находится оборудование и что
просрочено к возврату». Пример не назначает предметные требования без ответа
пользователя; запись критерия не означает его выполнения созданной системой.

По итогам разговора агент предлагает границы системы, а пользователь
подтверждает их: что входит в выбранную версию, что отложено и что не входит
в назначение системы. Фиксируются существенные границы, которые можно ошибочно
включить в задачу, а не перечень всех отсутствующих возможностей. Например:
учёт и выдача оборудования входят в версию, закупка отложена, расчёт зарплаты
не входит в назначение системы. Эти примеры не выбирают scope за пользователя.

Если пользователь меняет тему, агент следует за его мыслью, кратко отмечает,
что незавершённый вопрос остаётся открытым, и сохраняет его. К этому вопросу
агент возвращается в подходящий момент, обязательно до завершения интервью.
Если ответ на новой теме уже закрыл прежний вопрос, повторно задавать его
не требуется.

Объём предстоящего интервью заранее непредсказуем, поэтому его длительность
и срок завершения не фиксируются. Агент не обещает заранее определённое время
прохождения интервью; вопросы уточняются по мере изучения задачи. Предложение
показывать предварительный список тем не принято как обязательное требование.

Агент не обязан выяснять календарный срок готовности первой полезной версии
создаваемой системы. Срок не входит в обязательные вопросы интервью;
состав и приоритеты версии определяются без обязательной привязки к дате.

Агент просит разделить возможности создаваемой системы на обязательные
для первой версии, желательные и будущие. Такое разделение определяет состав
и последовательность разработки без привязки к календарному сроку.
Агент объясняет категории простыми словами; окончательное отнесение возможности
к выбранной версии подтверждает пользователь.

Агент выявляет зависимости между возможностями, объясняет их простыми словами
и предлагает последовательность разработки. Например, учёт сотрудников
и оборудования может потребоваться до выдачи, а отчёты и уведомления — после
появления основных операций. Пример не задаёт обязательный порядок для всех
проектов. Пользователь определяет состав версий; агент выбирает и обосновывает
технически выполнимый порядок внутри подтверждённых границ.

Предложенная последовательность разработки является рекомендацией агента.
Пользователь не обязан с ней соглашаться и может принять, изменить или
отклонить её. Утверждение требований само по себе не означает принятия
предложенного порядка. Если порядок отклонён или изменён, агент учитывает
решение пользователя и сообщает о зависимостях, которые мешают выполнить его.

После запуска разработки агент может самостоятельно менять внутренний порядок
работ, если состав версии, утверждённые требования, обязательные проверки
и решения пользователя не меняются и перестановка не создаёт новых расходов,
внешних подключений или существенных рисков. Агент сохраняет обновлённый порядок
и кратко объясняет причину в отчёте. Если перестановка меняет согласованный
результат, границы версии либо откладывает существенную для пользователя часть,
агент сначала обращается к пользователю.

Интервью допускается на любом языке, с которым может работать выбранный агент;
ограничения только русским языком нет. Требования к понятности вопросов,
объяснениям и примерам сохраняются независимо от языка. По умолчанию итоговое
ТЗ и аннотации составляются на языке интервью; пользователь может выбрать
для них другой язык.

По умолчанию интерфейс создаваемой системы проектируется на языке, на котором
агент проводит интервью. Пользователь может попросить другой язык, доступный
выбранному агенту. Это правило выбирает язык текстов интерфейса; оно само
по себе не подтверждает качество перевода и не означает одновременную
поддержку нескольких языков — такая потребность уточняется отдельно.

Агент обязан отдельно спросить, должна ли готовая система поддерживать
несколько языков одновременно и переключение между ними. Если ответа нет,
пункт отмечается как не предоставленный, но не блокирует завершение или
утверждение ТЗ. Отсутствие ответа не включает многоязычность автоматически.

После каждых пяти ответов пользователя агент простыми словами суммаризирует,
что он понял из этих ответов о желаемой работе системы. Это прямое требование
пользователя к ритму интервью. Сводка отражает полученные ответы; нерешённые
вопросы не представляются согласованными требованиями. Дополнительные итоги
до пяти ответов пока не выбраны как обязательное правило. Итоговое подтверждение
целого процесса обязательно по принятому ниже порядку завершения интервью.

Следующий ответ пользователя уточняет вход первого желаемого сценария: человек
должен понимать, чего он хочет и как система должна работать с позиции процессов.
Пользователь задаёт желаемый ход работы. Последующим ответом он уточнил границу:
агент должен выяснить весь процесс, чтобы воспроизвести его в коде. Вопросы
охватывают основной ход, пропущенные шаги, исключения и краевые состояния.
Любая неоднозначность в желаемом поведении процесса требует уточнения у
пользователя; агент не подменяет ответ собственной догадкой. Понимание процесса
должно быть достаточным для его последующей реализации. Это требование к сбору
требований, а не разрешение на runtime-разработку в notebook.

Интервью сразу собирает целевой процесс — как система должна работать.
Агент не обязан предварительно выяснять существующий ручной процесс или способ,
которым задача решается сейчас. Это принятое отличие от optional Current Workflow
референсной методологии AOS-FARM. Если пользователь просит рекомендацию и ещё
не знает целевое решение, агент в рамках тьютора помогает найти варианты
по принятым ниже правилам исследования; без такой просьбы текущий процесс
не подменяет целевой и не становится обязательным блоком интервью.

Если пользователь передал материалы проекта, агент сначала изучает их и задаёт
вопросы только о пробелах, не повторяя вопросы с уже имеющимися однозначными
ответами. Противоречия отмечаются и сохраняются для обсуждения в конце интервью
по правилам ниже. Понимание, полученное из материалов, включается в итоговое
описание всей системы и предъявляется пользователю для принятия или непринятия;
само наличие ответа в материале не заменяет этого итогового решения.

Если это помогает понять процесс, агент может попросить обезличенный пример
документа, таблицы или экрана, например пустой бланк выдачи оборудования
без настоящих персональных данных. Пользователь не обязан предоставлять пример;
его отсутствие не блокирует интервью или утверждение ТЗ. Полученный пример
фиксируется как источник понимания, а не как автоматически утверждённое
требование или разрешение хранить чувствительные данные.

Если часть переданных материалов невозможно прочитать, агент называет
недоступные файлы, объясняет, каких сведений не хватает, и продолжает интервью
по доступной информации. Содержание непрочитанных материалов не считается
известным; связанные пробелы сохраняются открытыми и предъявляются в конце
интервью по общему порядку. Если из-за недоступности нельзя определить,
какие именно сведения отсутствуют, агент явно сообщает об этом.

Если пользователь пока не знает, как должен работать отдельный участок процесса,
предпочтительный вариант — он изучает вопрос и возвращается с готовым решением.
Это предпочтение, а не обязательное условие получения помощи. Агент должен иметь
возможность сетевого исследования: найти примеры других проектов либо сведения
о том, как процесс устроен на практике, и предложить пользователю несколько
вариантов с понятными объяснениями различий и последствий. Пользователь выбирает
желаемое поведение; до выбора вопрос остаётся открытым.

На ответ «не знаю» агент спрашивает пользователя, найти ли варианты решения
или отложить вопрос до конца интервью. Агент не выбирает этот путь за
пользователя. При выборе поиска он предлагает варианты по правилам исследования
выше; при выборе отсрочки сохраняет вопрос открытым и обязательно возвращается
к нему в конце интервью. Сам ответ «не знаю» не запускает поиск автоматически.

При выбранном поиске агент сначала предлагает топ-3 подходящих решений,
отдавая приоритет лучшим практикам и отраслевым решениям. Варианты сопровождаются
понятными примерами, комментариями, ограничениями и рекомендацией агента
с объяснением выбора. Основания и источники показываются по правилам исследования
ниже; оценка применимости к задаче отличима от подтверждённой практики.
Если первая тройка не устраивает пользователя, агент предлагает три других
решения, сохраняя приоритет лучших практик и отраслевых подходов.
Если удалось найти только одно или два обоснованных подходящих решения,
агент показывает найденные и объясняет, почему вариантов меньше трёх.
Пользователь принял это исключение; выдуманные результаты исследования
для заполнения тройки недопустимы.

Если ответ пока отсутствует, агент сохраняет вопрос открытым и продолжает
интервью по темам, не зависящим от этого ответа. Пользователь принял такой
порядок и отдельно потребовал: в конце интервью агент обязательно поднимает
все оставшиеся вопросы без ответов. Отложенный вопрос не теряется и не
заполняется предположением вместо решения пользователя.

Если новый ответ противоречит ранее полученному, агент принимает и сохраняет
его, сразу указывает пользователю на противоречие и продолжает интервью.
Немедленного разрешения конфликта не требуется: агент сохраняет обе формулировки
и открытый конфликт, не выбирая действующее правило самостоятельно. В конце
интервью он возвращается ко всем неразрешённым конфликтам вместе с вопросами
без ответов. Например, ответы «выдачу оборудования подтверждает руководитель»
и «подтверждение выдачи не требуется» сохраняются как конфликт до уточнения
пользователем. Принятие нового ответа как записи не означает автоматической
отмены прежнего требования или согласования противоречивого ТЗ.

Исследование направлено на конкретный пробел и следует правилам provenance
[Reference](05_Reference.md#8-targeted-research-record). Варианты сопровождаются
ссылками на основания; наблюдаемая практика отличима от предложения агента.
Чужой проект не становится источником требований вместо ответа пользователя.
Сетевой доступ для этого сценария должен быть предусмотрен в выбранной среде;
его недоступность обозначается явно и не заменяется выдуманными результатами
исследования. Это требование к будущей возможности продукта, не отдельное
поручение на сетевой поиск в текущем интервью.

описанного здесь первого сценария; его дальнейшая применимость ещё не решена.

меняют автоматически ранее выбранный scope X1/scaffold/core или dispositions
фич. Поведение интервью принадлежит FTR-001, подготовки спецификации — FTR-003.

**Подтверждение сводки:** пользователь ответил «Все верно» на пять пунктов:
исходное понимание процессов пользователем; выяснение агентом всего процесса
без догадок; исследование вариантов при отсутствии решения с выбором за
пользователем; ТЗ для агента/программиста с простыми аннотациями; понятный диалог
со сводкой после пяти ответов. Подтверждение относится к этим требованиям,
не закрывает перечисленные открытые вопросы и не принимает весь пакет проекта.

### Общая картина продукта и два режима подготовки

Пользователь принял следующую рекомендацию в текущем интервью. AOS поддерживает
оба режима; по умолчанию предлагает последовательную подготовку версий.

Сначала агент выясняет общую картину всего задуманного продукта: пользователей,
процессы, их связи и желаемый результат. Затем предлагает последовательность
разработки законченных полезных частей с объяснением последствий; пользователь
выбирает границы версии. Подробное интервью охватывает все процессы выбранной
версии, исключения и неоднозначности до достаточной ясности для разработки.
Известные требования к следующим версиям и открытые вопросы сохраняются и
прорабатываются позднее. Будущие требования, влияющие на выбранную версию,
не откладываются: их необходимо выяснить до её реализации.

Альтернативный режим — подготовка всего продукта до запуска разработки без
последующих уточнений требований. В этом режиме все его части, связи и важные
решения подробно разбираются заранее; интервью может занимать несколько бесед.
Оставленные на потом существенные решения несовместимы с заявлением о готовности
всего продукта к такой разработке. Подготовка требований не гарантирует отсутствия
непредвиденных технических препятствий и не заменяет проверку среды и полномочий.

Общая картина продукта и подробные требования версий сохраняют существующих
владельцев Product Spec и Feature Passport. Выбор режима не требует нового
параллельного каталога. Подготовленная единица разработки должна быть законченной
полезной частью с описанными связями, а не набором несвязанных мелких изменений.
Это принятое продуктовое требование к интервью AOS; оно не означает, что все
фичи самого AOS уже подготовлены или получили разрешение на реализацию.

**Уточнение пути разработки — DRAFT:** после принятия достаточного ТЗ и отдельной
команды на полный цикл выбранная конечная версия может быть предметом одной
общей задачи по [§16](#autonomous-project-outcome). Подготовка всего продукта
использует тот же путь только при явно выбранном полном составе. Детальную
декомпозицию выполняет агент; следующий внутренний шаг не является выбором
новой версии пользователем.

### Завершение черновика агентом по умолчанию

Пользователь принял вариант, сокращающий число предсказуемых вопросов.
По умолчанию агент сначала собирает основные сведения: цель и полезный результат,
типы пользователей, целевые процессы, жизненный цикл главных сущностей,
границы первой версии, критические запреты и подтверждения человека,
существенные интеграции и критерии проверки. Состав основных вопросов
адаптируется к проекту и не имеет заранее фиксированного числа или времени.

Когда этих сведений достаточно для содержательного проекта ТЗ, агент прекращает
последовательное согласование второстепенных и предсказуемых пунктов. Он сам
доделывает полный черновик, используя ответы пользователя, переданные материалы,
принятые defaults AOS, обоснованные лучшие практики и результаты разрешённого
исследования. Агент не скрывает способ заполнения: собственные дополнения
помечаются как рекомендации или предположения, а отсутствие основания — как
открытый вопрос. Они не выдаются за решения пользователя.

Вместе с черновиком агент предъявляет один нумерованный пакет для рассмотрения:
что взято из ответов, что предложено агентом по умолчанию, какие конфликты
обнаружены, какие сведения не предоставлены и что действительно требует
решения до утверждения. Пользователь может принять пакет целиком либо назвать
номера пунктов для исправления. Подтверждение точной версии ТЗ принимает
включённые в неё явно показанные рекомендации; до этого они остаются proposal.

Неразрешённый существенный вопрос не запрещает агенту подготовить полный
черновик и предложить рекомендуемый вариант. Он запрещает скрыть неопределённость,
выдать предложение за решение человека или начать зависимую реализацию.
Таким образом, требование уточнять любую неоднозначность выполняется через
основное интервью и итоговый пакет, а не обязательно через отдельный вопрос
по каждому полю до появления первого полного черновика.

Перед статусом `READY_FOR_HUMAN_REVIEW` агент применяет минимальный порог
достаточности. В черновике должны быть определены либо явно предложены для
принятия: полезный результат, участники, начало и конец основных процессов,
жизненный цикл главных сущностей, границы первой версии, критические запреты
и подтверждения человека, существенные интеграции и наблюдаемые примеры
приёмки. Черновик можно подготовить и при неполноте, но нельзя назвать готовым
к утверждению, если материальный пробел не закрыт ответом пользователя или
видимой рекомендацией агента. Сам факт заполнения всех полей полноту не доказывает.

Глубина завершения зависит от риска. Для обычной обратимой системы применяется
профиль `STANDARD`: агент предлагает безопасные defaults и выносит их на общее
рассмотрение. Для системы, где ошибка может причинить существенный финансовый,
правовой, медицинский, физический ущерб, раскрыть чувствительные данные или
затронуть много внешних пользователей, применяется профиль `STRICT`. В нём
материальные ограничения безопасности и доступа нельзя скрыто закрывать defaults,
а независимая проверка настоятельно рекомендуется. Отсутствие ответа о законах
и внутренних правилах по-прежнему не блокирует подготовку и утверждение ТЗ,
но агент не заявляет соответствие неизвестным требованиям; зависимое действие
может потребовать отдельного подтверждения до реализации.

Требования в чистовом ТЗ формулируются отдельно и проверяемо: одно существенное
поведение или правило на требование, с источником и хотя бы одним связанным
примером приёмки. Составное пожелание пользователя можно сохранить дословно
в записи интервью, но в ТЗ оно разделяется без потери смысла.

### Завершение интервью перед итоговым ТЗ

Пользователь принял обязательное итоговое подтверждение. Перед подготовкой
итогового ТЗ агент показывает целостное описание будущей работы системы простыми
словами. По уточнению пользователя итог охватывает понимание всей системы,
включая сведения из переданных материалов; выбранная версия и будущие части
обозначаются явно, с глубиной детализации по выбранному режиму подготовки.
Пользователь явно принимает или не принимает это понимание системы.
При непринятии описание остаётся неподтверждённым; агент выясняет необходимые
поправки и обновляет описание.
Поправки учитываются в описании; итоговая версия описания требует подтверждения
до подготовки итогового ТЗ. Промежуточные записи и черновики допустимы во время
интервью, но не выдаются за подтверждённое итоговое ТЗ.

Для итогового согласования пользователь выбрал сочетание трёх представлений:
короткое описание всей системы простыми словами, схемы основных процессов
со стрелками и развилками, а также подробные таблицы правил и исключений.
Все представления описывают одни и те же требования и не должны противоречить
друг другу. Пользователь проверяет смысл описания и схем; агент отвечает за
соответствие им подробных таблиц. Согласование этих материалов не заменяет
отдельного утверждения готового ТЗ.

После подготовки ТЗ агент предъявляет его пользователю для отдельного
утверждения. ТЗ считается принятым только после явного утверждения пользователем;
принятие предварительного описания системы и сам факт создания файлов ТЗ
этого утверждения не заменяют. Запуск разработки начинается по отдельной
команде пользователя: утверждение ТЗ само по себе разработку не запускает.

Пользователь выбрал утверждение ТЗ в чате сообщением «Утверждаю» после
предъявления конкретной версии. Агент сохраняет факт утверждения и связь
с этой версией в материалах проекта. Утверждение не переносится автоматически
на последующие изменения. Принятие этого порядка в текущем интервью
не является утверждением ещё не предъявленного итогового ТЗ.

Если после утверждения ТЗ пользователь меняет требование, агент простыми
словами объясняет последствия и какие части системы затронет изменение.
Изменённое ТЗ предъявляется пользователю для повторного утверждения;
утверждение прежней версии не распространяется автоматически на новую.
Если разработка уже запущена, пользователь принял следующий порядок:
затронутая изменением работа приостанавливается, а независимая может
продолжаться в пределах ранее разрешённой разработки, только если агент
может обосновать, что изменение её не касается. Агент объясняет, что затронуто,
что приостановлено и что можно продолжать. Если границы влияния неясны,
агент сначала выясняет их, не объявляя спорную работу независимой.
Реализация изменений начинается после повторного утверждения ТЗ и отдельной
команды пользователя на реализацию этих изменений.

Пример: изменение правил выдачи оборудования приостанавливает разработку
выдачи. Работу над оформлением справочника оборудования можно продолжить,
если агент обосновал, что его содержание и поведение остаются прежними.

Если при разработке обнаружен пробел в ТЗ, агент сразу сообщает пользователю,
простыми словами объясняет ситуацию, предлагает варианты и свою рекомендацию.
До ответа приостанавливается работа, зависящая от этого решения; независимая
работа может продолжаться в пределах утверждённого ТЗ и ранее разрешённой
разработки. Неописанное поведение не выбирается агентом самостоятельно.
Внутренние технические решения, не меняющие согласованное поведение, стоимость
или ограничения системы, агент принимает сам в действующих границах полномочий.
Если ответ пользователя меняет ТЗ, применяются повторное утверждение ТЗ
и отдельная команда на реализацию изменений по порядку выше.

Пример: если ТЗ не определяет, можно ли выдавать неисправное оборудование,
агент сразу задаёт вопрос и приостанавливает реализацию этого правила.
Независимую работу над поиском оборудования он может продолжить.
Этот порядок относится к разработке; конфликты ответов во время интервью
по-прежнему отмечаются сразу и обсуждаются в конце интервью.

Перед итоговым подтверждением агент предъявляет все сохранённые вопросы без
ответов и неразрешённые конфликты ответов и возвращается к их обсуждению.
Он показывает, какие из них влияют на
выбранную версию, а какие относятся к будущим версиям. Существенные вопросы
и конфликты выбранного объёма необходимо разрешить до завершения его ТЗ;
вопросы и конфликты будущих версий сохраняются открытыми и не скрываются
из общей картины продукта.

Если в конце интервью существенные вопросы выбранного объёма остаются без
решения, ТЗ сохраняется как черновик. Агент явно показывает, что необходимо
решить для его утверждения. Сохранение черновика не означает принятия ТЗ
или разрешения начать разработку.

Перед предъявлением итогового ТЗ агент самостоятельно проверяет его полноту
и отсутствие неразрешённых противоречий по адаптированной методологии.
В частности, для каждого главного процесса проверяются начало, завершение,
ответственные, исключения и наблюдаемый проверяемый результат. Обнаруженные
пробелы и конфликты обрабатываются по правилам интервью. Успешная проверка
агента не заменяет принятие описания системы или утверждение ТЗ пользователем.

Рассмотрение проходит тремя слоями. Сначала пользователь видит короткое описание
системы и основные схемы. Затем — одну нумерованную страницу решений, разделённую
на четыре группы: необходимо решить сейчас; рекомендованный default агента;
не предоставлено, но не блокирует; отложено в будущую версию. После этого доступен
полный текст ТЗ с источниками и критериями приёмки. Перед запросом «Утверждаю»
агент ещё раз простыми словами показывает, что изменится для пользователя,
и перечисляет только материальные решения. Общее согласие с описанием не скрывает
нерешённый конфликт и не заменяет привязку утверждения к точной редакции.

Результат проверки предъявляется пользователю простыми словами. Агент показывает,
что проверено, какие сведения не предоставлены, какие ограничения приняты
без уточнения и что ещё мешает утверждению. Технические детали проверки могут
сохраняться для агента и программиста, но не заменяют понятного объяснения.

Перед утверждением ТЗ агент предлагает независимую проверку другим агентом,
который не проводил интервью. Такая проверка рекомендуется для поиска пропусков,
но не является обязательной: пользователь может её пропустить, и отсутствие
проверки не блокирует утверждение ТЗ. Выполненная независимая проверка также
не утверждает ТЗ вместо пользователя.

Пользователь принял двухэтапный порядок независимой проверки. Сначала
проверяющий читает только ТЗ, аннотации и схемы и оценивает, достаточно ли их
программисту или новому агенту без устных пояснений. Затем он читает сохранённые
записи интервью и материалы-источники и проверяет, не искажены ли ответы
и не потеряны ли требования. История чата не используется как скрытый источник:
если без неё ТЗ нельзя проверить, документация считается недостаточной.

Сводки после пяти ответов проверяют понимание отдельных ответов и не заменяют
подтверждение процесса целиком. Подтверждение описания не закрывает существенные
неоднозначности одним общим согласием; для выбранного объёма они уточняются по
правилам интервью. Оно относится к желаемому поведению, а не к приёмке ещё
не созданного кода или разрешению на его выполнение и Git-доставку.

### Технические решения при подготовке ТЗ

Пользователь принял разделение: агент выявляет решения о построении системы,
влияющие на стоимость, удобство и ограничения, объясняет варианты простыми
словами и получает выбор пользователя. Например, требование работать без
интернета или место хранения данных обсуждаются через последствия для
пользователя. Такие вопросы дополняют описание процессов и не требуют от
собеседника знания программирования.

Пользователь исключил из интервью выяснение ограничений бюджета на работу
будущей системы, например ежемесячных расходов на сервер или платный ИИ.
Отдельный сбор эксплуатационного бюджета не требуется. Это не отменяет
принятого выше объяснения стоимости конкретных предлагаемых решений и не
означает разрешения на расходы или подключения платных услуг.

Внутренние детали программирования агент определяет самостоятельно в пределах
согласованного поведения и ограничений. Это не даёт права под видом технической
детали менять требования, выбирать новый существенный внешний эффект или
обходить защищённые решения [Core](00_Core.md#15-защищённые-решения-человека).
Достаточный ранее принятый выбор не требует повторного согласования; обычный
обратимый HOW остаётся за агентом. Ответ принимает этот порядок взаимодействия,
но не выбирает конкретные технологии, providers, dependencies или target.

Пользователь принял разделение ТЗ и технической архитектуры. ТЗ описывает
поведение системы, процессы, данные, роли, интеграции, ограничения и проверяемые
результаты, включая подтверждённые существенные технические ограничения.
После утверждения ТЗ и отдельной команды на разработку агент сначала готовит
связанный с точной версией ТЗ архитектурный документ: компоненты, технологии,
хранение данных, связи, проверки, восстановление и развёртывание.

Архитектура не изменяет утверждённые требования. Решения с существенными
последствиями для пользователя агент объясняет и возвращает на выбор;
внутренние обратимые решения принимает самостоятельно. После проверки
архитектуры агент может перейти к реализации без нового разрешения, если
команда уже охватывает разработку, требования и границы не изменились
и не требуется отдельное защищённое действие.

Для создаваемой системы с пользовательским интерфейсом после утверждения ТЗ
рекомендуется подготовить простые макеты основных экранов до реализации интерфейса.
Макеты проверяют понятность пользовательского пути и не заменяют утверждённые
требования или отдельную техническую архитектуру.
Основание — пункт 3 §21 [ТЗ интервью версии 0.3-draft](../workspace/AOS_INTERVIEW_TO_TZ_IMPLEMENTATION_BRIEF.md)
и [утверждение его exact revision](../workspace/AOS_INTERVIEW_TO_TZ_APPROVAL.md).
Без отдельного требования применимого ТЗ отсутствие макета само по себе не
блокирует разработку интерфейса; утверждённые bytes этих источников не изменяются.

<a id="ux-pages-product"></a>

### FTR-032: два представления UX-страниц — DRAFT / PROPOSAL

По поручению пользователя модель `AOS-UX-PAGES-DUAL-SURFACE-MODEL R2`
используется для проработки [FTR-032](06_Features.md#ftr-032-contract).
Это кандидат результата выбранного UX-модуля, не обязательная стадия каждого
проекта и не принятие всего R2. Рекомендация макетов выше остаётся в силе;
FTR-027 не активируется и не объединяется с FTR-032.

Человек по запросу «Покажи интерфейс проекта» получает понятный workspace:
страницы с человеческими названиями, показанную редакцию, ограничения макета,
существенные вопросы и одно следующее действие. Он пробует поддержанный сценарий,
просит изменение обычным языком, видит объяснение фактического diff и передаёт
решение по показанной редакции. Для этого не требуется читать YAML/hash, искать
папки, устанавливать parser или вводить команды. Доступность такого пути в конкретной
среде проверяется пилотом, не выводится из наличия index.html.

Инженер/агент получает Engineering Surface той же редакции: нужные требования,
поведение/данные, источники, gaps, проверки и решения для конкретной FRONTEND либо
INTEGRATION задачи. Человек может открыть эти детали, но существенная неопределённость
и её пользовательское последствие видны сразу. Две поверхности не являются двумя
ролями доступа. Полнота страницы, полнота journey, выполненные проверки, решение
человека и разрешение на реализацию показываются раздельно.

Первый законченный путь — PROPOSAL: одна форма и связанная страница, оба представления,
ограниченная синтетическая симуляция, одна коррекция/diff, решение через действующий
доверенный агентный канал и один FRONTEND pack. Generated viewer только подготавливает
контекст решения; прямой writable browser UI не обещается. Этот компромисс требует
выбора DS-O02 у [FTR-032](06_Features.md#ux-pages-open-decisions). Production UI/backend,
новый approval service, универсальный UI framework и SaaS не входят в этот кандидат.

Качество проверяется по способности человека выполнить путь без технических данных,
пониманию принятого scope, обнаружению инженером известного gap и затратам полного
цикла. Рейтинги 9/10 или 10/10 не заявляются. Методы и предложенные численные пороги
пилота — [Development](03_Development.md#ux-pages-verification); измерения NOT_RUN,
польза/стоимость UNKNOWN. [Reference](05_Reference.md#ux-pages-r2-source) хранит
происхождение и ограничения R2, включая недоступные исходные файлы.

### Готовая полная спецификация

AOS сохраняет original input, проверяет missing fields и contradictions, показывает added assumptions, задаёт только material questions, создаёт DRAFT Product Spec/Feature Passport и останавливается до architecture/execution authority.

### Неполная идея

Problem Interview определяет user/pain/current workaround, отделяет outcome от solution, фиксирует success signals, constraints, non-goals, unknowns, follow-up questions и sensitive/provider concerns.

### Прогрессивная глубина

| Profile | Minimum depth |
|---|---|
| Small reversible | Goal, scope, observable result, focused check |
| Medium feature | Users, flow, acceptance, dependencies, regression |
| High/protected | Full constraints, rollback, authority checkpoints |
| Sensitive/regulated | Data/provider boundary, specialist review |

Точные thresholds остаются `UNDECIDED`.

### Исходные ответы и происхождение требований

Пользователь принял сохранение исходных ответов отдельно от итогового ТЗ,
в той же папке проекта. Записи интервью содержат вопросы, исходные ответы
и уточнения; ТЗ содержит согласованные требования без всей переписки.
Каждое требование связано ссылкой с ответом или переданным материалом,
из которого оно появилось. Агент самостоятельно оформляет и поддерживает
эти связи; ручное оформление пользователем не требуется.

В документах явно различаются пять классов сведений: решение пользователя,
сведения из переданного материала, предположение агента, рекомендация агента
и открытый вопрос. Основной текст ТЗ остаётся понятным; рядом с каждым
существенным требованием сохраняются его статус и ссылка на источник.
Предположения, рекомендации, конфликты и открытые вопросы дополнительно
собираются в отдельные понятные таблицы. Сведение из материала и предложение
агента не становятся подтверждённым требованием без решения пользователя.

Каждый ответ сохраняется сразу после получения, до следующего вопроса.
Агент записывает исходный ответ и отдельно своё понимание, обновляет оставшиеся
вопросы и конфликты. Сводка после каждых пяти ответов не заменяет сохранение
каждого ответа. Если сохранение не удалось, агент сообщает об этом и не
представляет ответ как сохранённый. При неожиданном прерывании последний ответ,
сохранение которого ещё не завершилось, может потребоваться повторить;
уже сохранённые записи используются для продолжения интервью в новом чате.

При изменении решения прежний ответ сохраняется как история, а действующее
требование обновляется после утверждения. Такая связь позволяет проверить
понимание агента и передать контекст другому агенту; она не заменяет утверждение
ТЗ и не доказывает переносимость активного исполнения между средами.
Записи интервью служат источниками, а не параллельным владельцем требований.

### Существенные условия качества: запись и передача — DRAFT

Уточнение FTR-003 по инструкции пользователя от 2026-09-15 помогает сохранить условия, меняющие поведение, границы реализации, приёмку, восстановление, совместимость, работу с данными или затраты. Например, «после сообщения об успешном сохранении запись нельзя потерять при перезапуске» связывается с исходным ответом, областью действия и проверяемым примером. Для текущего применения достаточно читаемого структурированного представления уже существующих требований C-003/C-002. Оно производное: факты остаются в своих constraints/metrics/acceptance, новая нормативная схема и отдельный Quality Profile artifact не создаются. Пользователь видит смысл, источник, статус, область и способ проверки либо открытый вопрос. Агент ведёт ссылки; человек не заполняет YAML или каталог concerns. [FTR-003](06_Features.md#quality-requirements-behavior) определяет точное поведение.

Сохраняется текущий порядок интервью: использовать известные ответы, выяснять существенные условия обычным языком, не задавать вопрос, который ничего не изменит. Специальные правила о непредоставленных юридических требованиях и доступности из §5 не заменяются новым blanket gate; непроверенное явно остаётся непроверенным, а небезопасное зависимое действие не получает разрешения.

Сейчас внедряется документальное уточнение; оно не доказывает экономию, не отменяет уже принятый сбор условий качества и не запускает pilot или разработку.

### Проверяемые примеры в ТЗ

системы для основных процессов и исключений. Агент составляет их по ответам
интервью; пользователь проверяет соответствие ожидаемых результатов своему
замыслу. Каждый пример понятным языком описывает исходную ситуацию, действие

Например: сотрудник отправляет заявку — руководитель получает уведомление;
руководитель отклоняет заявку — сотрудник видит причину. Это иллюстрации формы

Original request, actor, problem, desired outcome, constraints, non-goals, assumptions, unknowns, source и sensitive flags.

Registry индексирует Feature Passports, но не заменяет их и не смешивается с execution/verification/protected registries.

### FTR-031: rbac abac — доступ к полям внутри приложения, DRAFT

Текущий запрос связывает материал `2.0-candidate` от 2026-09-15 с существующей
[FTR-031](06_Features.md#ftr-031-contract), technical identifier `rbac_abac`.
Подтверждено направление: уполномоченный непрограммист настраивает доступ к
значениям существующих полей внутри созданного на основе AOS приложения.
Сокращённый состав и конкретная семантика candidate остаются PROPOSAL;
проработка не активирует DEFERRED feature и не принимает всю редакцию.

Пользователь открывает «Настройки → Доступ к полям», выбирает уже существующие
объект и роль, задаёт «Видеть / Заполнять при создании / Изменять», при необходимости
добавляет «только свои / только назначенные мне», проверяет искусственный пример,
видит изменения и применяет новую версию. Сервер приложения обеспечивает этот
доступ на реальных путях чтения/записи. Один редактор матрицы без enforcement
не выполняет результат. YAML, код и внутренние термины для обычной настройки не нужны.

Первый срез — PROPOSAL: одна страница настроек, плоские поля, role grants и
ограниченный набор условий, одна активная модель на область, версии/откат и
один адаптер первого приложения. Модуль переиспользует его identity, роли,
доступ к объектам и хранилище; не создаёт login, не назначает роли/администраторов
и не редактирует структуру БД, типы полей или бизнес-правила. Полноценные IAM,
policy marketplace, свободные выражения и LLM на каждом запросе не требуются.

Управление настройками разрешает host-приложение через MANAGE_FIELD_ACCESS в
конкретной области. Это прикладная административная возможность, включая выдачу
grants своей роли в делегированных пределах; она не равна автоматическому чтению
значений и не предоставляет полномочий coding agent AOS. FTR-019 остаётся владельцем
базовой границы действий AOS; прикладное «Применить» не требует C-006 на каждый клик.

Поддержка более сложных каналов доступа добавляется по ТЗ приложения. Обязательный
для него экспорт нельзя молча исключить ради облегчения модуля. Польза проверяется
по правильности итоговой матрицы, отсутствию пропущенных расширений доступа,
ошибкам и помощи пользователю; испытание и экономия NOT_RUN/UNKNOWN.
[Architecture](02_Architecture.md#rbac-abac-contract) владеет стыками,
[Development](03_Development.md#rbac-abac-verification) — проверками,
[Reference](05_Reference.md#rbac-abac-source) — происхождением и ограничениями источника.

<a id="aos-origin-project-scope"></a>

### Проекты текущей версии и позднее подключение других систем

В текущем интервью пользователь определил границу проектируемой версии: AOS
работает только с проектами, созданными с его помощью. Это включает начало
нового AOS-проекта и дальнейшую работу с уже созданным AOS-проектом. Работа
с другими уже функционирующими системами планируется позднее отдельным модулем.
Это выбранный scope, а не утверждение о проверенной runtime-поддержке.

Пользователь уточнил: разработка такого проекта должна вестись в инфраструктуре
AOS. Одного интервью и ТЗ, подготовленных AOS, недостаточно, если последующая
разработка ведётся независимо от AOS. Выбрано участие AOS в процессе разработки,
а не только в выдаче документации.

Предположение пользователя о «специальной среде» не считается доказательством
существующего runtime или выбором отдельной IDE/виртуальной машины. По текущему
[архитектурному описанию](02_Architecture.md#3-модель-слоёв) AOS предусматривает
подготовку задач, ограниченное исполнение, проверки и сохранение состояния;
конкретные средства исполнения и окружение требуют своего профиля.

Пользователь разрешил ручное изменение кода программистом. Такие изменения
допустимы в проекте, разработка которого ведётся с AOS; обязательность выполнения
всех правок только агентом через заранее созданную задачу AOS не выбрана.
Пользователь принял порядок обработки таких правок: перед следующей работой
агент обнаруживает изменения, сохраняет их и проверяет, не нарушили ли они
согласованную работу системы. Если всё в порядке, агент учитывает актуальное
состояние и продолжает работу. Если изменилось поведение или возникло
противоречие с ТЗ, агент объясняет расхождение и уточняет намерение пользователя
до зависимого продолжения. Он не переписывает требования по факту изменения
кода и не исправляет ручную правку вопреки ещё не уточнённому намерению.
Ручная правка сама по себе не означает проверенность результата и не разрешает
агенту автоматически перезаписывать её. Недоступная или неполная проверка не
считается подтверждением, что всё в порядке; сохраняются действующие правила
для UNKNOWN/NOT_RUN. Способ обнаружения и хранения изменений остаётся HOW;
обязательный постоянный фоновый монитор этим решением не выбран.

Обследование существующего проекта в J-002 и FTR-002 для текущей версии относится

### Recovery / FTR-033 — продолжение существующего проекта, DRAFT

По текущему поручению candidate v0.2 от 2026-09-15 привязан к существующей
[FTR-033](06_Features.md#ftr-033-contract): display name Recovery, identifier
`recovery`. Направление подтверждено, подробности — PROPOSAL; DEFERRED сохраняется.
Модуль помогает подхватить работающий, незавершённый или зашедший в тупик проект,
включая созданный вне AOS. Он не расширяет автоматически текущую версию AOS.

Первый предложенный результат — понятная оценка одной выбранной области с
источниками, непроверенным и ограничениями, решение человека о направлении и
минимальный пакет для одной следующей задачи PLAN. Исходный проект не меняется:
read-only относится к нему и VCS; разрешённые отчёт/состояние сохраняются во
внешнем workspace. Управляемое продолжение не требует переписать код, topology,
все документы или установить AOS в исходный project root. Действительные прежние
решения сохраняются в своём scope, их не требуется принимать заново из-за происхождения проекта.

Для владельца: цель, наблюдаемый симптом, что нельзя потерять → bounded assessment
→ одна рекомендация с существенной альтернативой/остановкой → выбор exact
направления и следующей задачи → пакет и подтверждение получения. Технические
факты выясняет агент; желаемое и сохраняемое бизнес-поведение не угадывает по коду.
ADOPT/RECOVER обозначают intent, не диагноз и не отдельный обязательный вопрос.

HANDOFF_PREPARED означает только готовность пакета, HANDED_OFF — подтверждённое
получение той же редакции и доступ к нужным inputs. Ни одно не означает ремонт,
успешные runtime tests или разрешение исполнения. Исправление выполняет обычный
workflow после подготовки задания и отдельно применимых полномочий. FTR-014
сохраняет восстановление выполнения AOS; FTR-004 — optional installation.

Не обещаются окончательная root cause по static scan, восстановление потерянных
данных, полное здоровье продукта, сроки/стоимость или возврат в production.
Корректный результат может быть планом проверки, уточнением или паузой.
Польза измеряется пониманием результата без технической подсказки, достаточностью
handoff и затратами сопровождения; эффект реального ремонта — отдельным выполненным
slice. Pilot, usability и экономия NOT_RUN/UNKNOWN. [Architecture](02_Architecture.md#recovery-contract)
владеет records/стыками, [Development](03_Development.md#recovery-verification) —
проверкой, [Reference](05_Reference.md#recovery-source) — provenance материала.

<a id="repository-graph-purpose"></a>

### Модуль «Граф RAG»: поиск, карта и объяснение отличий

**Простыми словами:** агент находит нужные документы и код, показывает связи между ними и объясняет, чем наблюдаемое состояние отличается от описанного замысла. Например: «Документ требует проверку экспорта; тест найден, но ещё не запускался». Результат помогает подготовить следующее действие, а не объявляет проект исправным по наличию файлов.

По инструкции пользователя от 2026-09-14 существующая [FTR-017](06_Features.md#ftr-017-contract) переименована в **«Граф RAG»** и составляет одноимённый модуль из одной фичи. Граф и retrieval — две группы поведения внутри неё, с общим разрешённым корпусом и отдельными критериями. Это подтверждение названия, состава и направления документационной проработки; реализация и включение в roadmap/ядро требуют своего применимого основания.

Первая область пилота — разработка самого AOS, в границе Development Factory и Knowledge. После создания AOS модуль может помогать в проектах, созданных через AOS, в их разрешённой области; это не активирует FTR-033 для сторонних работающих систем. Он не входит автоматически в первый Product Runtime slice и не обязателен для каждого запроса. Установленная поставка использует источники своего проекта и не зависит от development-репозитория AOS.

Базовый документируемый профиль: один локальный corpus; точный и текстовый поиск; Markdown/text, явно поддержанные JSON-ссылки и ограниченная статическая структура Python; объяснённый обход связей; различимые «запроектировано»/«наблюдается», mapping и Delta; компактный контекст существующему агенту; проверка актуальности и продолжение по разрешённым сохранённым ссылкам. Пользователь задаёт вопрос обычным языком без ручного графа. Отсутствие полной карты не блокирует поиск; сравнение требует достаточных сопоставимых источников и не доказывает отсутствие по поисковой выдаче.

Граф/индекс — восстановимые производные представления. Они не владеют требованиями, архитектурными решениями, Project Memory, разрешениями, Evidence или статусами принятия. Context Pack остаётся у FTR-016, выбор/исполнение — у существующих owners. Сбой/отключение модуля оставляет прямой поиск и стандартный flow. Индекс активируется при доказанной поисковой потребности; выигрыш по качеству, времени и полным затратам пока не измерен. Роли не требуют отдельных агентов.

Уточнение impact-поведения — **DRAFT**, адаптация DIP-R1: на вопрос «что стоит перепроверить после этого изменения?» модуль показывает зависимости и возможных потребителей с основаниями, отдельно — условные связи и непроверенное. Например, ссылка на документ сама по себе не делает экран его зависимым потребителем. Ответ различает замысел и наблюдение, объясняет пределы поиска и предлагает одно следующее действие; он не утверждает, что найденные части сломаны или обязательно требуют изменения. Это представление внутри FTR-017, с [точной семантикой](06_Features.md#graph-rag-impact-behavior), без новой фичи или обязательной карты для обычной работы.

В базовый профиль не входят обязательные vector/graph DB, embeddings, платная переформулировка/ранжирование, отдельный answer-agent, сервер, watcher/daemon, Git hooks, облачная синхронизация, marketplace, универсальный parser, runtime instrumentation и автоматическое исправление по Delta. Поддержанный host не означает универсальную совместимость или sandbox внешнего агента. Lifecycle и Git delivery сохраняют существующие границы.

Нынешнее расширение заменяет прежние исключения «RAG и сравнение AS-IS/TARGET вне первой версии» в перенесённом R2. Исходник R2 сохраняется историческим; его source-bound safety и прямой fallback продолжают действовать. [Архитектура](02_Architecture.md#graph-rag-module-contract), [проверки](03_Development.md#graph-rag-verification), [R3 и crosswalk источников](05_Reference.md#graph-rag-r3-source). Остальные FTR сохраняют свои dispositions.

<a id="event-diagnostics-purpose"></a>

### Диагностика попытки действия — ограниченное уточнение FTR-025, DRAFT

Пользователь должен иметь возможность понять, какое действие пытались выполнить, к какой попытке/задаче относится сообщение и чем она закончилась. Диагностическая запись помогает разбору, но не определяет состояние проекта: отсутствие записи не доказывает отсутствие действия, а начатая попытка без результата не объявляется ни успешной, ни неуспешной.

В текущую [FTR-025](06_Features.md#event-diagnostics-behavior) включается контракт такого результата для одного выбранного action. Сначала проверяется, достаточно ли существующего report/ledger; новый файл или отдельный writer не обязательны. Дополнительная диагностика не заменяет обязательную историю controller, Evidence и текущие результаты проверок. Её отказ не переигрывает действие и не скрывает его исход; ограничение показывается через существующий безопасный канал, если он доступен.

Это документальная адаптация FTR-025-A R2, не выбор FTR-025 для реализации и не закрытие её полного incident/lesson/regression scope. Нет сбора свободных payload, prompts или secrets; нет скрытой записи из read-only операций. Формат, destination, конкретный механизм записи и численные лимиты выбираются при bounded integration binding. [Проверки](03_Development.md#event-diagnostics-verification) требуют полезного положительного результата и отказного пути; runtime и польза пока NOT_RUN.

## 10. MVP-кандидат — PROPOSAL

Safe entry/discovery, adaptive intake, Product Spec/Feature Passport, one Task Brief, separate Execution Authorization, scope/risk/human authority, one change, Evidence mapped to acceptance, human acceptance, compact handoff и lesson proposal.

## 11. Критерии первого vertical slice

Slice решает identified user problem, даёт observable result, имеет described I/O/states/failures/recovery, executable acceptance/negative cases, работает без full Control Plane, имеет minimal dependencies, создаёт learning и не включает implicit Git delivery.

## 12. Модель product acceptance

Feature documentation-ready, когда определены users, trigger, I/O, observable result, states, failures/recovery, non-goals, acceptance, negative cases, human decisions и research gaps.

Product acceptance требует explicit human decision по exact revision.

## 13. Кандидатные показатели успеха — PROPOSAL

Time intent→Task Brief, clarification loops, scope drift, resume time, review time, false-green incidents, tasks without re-planning, lesson reuse, user understanding, Governance overhead и maintainability.

Для подготовки к автономной реализации основной показатель — **человеческое время
на принятый результат при сохранении качества**. В объявленной группе заданий
суммируются минуты подготовки, ответов/координации, проверки и ручных исправлений,
включая неудачные попытки и подготовку используемых инструкций. Сумма делится на
число результатов с явным человеческим принятием exact revision (§12), а не на
число agent PASS или завершённых runs. Один результат не считается повторно по
числу проверок. При нуле принятых результатов отношение не определено; неизвестные
затраты остаются UNKNOWN, частичная сумма не выдаётся за полную.

Рядом показываются причины вмешательств, вопросы с уже доступным ответом
(с locator), существенные пропуски требований/ошибок, ложные блокировки допустимого
решения и затраты неудачных попыток: человеческое и агентское время, доступные
tokens/денежные расходы. Меньше вопросов само по себе не успех, если агент
пропустил необходимое решение человека. Экономия не подтверждена при ухудшении
приёмки, росте существенных пропусков, ложных блокировок или нарушении полномочий.

Текущий и уточнённый подход можно сравнить на одинаковых заданиях с одинаковыми
критериями качества, scope и полномочиями. Фиксируются редакции входов, условия
модели/среды и ресурсные пределы; эффект знакомства с задачей указывается отдельно.
Порог полезной экономии и бюджет будущего сравнения согласуются до запуска.
Это предложение измерения, не фактические данные и не разрешение на прогоны.
Компактная фиксация — в [существующем отчёте Development](03_Development.md#human-effort-report).

## 16. Модульное ядро — DRAFT состава

Пользователь подтвердил направление: полные описания выбранных фич при небольшом обязательном ядре. Этот раздел формирует продуктовый contract предложения; утверждение точного состава остаётся отдельным решением MOD-DEC-01. Единственный индекс возможностей и их placements находится в [06_Features](06_Features.md#4-индекс-каталога).

Основной пользователь — владелец проекта, ставящий ограниченную задачу агенту. Основной результат: понятный проверенный итог одной разрешённой задачи с доказательствами, решением человека и возможностью продолжения. Система должна обеспечивать цепь:

намерение → уточнённые требования и контекст → одна задача и отдельные полномочия → выполнение → проверка → при дефекте расширяемая диагностика/исправление → итоговая проверка → review и человеческое решение → сохранённое состояние.

Для нового проекта discovery фиксирует отсутствие существующего repository и запрашивает лишь необходимые сведения; для существующего исследует разрешённую область. Архитектурная необходимость выявляется до исполнения: если без решения задачу нельзя выполнить, модуль FTR-005 либо явное внешнее человеческое решение требуется для этого сценария. Git-доставка FTR-015 следует после результата только при отдельном запросе; её отсутствие не отменяет техническое завершение.

Полные модули сохраняют задачи установки/обновления/удаления, backlog, архитектурного выбора, Git-доставки, audits, patterns, CI и incidents. Отсутствие модуля допускается лишь для сценария, который не требует его результата. Невозможность выполнить required check никогда не заменяется PASS; модуль не получает право менять scope, authority или state другого владельца.

В scope первой документационной версии входит описание конечного поведения выбранных возможностей и требования переносимости; реализация и одновременное подтверждение поддержки всех ОС сюда не входят. Полнота ТЗ не означает одновременный запуск всех модулей. FTR-017/FTR-030 предлагаются как поддерживающие модули: их контракт описывается полностью, но индекс активируется после измеренной поисковой потребности, strict tools — для определённых стабильных contracts. Локальная базовая проверка валидности данных не зависит от установки отдельного модуля tools.

<a id="autonomous-project-outcome"></a>

### Общий результат выбранной версии проекта — DRAFT

Источник уточнения — поручение исправить системный пробел SYS-01 по плану
документационных правок. Конечная выбранная версия, включённые возможности,
общие пользовательские сценарии, ограничения и исключения принадлежат Product
Spec; поведение частей — их Feature Passports. Полнота версии не выводится из
каталога всех FTR или числа завершённых частей.

После согласования достаточного задания и отдельных полномочий агент доводит
эту версию до одного проверяемого технического результата: реализованы включённые
части, работают обязательные взаимодействия, подтверждены общие критерии,
сохранены данные и состояние продолжения. Обычная декомпозиция, выбор следующей
внутренней работы, интеграция и correction не требуют промежуточного Human ACCEPT.
Человек получает общий review package; техническое завершение не включает
автоматически Git delivery, deployment, эксплуатацию или пользовательское принятие.

Различаются два применения: внешний coding agent создаёт выбранную версию AOS;
будущий AOS создаёт версию пользовательского проекта по его ТЗ. Состав и критерии
этих проектов не смешиваются. Product tests AOS не доказывают автономность его
внешней разработки; готовое ТЗ пользовательского проекта не доказывает его сборку.
Нынешний S0–K4, grouping/dispositions и открытые SC-DEC/MOD-DEC сохраняются.
Это уточнение не выбирает более широкую версию AOS и не выдаёт launch authority.

Общая task, внутренние работы, зависимости и завершение определяются
[Development §25.0](03_Development.md#autonomous-project-development).

<a id="autonomous-module-outcome"></a>

### Автономная сборка каждого выбранного модуля

Требование человека: единицей автономной разработки является весь выбранный
модуль. Для модуля из одной фичи границы совпадают; для составного модуля
внутренние FTR сохраняют contracts и критерии, но не требуют отдельных ручных
запусков, разрешений на каждый обычный шаг или промежуточного Human ACCEPT.

До запуска согласованы результат модуля, входящие FTR и exact contracts,
внешние интерфейсы/версии, target/environment, dependencies, данные/providers,
полномочия, лимиты и проверяемые критерии. Агент затем самостоятельно выполняет
декомпозицию, сборку фич, внутреннюю интеграцию, проверки, диагностику/correction,
сохранение состояния и supported resume до единого технического результата.
Declared интеграции с ядром и уже доступными модулями входят в тот же scope.
Успешные отдельные фичи при неработающем модуле не означают completion.
Если модуль включён в заранее выбранную общую версию, его сборка и проверка
являются внутренней работой [общей задачи](#autonomous-project-outcome);
самостоятельный запуск модуля сохраняет собственную task и отдельную authority.

Человек получает один итоговый review package. Пользовательский dogfood,
принятие результата и protected/Git delivery остаются отдельно от технической
сборки. Human gates, являющиеся поведением самого продукта, реализуются и
проверяются с явно синтетическими fixtures; такие fixtures не выдаются за
реальные человеческие решения или полномочия разработки.

Если обязательное решение, доступ или внешняя зависимость отсутствует до старта,
модуль не готов к автономному запуску. Неожиданный material conflict либо выход
за authority даёт точную остановку; это незавершённый автономный run, а не PASS.
Обычный дефект и выбор обратимого HOW в согласованных границах решает агент.
Правило относится ко всем модулям по мере их выбора; полная подготовка всех
поздних dossiers одновременно не требуется. [Development](03_Development.md#autonomous-module-development)
задаёт достаточность входа и доказательства результата.

<a id="core-connector-outcome"></a>

### Подключение к ядру: коннекторы и очереди — R7

Человек выбрал смешанную модель обмена и наличие минимальных локальных
коннекторов/очереди уже в первом ядре. Ядро предоставляет объявленные точки
подключения: быстрый read-only запрос возвращает результат напрямую, команда
с эффектом или отложенная работа доставляется через сохраняемую очередь,
событие сообщает наблюдение объявленным consumers. Вызов внутренних классов
или storage другого модуля не заменяет публичный интерфейс.

Пользователь видит отдельно приём запроса, ожидание/доставку, фактическое выполнение,
результат и причину остановки. Повтор доставки не должен повторять завершённый
логический эффект. Отказ optional-модуля не выключает независимые возможности
ядра; required недоступная capability сохраняет незавершённый критерий.

Модуль подключается после проверки contracts/capabilities и интеграционных
сценариев. При отключении новая работа больше не принимается, ожидающая явно
приостанавливается, выполняющаяся reconciled. Удаление реализации не означает
удаление данных; зависимые consumers и сохранённые сообщения учитываются до
удаления. Обновление, удаление данных и migration имеют отдельный объявленный scope.

Это расширение базовых обязанностей core, а не новый backlog FTR-007 или
обязательный внешний broker, daemon/service либо dynamic plugin loader.
Локальная композиция допустима. [C-015/C-016](02_Architecture.md#module-connector-queue)
задают contracts; [протокол агента](03_Development.md#feature-module-protocol)
определяет подготовку, подключение и проверку каждого выбранного модуля.

<a id="scaffold-core-outcome"></a>

## 17. Scaffold и первое ядро — SCAFFOLD_CORE_DRAFT

Пользователь результата — владелец проекта, заранее задавший достаточную bounded задачу и полномочия. Наблюдаемый итог первого ядра: одна разрешённая локальная задача проходит от достаточного input через execution/check/diagnose/correct до проверенного результата, понятного review package и состояния, из которого работа воспроизводимо продолжается. Владелец не управляет каждой correction и каждым переходом между согласованными срезами.

**Scaffold разработки AOS** — подготовленная запускаемая основа implementation target и локального dev/check cycle. Она не устанавливает AOS в произвольные чужие проекты и не включает полный installer/update/uninstall FTR-004. Его базовый контракт:

- **Actor/trigger:** внешний агент получает принятую задачу S0, exact target и отдельную authority.
- **Входы:** согласованный [профиль](02_Architecture.md#scaffold-core-profile), достаточный исходный Product/Feature Contract, поддержанное окружение, path/operation boundary и проверенный внешний host.
- **Результат:** минимальная запускаемая поверхность продукта, объявленные runtime/dev dependencies, инструкции и entrypoints локальных checks, воспроизводимая идентификация candidate, durable state/evidence для разработки. Toolchain и test harness доступны без запуска ещё не реализованного AOS.
- **Порядок:** наблюдение target → подготовка только отсутствующей разрешённой основы → проверка запуска/окружения → сохранение candidate и handoff K1. Существующий target допускается только после inventory; scaffold не очищает его до «чистого» состояния.
- **Отказы:** wrong root/identity, конфликт user files, path escape, missing dependency, unavailable required check или прерванный effect дают точную причину и незавершённый критерий; automatic overwrite и слепой retry запрещены.
- **Recovery:** сохранить observations; reconcile planned/actual effects; повторить только доказанно незавершённое действие по fresh boundary. Разрушительный rollback не входит автоматически.

| Срез | Достаточный вход | Результат и критерий выхода |
|---|---|---|
| S0 — development scaffold | Решения SC-DEC-01…03, фактический launch SC-DEC-04, внешний host/preflight | В чистом поддержанном окружении воспроизводимы prepare/start/check; dependencies объявлены, source/installed claims различены, unrelated state сохранено. Handoff содержит candidate, commands/provenance, объявленные интерфейсы C-015/C-016 и профиль подготовки подключения/очереди; следующий K1 |
| K1 — достаточная задача | S0, заранее подтверждённые problem/outcome/scope и source inputs | Базовые FTR-001/002/003/006 формируют source-bound Intent/Spec/Passport/Brief. Существующие решения читаются без повторного интервью; material missing input блокирует только зависимое действие. End-to-end отрицательный пример не получает выдуманное approval |
| K2 — один разрешённый effect | K1, current parent authority, preview и permission; базовые state/validation capabilities доступны до effect | FTR-009/019/010 создают точный candidate и effect record; FTR-013/011 проверяют scope/result. Положительный effect проходит, denial не меняет target. До первого queued effect доступны регистрация коннектора, durable queue, persistence, validation и reconciliation; сообщение не заменяет fresh admission |
| K3 — correction и continuation | K2, известные критерии/checks, durable observations | При дефекте полный controller loop диагностирует, выполняет bounded correction и перепроверяет candidate. Прерывание до/после effect, run pause и fresh-session resume не теряют ledger и не повторяют effect; duplicate delivery/потерянный acknowledgement и отмена различены |
| K4 — цельный core result | K1–K3, финальный exact candidate и применимые required checks | FTR-008/012/016 дают понятный status/review/handoff. Интегрированный direct/queued journey с коннекторами подтверждает каждый критерий, сохраняет NOT_RUN/UNKNOWN и не выдаёт технический результат за Human ACCEPT или Git delivery |

S0–K4 — порядок доказательства результатов, а не запрет заранее реализовать обязательного consumer. Минимальные state/identity/authority/check гарантии должны появиться до первого effect K2; детализацию реализации выбирает агент. Все срезы могут принадлежать одной исходной task; переходы не требуют нового человеческого решения, если цель, contracts и полномочия сохраняются. Человек выбрал явные lifecycle-переходы execution → validation → при дефекте execution; их применимость и atomic admission задаёт [Development](03_Development.md#core-lifecycle-transitions). Сами S0–K4 не являются lifecycle stages.

В автономном положительном journey execution ссылается на exact Product/Feature Contract, принятый до run и переданный во входах. K1 может прочитать его напрямую или подготовить производные DRAFT-представления, сохранив исходную ссылку; смысловая похожесть нового текста не переносит human acceptance на новые bytes. Если для дальнейшего effect требуется принять именно новую product revision, это уже материальный input gap и Human Gate, а не повод автоматически подтвердить её агентом.

**Приёмка автономного интервала:** заранее достаточные inputs позволяют дойти до K4 без новых product решений; обычный дефект исправляется в scope; после поддержанного host interruption работа продолжается по сохранённому состоянию; required checks и effects согласованы с exact candidate. Проверки [SC-T01…26](03_Development.md#scaffold-core-checks) задают наблюдаемые Evidence. Usability claims «человек понял результат» остаются отдельным human observation и не заменяются агентской оценкой.

Правило manual dogfood сохраняет смысл проверки пользовательской пользы. Для этого DRAFT предлагается: сначала разрешённая техническая реализация S0–K4 и воспроизводимые positive/negative journeys, затем пользовательский dogfood для принятия/расширения продукта. Рутинная correction не требует повторного ручного dogfood; изменение этого порядка относится к SC-DEC-01. Без принятия уточнения нельзя заявлять весь интервал как уже разрешённую automation.

Будущие фичи прорабатываются по одной после выбора человеком. Они не входят в первое ядро автоматически. Полный backlog, installer, архитектурный модуль, CI/Git delivery, search/index, patterns, audit tools, UI и domains остаются вне этого интервала, кроме явно названной необходимой базовой гарантии. [Точный scope каждой core-возможности](06_Features.md#core-first-scope) принадлежит dossier; [правило расширения](03_Development.md#feature-integration-readiness) проверяет только реальные стыки.

## 18. Переносимость первого ядра

Человек задал переносимость системы между ОС и выбрал macOS первой средой
проверки. Ядро и форматы сохраняемых предметных данных не должны зависеть от
конкретной ОС. Linux и Windows — целевые платформы, поддержка которых
подтверждается последующими запусками; непроверенное не объявляется поддержанным.

Первое ядро должно пройти проверки на выбранном профиле macOS. Версия ОС,
архитектура машины, runtime и ограничения adapter фиксируются до launch;
одна проверенная конфигурация не доказывает все версии macOS. Разработка сначала
на macOS не допускает macOS-only зависимости в ядре. Переносимость обязательна
с S0, но создание всех платформенных adapters в первой реализации не требуется.

ОС-специфические возможности доступны через объявленные adapters/capabilities.
Нет обязательной зависимости ядра от macOS-приложений, Unix shell или конкретного
терминала. Отсутствие capability блокирует зависимый сценарий; независимые
возможности сохраняются. Альтернатива допустима только при сохранении authority,
result validation и recovery, иначе нужен точный BLOCKED/UNKNOWN.

Чтение переносимого state на другой ОС не означает разрешение resume: paths,
permissions, environment, authority и actual effects проверяются заново.
Поведение и проверки принадлежат [Architecture](02_Architecture.md#core-platform-boundary)
и [Development](03_Development.md#core-platform-checks). Выбор stack/target/host
остаётся в существующем SC-DEC реестре; здесь не создаётся новый набор решений.
