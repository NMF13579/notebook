Я бы сделал эту фичу одной из ключевых возможностей AOS. Она не должна быть «поддержкой FPF», а самостоятельным механизмом, который может работать как без FPF, так и вместе с ним.

# Feature: FPF Reasoning Integration

## Назначение

Интеграция First Principles Framework (FPF) в Documentation Assembly Pipeline для повышения качества анализа требований, проектирования и архитектурных решений.

FPF не управляет агентом и не заменяет жизненный цикл AOS. Он выступает как слой инженерного рассуждения, который помогает агенту:

* отделять факты от предположений;
* выявлять противоречия;
* анализировать альтернативы;
* строить аргументированные решения;
* отслеживать происхождение и актуальность Evidence;
* уменьшать количество ошибок проектирования до начала реализации.

---

## Цель

Превратить LLM из генератора текста в инженерного помощника, который способен:

* анализировать проблему;
* задавать правильные вопросы;
* выявлять пробелы в ТЗ;
* аргументировать архитектурные решения;
* документировать причины выбора;
* работать воспроизводимо.

---

## Проблема

Современные LLM хорошо генерируют текст, но:

* смешивают факты и предположения;
* делают скрытые assumptions;
* редко предлагают альтернативы;
* не показывают слабые места решения;
* не различают уровень уверенности;
* плохо отслеживают происхождение информации.

В результате возникают:

* ошибки Specification;
* лишние задачи;
* неверная декомпозиция;
* переделка архитектуры;
* потеря требований.

---

## Основная идея

FPF не должен быть отдельным режимом работы.

Он должен работать внутри каждого этапа Documentation Assembly Pipeline, помогая агенту принимать более качественные решения.

Project Brief
      ↓
FPF Analysis
      ↓
Specification
      ↓
FPF Analysis
      ↓
UX Contract
      ↓
FPF Analysis
      ↓
Task Decomposition
      ↓
Task Brief

---

## Архитектура

Система состоит из двух частей.

### 1. FPF Lite (AOS-FARM)

Минимальный встроенный профиль.

Используется всегда.

Содержит только необходимые правила:

* FACT vs HYPOTHESIS;
* UNKNOWN;
* ASSUMPTION;
* ALTERNATIVES;
* EVIDENCE;
* RATIONALE;
* SCOPE CHECK.

Работает без внешней библиотеки.

### 2. Full FPF (AOS-Solution-Patterns)

Полная справочная библиотека.

Содержит:

* полный каталог FPF;
* compatibility map;
* examples;
* snapshots;
* provenance;
* retrieval;
* дополнительные паттерны.

Используется только по необходимости.

---

## Основные возможности

### 1. Анализ требований

Для каждого требования агент определяет

* факт;
* предположение;
* гипотезу;
* неизвестное;
* решение человека.

### 2. Поиск противоречий

Находит:

* конфликтующие требования;
* несовместимые ограничения;
* неоднозначные формулировки;
* отсутствующие решения.

### 3. Анализ альтернатив

Для каждой архитектурной задачи агент должен предложить минимум два варианта.

Для каждого:

* преимущества;
* недостатки;
* риски;
* влияние;
* область применимости.

### 4. Decision Rationale

Каждое важное решение сопровождается причиной выбора.

Например

Выбран OAuth.
Причина:
— лучше масштабируется;
— поддерживает внешних провайдеров;
— соответствует требованиям безопасности.

### 5. Evidence

Агент фиксирует

* какие утверждения подтверждены;
* какими источниками;
* какие остаются неподтвержденными.

### 6. Unknown Tracker

Все неизвестные собираются автоматически.

Например

UNKNOWN
Как долго хранить токен?
Нужно ли подтверждение почты?
Какой retention логов?

### 7. Alternative Comparison

При выборе решения автоматически строится сравнительная таблица.

### 8. Weak Link

Определяется самое слабое место аргументации.

### 9. Architecture Review

Перед созданием задач агент проверяет:

* все ли требования понятны;
* нет ли противоречий;
* достаточно ли информации.

### 10. Human Decision Package

Человеку показывается только:

* варианты;
* риски;
* неизвестные;
* рекомендация.

Без внутренних рассуждений модели.

---

## Где используется

### Project Brief

Помогает правильно понять проблему.

### Specification

Главная область применения.

### UX Contract

Проверяет

* пользовательские сценарии;
* альтернативные flow;
* пропущенные состояния.

### Task Decomposition

Помогает разбивать задачи.

### Architecture Decision

Оценивает варианты.

### Human Review

Формирует пакет решений.

---

## Где НЕ используется

FPF не участвует в

* Code Assembly Pipeline;
* commit;
* push;
* merge;
* release;
* lifecycle;
* approval;
* Risk Profile;
* execution authorization.

---

## Интеграция с AOS

AOS-FARM
│
├── Documentation Assembly Pipeline
│      │
│      ├── FPF Lite
│      │
│      └── Human Review
│
├── Code Assembly Pipeline
│      │
│      └── Scope Check
│
└── Governance

Полный FPF подключается из

AOS-Solution-Patterns

через pinned release.

## Основные артефакты

После анализа агент создаёт

* Problem Analysis;
* Architecture Rationale;
* Unknown Report;
* Alternative Comparison;
* Evidence Summary;
* Human Decision Package.

---

## Ограничения

FPF

не может:

* разрешать выполнение;
* менять Scope;
* назначать Risk Profile;
* принимать решения за человека;
* изменять Lifecycle;
* выполнять команды.

---

## Результат

После внедрения агент сможет:

* понимать ТЗ значительно глубже;
* автоматически находить противоречия;
* предлагать более качественные архитектурные решения;
* объяснять свои выводы;
* документировать причины выбора;
* уменьшать количество ошибок ещё до начала разработки.

## Моя рекомендация

Я бы ещё немного расширил эту фичу и назвал её не просто FPF Integration, а Engineering Reasoning Engine (ERE).

Тогда FPF станет первой поддерживаемой методологией, но не единственной. Архитектура будет готова к подключению и других методологий (DDD, C4, Arc42, Event Storming, Jobs To Be Done, Shape Up и др.) через тот же механизм.

Получится следующая модель:

Engineering Reasoning Engine
│
├── FPF
├── DDD
├── C4
├── Arc42
├── JTBD
└── будущие методологии

Такой подход значительно повышает долгосрочную расширяемость AOS без необходимости перестраивать ядро при появлении новой инженерной методологии.
